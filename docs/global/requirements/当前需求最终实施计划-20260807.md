## 2. 总体业务模型

### 2.1 商品和组织解耦

```text
商品 → 商品分类 → 仓库类型

组织 → 组织拥有的启用仓库 → 仓库类型

组织可用商品
= 该组织拥有的仓库类型所对应分类下的商品
```

商品不直接绑定组织、供应商和具体仓库。

### 2.2 具体仓库在业务单据中选择

- 商品只继承分类规定的仓库类型；
- 采购、销售、生产、领用、入库和出库单选择当前业务组织；
- 具体仓库必须属于当前组织；
- 具体仓库类型必须与商品分类仓库类型一致；
- 同一组织存在多个同类型仓库时，由业务单据操作者选择具体仓库。

### 2.3 库存只能过账一次

反向生成单据必须明确唯一库存执行者：

- 报损选择退货：采购退货单执行唯一一次出库；
- BOM退库：BOM退库单执行唯一一次入库；
- 领用正常退回：领用退回单执行唯一一次入库；
- 技术纠错：通过明确冲正流水处理，不直接删除库存流水。

## 4. 需求一：商品主档移除交易归属字段

### 4.1 目标

商品主档只描述商品本身，不提前指定：

- 所属组织；
- 默认供应商；
- 默认仓库。

实际组织、供应商和仓库在采购或其他业务单据中选择。

### 4.2 现有表调整

目标表：

```text
hspsi_goods_info
```

计划停止使用并最终删除：

```text
org_id
vendor_id
warehouse_id
idx_org_id
idx_goods_warehouse_id
```

明确不增加临时商品技术标识：

```text
is_temporary
source_type
source_id
```

“临时补充”只是采购单据内的快捷建档方式，保存后即为正式商品/SKU。建议索引：

```text
INDEX(goods_catg_id, status, deleted_at)
```

### 4.3 分类表不增加组织字段

现有分类表：

```text
hspsi_goods_info_category
```

继续使用现有：

```text
warehouse_type
```

建议补充查询索引：

```text
INDEX(warehouse_type, status, deleted_at)
```

不增加：

```text
org_id
org_ids JSON
org_scope_type
分类组织关联表
```

### 4.4 迁移策略

不能第一步直接删除商品字段，建议分两阶段：

1. 代码停止读写商品组织、供应商和仓库；
2. 审计所有业务调用和历史数据；
3. 观察一个稳定周期；
4. 再执行字段和索引删除迁移。

### 4.5 业务校验

- 商品保存必须选择有效分类；
- 分类必须配置有效仓库类型；
- 业务单据按组织仓库类型筛选可用商品；
- 库存过账再次校验仓库类型和商品分类一致；
- 后端不能信任前端传入的商品默认仓库。

## 5. 需求二：默认SKU与单据内商品/SKU快捷建档

### 5.1 数据库改动

无需新增表和字段，复用：

```text
hspsi_goods_info
hspsi_goods_info_sku
```

单据内的未保存商品/SKU只是前端草稿对象，不设置临时商品数据库标志。

### 5.2 商品资料页面默认SKU规则

- 打开新增商品页面时生成一条SKU草稿行；
- 第一条SKU自动 `isDefault = 1`；
- 用户无需点击“设为默认”；
- 新增第二条及后续SKU默认不是默认SKU；
- 后端保证有且只有一个默认SKU；
- 只有一条SKU时不能取消其默认状态；
- 导入和API创建执行相同校验。

### 5.3 未填写SKU时的“默认规格”映射

| SKU字段 | 商品来源或默认值 |
| --- | --- |
| `spec_models` | 商品 `spec_models`；为空时使用“默认规格” |
| `image` | 商品 `goods_image` |
| `pcs_qty` | `1`，表示1个该SKU等于1个基础单位 |
| `const_price` | 商品 `const_price` |
| `sale_price` | 商品 `sale_price` |
| `unit_type` | 商品 `unit_type` |
| `is_default` | `1` |
| `status` | 跟随商品状态，正常新建为启用 |
| `free_warranty_period` | 商品同名字段 |
| `is_alert_period` | 商品同名字段 |
| `alert_aty` | 商品同名字段 |
| `sort` | `0` |
| `remark` | 空，不复制商品备注 |

### 5.4 采购申请/采购订单内快捷建档

- 已有商品和SKU：直接选择；
- 已有商品但缺少SKU：在单据行内录入新SKU；
- 商品不存在：在单据行内录入商品，可同时录入SKU；
- 用户只填写商品信息、没有填写SKU时，按5.3自动生成“默认规格”SKU；
- 保存草稿或提交单据前，不向商品表和SKU表写入；
- 保存/提交时，在同一数据库事务中完成重复校验、创建正式商品、创建正式SKU、回填单据明细 `goods_id/sku_id` 和保存单据；
- 任一步失败时商品、SKU和单据一起回滚；
- 保存成功后的商品和SKU均为正式档案，正常出现在商品列表和后续业务选择中；
- 已有商品新增SKU时，如已有默认SKU则新SKU不是默认；如异常地没有默认SKU，则本次新SKU设为默认；
- 后端必须用唯一性校验和事务处理并发重复建档。

## 6. 需求三：业务单据附件

### 6.1 数据库方案

不新增通用附件表，也不新增附件日志表。

每张需要附件能力的业务单据主表增加：

```text
attachments JSON NULL
```

字段只保存附件元数据，不保存文件二进制或Base64。

示例：

```json
[
  {
    "id": "01JXYZ",
    "name": "采购合同.pdf",
    "objectKey": "purchase/orders/3812/01JXYZ.pdf",
    "size": 2381024,
    "mimeType": "application/pdf",
    "uploadedBy": "28",
    "uploadedAt": "2026-08-07T10:30:00+08:00"
  }
]
```

### 6.2 覆盖范围

附件字段只加在业务单据主表，不加在普通明细表。预计覆盖：

- 采购申请、采购订单、采购入库、采购退货、付款和退款主表；
- 销售订单、销售出库、销售退回、售后和收付款主表；
- 领用申请、领用出库、领用退回主表；
- 调拨、调整、盘点、报损、报损出库、报溢和通用出入库主表；
- 生产计划、BOM、BOM出库、生产入库和BOM退库主表。

实际迁移前必须从Prisma模型生成完整业务主表清单，逐表审阅，避免遗漏或错误加到明细表。

### 6.3 附件权限

- 草稿：允许新增和删除；
- 审核中：不允许上传或删除，只允许按单据查看权限预览和下载；
- 审核通过：允许新增，不允许删除历史附件；
- 作废、关闭：仅预览和下载；
- 后端按单据权限控制查看、上传、下载和删除。

### 6.4 操作审计

复用：

```text
hspsi_sys_oper_log
```

记录：

- 单据类型、单据ID；
- 附件ID和文件名；
- 上传、预览、下载、删除动作；
- 操作人、时间、IP和结果。

### 6.5 并发和文件一致性

- 更新附件JSON前锁定单据行，防止并发追加互相覆盖；
- 文件先进入OSS临时对象前缀；
- 单据字段更新成功后转入正式对象前缀或标记为正式引用；
- 数据库更新失败时清理临时对象；
- 定期清理没有业务引用的OSS孤儿对象；
- 数据库保存稳定 `objectKey`，不保存临时签名URL。

### 6.6 OSS配置

附件文件统一存储到通过环境配置接入的OSS，数据库只保存元数据。配置至少包括：

```text
OSS_REGION
OSS_BUCKET
OSS_ACCESS_KEY_ID
OSS_ACCESS_KEY_SECRET
OSS_STS_TOKEN（可选）
OSS_CNAME（可选）
OSS_UPLOAD_URL_TTL_SECONDS
OSS_DOWNLOAD_URL_TTL_SECONDS
OSS_ATTACHMENT_MAX_SIZE_MB
OSS_ATTACHMENT_MAX_COUNT
OSS_ALLOWED_EXTENSIONS
OSS_ALLOWED_MIME_TYPES
OSS_ORPHAN_RETENTION_HOURS
```

- 密钥只允许后端读取，不能进入前端构建产物或附件JSON；
- 私有Bucket通过后端鉴权后签发短期预览/下载URL；
- 文件大小、数量和格式使用配置控制，不做成业务字典；
- production使用独立Bucket或独立对象前缀，并设置最小权限账号。

孤儿对象运维命令：

```bash
# 默认只扫描并输出候选对象，不执行删除
pnpm --filter @hspsi/api attachments:orphans

# 明确确认扫描结果后执行删除
pnpm --filter @hspsi/api attachments:orphans:clean
```

production应由外部定时任务周期执行；对象年龄小于
`OSS_ORPHAN_RETENTION_HOURS` 的文件不会进入清理候选。

## 8. 需求五：入库明细自动生成批号

### 8.1 数据库改动

原则上不新增表和字段，继续使用各入库明细已有 `batch_no`。

### 8.2 已确认批号规则

自动批号格式固定为：

```text
PHYYYYMMDD
```

示例：上海时区2026年8月7日生成 `PH20260807`。

- 日期统一使用 `Asia/Shanghai`；
- 批号是按日归组标识，不带流水号，因此同一天自动生成的批号相同，不要求全局唯一；
- 采购入库、通用入库、生产入库等没有上游批次来源的全新入库明细，在批号为空时自动生成；
- 销售退货、领用退回、调拨入库、BOM退库等具有上游批次来源的入库，必须继承来源批号，以保证批次追溯，不重新生成批号；
- 只有新增明细行在批号为空时自动生成；
- 已有明细和已有批号不覆盖；
- 保存、编辑和重新打开不重新生成；
- 用户可以修改自动生成值，最终以用户保存值为准；
- 导入和API创建在批号为空时由后端补充；
- 复制历史入库单形成的是新明细，默认生成复制当日批号，不复制原批号；
- 批号生成不使用Redis流水，也不声明唯一约束。

## 9. 需求六：直接领用出库反向生成申请

### 9.1 数据库方案

原则上不新增表，复用：

```text
hspsi_draw_approve
hspsi_draw_approve_output
hspsi_business_document_relation
```

现有领用出库的 `draw_id`、`generation_key` 和单据关系表已用于区分反向生成方向及请求幂等；未为反向申请新增主表。

### 9.2 业务流程

1. 用户直接创建并完成领用出库；
2. 同一事务内扣减库存；
3. 反向生成领用申请；
4. 申请状态直接设为已通过；
5. 建立双向单据关系；
6. 对应申请后续被否决时，只将申请置为无效/已作废，已生效领用出库单和既有库存扣减保持有效；
7. 系统幂等地自动生成一张草稿状态领用退回单，来源指向原领用出库；
8. 草稿退回单不执行库存入库，必须由操作人员核对并完成后才实际退库；
9. 申请否决事件重复到达时不得重复生成退回单；

## 13. 需求十一：采购单据内快捷补充正式商品/SKU

### 13.1 业务定位

“临时补充”表示采购申请、采购订单录入时发现系统中缺少商品或SKU，因此当场补充档案；它不表示商品是临时商品。

不新增临时商品表，不修改商品表增加临时标志，复用：

```text
hspsi_goods_info
hspsi_goods_info_sku
hspsi_purchase_approve_detail
hspsi_purchase_order_detail
```

### 13.2 流程

1. 采购申请、采购订单明细允许选择“补充商品”或“补充SKU”；
2. 补充商品必须选择已有有效分类，分类决定仓库类型；
3. 补充SKU必须关联已有商品；
4. 未保存时只保留前端草稿；
5. 保存草稿或提交时才创建正式商品/SKU；
6. 没有填写SKU时按5.3自动创建默认规格SKU；
7. 创建出的 `goods_id/sku_id` 回填采购明细；
8. 全流程使用同一事务，单据失败则正式档案创建也回滚；
9. 创建成功后商品/SKU进入普通商品列表，可以正常采购、入库、领用、退库和追溯。

### 13.3 重复与并发规则

判重顺序确定为：

1. 先按标准化后的商品名称判断有效商品是否重复；
2. 商品名称不重复时才允许创建新商品；
3. 对已有商品补充SKU时，再按该商品下标准化后的SKU规格判断是否重复；
4. 当前SKU表没有独立 `sku_name` 字段，“SKU名”按 `hspsi_goods_info_sku.spec_models` 判断；
5. 商品名称或SKU规格任一重复时禁止新建，提示用户返回单据行选择已有商品/SKU；系统不自动替换用户当前输入。

标准化至少包括去除首尾空格；大小写和字符比较遵循数据库当前排序规则。并发保护建议增加：

```text
UNIQUE KEY uk_goods_name (goods_name)
UNIQUE KEY uk_goods_sku_spec (good_id, spec_models)
```

- 唯一约束同时约束软删除历史记录，避免有业务历史的同名档案被重新创建；
- 迁移前只读检查已确认：包含软删除记录在内的全量商品无重名，同一商品下无重复SKU规格；9条有效SKU规格均非空；
- 前端检查只用于及时提示，后端检查和数据库唯一约束才是最终防线；
- 网络重试触发唯一冲突时返回明确的“商品名称已存在”或“该商品下SKU规格已存在”，不创建部分数据。

- 批号生成格式、流水规则和请求幂等键；
- 单据关系技术类型、库存过账版本和是否自动生成；
- 领用历史“全部、未退清、已退清”计算筛选；
- 菜单列表是否显示ID。

BOM退库原因本期使用自由文本 `return_reason`；未来确需标准化时再增加 `bom_return_reason`。

### 16.3.1 当前数据库只读审计结论

审计目标：`hspsi-dev-ai`，MySQL 8.4.10。未执行任何DDL或DML。

- 有效字典类别65个，有效字典项239个；
- 没有空字典类别；
- 没有同类别、同 `dict_value` 的有效重复项；
- 已核对商品、采购、库存、生产、销售、售后和领用共50组核心业务字段，全部存量值均可映射有效字典；
- 现有3条软删除字典项都属于旧版 `production_shortage_status`：`4已采购、5已解决、6已终止`；
- 当前有效缺料状态为 `0待审核、1已生成采购申请、2已解决、3已终止`；
- 当前数据库没有任何 `attachments` 字段；
- 当前 `hspsi_production_material_out` 没有 `destination_type`；
- 拟新增的 `temporary_outbound_destination`、`bom_return_status`、`bom_return_reason` 均不存在，不会与当前类别代码冲突；
- `dict_catg_code` 为 `VARCHAR(32)`；`temporary_outbound_destination` 长度30、`bom_return_status` 长度17，均符合限制。

production部署前必须重复执行同样的只读审计，确认拟新增值无冲突后才执行迁移。

### 16.4 受影响页面与字段—数据库对应

| 页面/页面组 | 主要修改 | 页面字段与数据库对应 |
| --- | --- | --- |
| 商品资料 | 移除组织、供应商、具体仓库；自动默认SKU；列表ID | 商品字段→`hspsi_goods_info`；SKU字段→`hspsi_goods_info_sku`；ID→`goods_id` |
| 采购申请、采购订单 | 单据行内补充商品/SKU；附件；ID | 草稿无直接库字段；保存后→正式商品/SKU及明细 `goods_id/sku_id` |
| 各类入库页面 | 新增行自动批号、附件、ID | 批号→各入库明细现有 `batch_no` |
| 全业务单据详情 | 通用附件面板 | `attachments[]`→各业务主表 `attachments JSON` |
| 领用申请、领用出库 | 直接出库反向生成申请、双向跳转、附件、ID | 复用领用主表及 `generation_key/auto_created`、单据关系表 |
| 库存查询 | 新增领用记录视图及组织、部门、领用人组合查询 | 查询现有领用出库/退回字段；未退数量为计算值 |
| 报损出库 | 去向增加退货、匹配采购来源、跳转采购退货、附件、ID | `go_where`、采购退货来源/幂等字段及单据关系 |
| 售后记录 | 外部原始申请、多次处理进展、附件、ID | 售后主表外部来源字段＋`hspsi_sale_order_service_progress` |
| 生产出库/BOM退库 | 多次退库、当前可退数量、历次记录、附件、ID | BOM退库主从表；可退数量为实时计算 |
| 新增临时出库 | 出库去向下拉 | `destinationType`→`hspsi_production_material_out.destination_type` |

ID列只覆盖菜单进入后的顶层业务/基础资料主列表。Dashboard、汇总报表、弹窗明细、SKU行、BOM行和没有单一主键的聚合结果不在范围内。

## 17. 实施顺序

### 第一阶段：低风险用户体验

1. 新增商品自动默认SKU；
2. 临时出库去向增加“其他”；
3. 菜单主列表增加ID；
4. 批号规则确认后实现自动批号。

### 第二阶段：商品主数据调整

1. 商品前端移除组织、供应商和默认仓库；
2. 后端停止依赖商品组织、供应商和默认仓库；
3. 按组织仓库类型过滤可用分类和商品；
4. 采购申请/订单内快捷补充正式商品/SKU，并在保存/提交事务中创建；
5. 完成全模块回归后再物理删除废弃字段。

### 第三阶段：附件和售后

1. 单据主表分批增加 `attachments JSON`；

4. 扩展售后主表外部来源字段；
5. 新增售后进展明细表；
6. 接入外部售后幂等同步。

### 第四阶段：库存反向链路

1. 直接领用出库反向生成申请；

## 18. 测试计划

### 18.1 商品和分类

- 无组织、供应商和仓库可以创建商品；
- 分类没有有效仓库类型时禁止创建商品；
- 组织只能选择其仓库类型覆盖的分类和商品；
- 同类型多个仓库可以由业务单据选择；
- 商品只有一条SKU时自动默认；
- API和导入无法绕过默认SKU和分类校验；
- 单据内只补充商品、不填SKU时生成一条字段映射正确的默认规格SKU；
- 已有商品补充SKU时不破坏原默认SKU；
- 保存或提交失败时商品、SKU和采购单据全部回滚；
- 并发保存和网络重试不会重复创建正式商品/SKU。

### 18.2 附件

- 草稿可以增删；
- 审核后只能新增；
- 作废、关闭只能查看和下载；
- 并发上传不覆盖；
- 失败上传不残留正式孤儿文件；
- 每次操作写入系统日志；
- 越权用户无法访问附件。

### 18.3 售后

- 一张售后主单可以新增多条进展；
- 进展按实际时间排序；
- 外部申请重复推送不重复建主单；
- 外部进展重复推送不重复新增；
- 外部原始申请不被人工操作覆盖；
- 售后商品批次明细与进展记录相互独立。

### 18.4 领用和报损退货

- 直接领用出库只反向生成一张申请；
- OA驳回申请不改变已完成库存；
- 报损退货不直接扣库存；
- 采购退货确认只扣一次；
- 找不到采购来源时被拦截；
- 多采购来源要求明确选择。

### 18.5 临时出库去向

- 页面不再硬编码“实验出库”；
- “实验出库”和“其他”均能保存并正确回显；
- `destination_type` 使用 `temporary_outbound_destination` 映射；
- 普通生产出库不被临时出库去向影响；
- production字典值核对前不硬编码默认值。

### 18.6 BOM退库

- 一张BOM出库支持多次部分退库；
- 自动带出当前可退数量；
- 累计退库不超过原出库；
- 并发提交不能超退；
- 临时物料可以退库；
- 退库完成只入库一次；
- 作废草稿释放占用；
- 原出库单可以查看全部退库历史；
- BOM退库主表附件按统一附件权限规则工作。

## 19. 数据迁移和上线风险

### 19.1 高风险

- 商品全局化可能产生跨组织同名、同编码和数据权限问题；
- 报损和采购退货可能重复扣库存；
- 领用先出库后生成申请会产生流程状态和库存事实差异；
- BOM多次退库存在并发超退风险。

### 19.2 中风险

- 附件JSON并发更新可能覆盖；
- 外部售后重复推送可能产生重复主单或进展；
- 单据内快捷建档可能因重复判断或并发控制不足产生重复正式商品/SKU；
- 自动批号可能因重复请求或并发冲突。

### 19.3 低风险

- 默认SKU；
- 菜单主列表ID；
- 临时出库去向字典与字段；
- 领用历史查询。

## 20. 开工前确认结论

1. 自动批号固定为上海时区 `PHYYYYMMDD`，是按日批次，不要求唯一；
2. 审核中单据不允许上传或删除附件；
3. 附件文件使用环境配置接入OSS，数据库只保存附件元数据；
4. 直接领用出库对应申请被否决时，只作废申请，已生效出库继续有效，并自动生成不操作库存的草稿领用退回单；
5. 商品按标准化商品名称判重，SKU按同商品下 `spec_models` 判重；重复时禁止新建并要求改用已有档案，但系统不自动替换；
6. BOM退库不需要审批；
7. BOM退回仓库固定为原出库仓库；
8. 售后进展允许有权限人员编辑或软删除，并保留操作审计；
9. 商品废弃字段在新功能验收并由用户确认无误后再执行物理删除。

尚需在部署配置中给出但不再属于业务口径确认的问题：

- OSS具体厂商、Endpoint、Region、Bucket、访问密钥；
- 单文件大小、单据附件数量、扩展名和MIME白名单；
- OSS签名URL有效期及孤儿对象清理周期。

## 21. 验收结论

本计划最终数据库新增表严格控制为3张：

```text
hspsi_sale_order_service_progress
hspsi_production_material_return
hspsi_production_material_return_detail
```

除新增3张表外，现有表的主要结构调整包括：

- 各业务单据主表按范围增加 `attachments JSON`；
- `hspsi_production_material_out` 增加 `destination_type`；
- 采购退货主表增加自动生成来源及幂等字段；
- 售后主表增加外部来源和原始快照字段；
- 商品表停止使用并分阶段删除 `org_id/vendor_id/warehouse_id`；
- 商品表明确不增加 `is_temporary/source_type/source_id`。

其他需求优先复用现有业务表、通用单据关系、系统操作日志、现有批号字段和字典能力。所有库存链路必须通过事务、行锁和幂等键保证不会重复过账或累计超量。
