# 大型企业级进销存敏感字段权限设计说明

> 适用范围：大型企业进销存、ERP、供应链及财务协同系统
> 设计对象：金额、成本、价格、利润、结算信息及其他关键敏感字段
> 文档性质：行业可行性论证与产品设计说明
> 资料核验日期：2026-08-16

## 一、设计目的

大型企业的进销存系统通常由采购、仓储、销售、生产、财务、管理层等多个岗位共同使用。同一岗位需要参与业务，但不代表其必须看到全部财务信息。

例如，仓库管理员需要查看商品、数量、批次、仓库和出入库状态，但通常不需要查看采购金额、库存成本或销售利润；财务人员需要在同一个业务界面查看和核对金额；采购负责人可能还需要录入、修改采购价格。因此，系统需要针对同一业务数据分别控制敏感字段“是否可见”和“是否可编辑”。

### 结论先行

本方案不是个人经验式设计，也不是为当前项目临时拼出的特殊功能。其核心结构与 NIST 的 RBAC 和最小权限原则，以及 Microsoft Dynamics 365、SAP S/4HANA、Oracle Fusion Cloud ERP、金蝶云等成熟企业产品的权限模型一致：

> 先确定用户能否进入业务功能，再确定用户能访问哪些组织和业务数据，最后对同一业务对象中的敏感字段继续判断不可见、只读或可编辑。

本系统采用“组织/岗位/菜单权限 + 数据范围 + 金额字段白名单”的组合，是上述企业级模型在当前人员规模下的简化落地。授权人数较少，所以金额权限直接明确授予到人；这只改变授权载体，不改变分层授权、默认拒绝和服务端强制校验这些行业原则。

## 二、总体权限模型

企业级权限应由以下四层能力共同组成：

1. **身份与组织关系**：确定当前人员是谁、属于哪个组织、部门和岗位。
2. **菜单与操作权限**：确定人员可以进入哪些页面、使用哪些按钮。
3. **数据范围权限**：确定人员可以查看哪些组织、仓库、部门或业务单据的数据。
4. **敏感字段权限**：在前面三层均允许的基础上，进一步确定金额等关键字段是否可见、是否可编辑。

四层权限是相互叠加、彼此独立的。最终访问结果可以概括为：

> 最终权限 = 身份有效 × 页面权限 × 数据范围 × 敏感字段权限

因此，一个人即使能进入“库存查询”页面并查看本组织库存，也不代表他自动拥有查看库存成本的权限；只有同时获得金额查看授权后，金额字段才会显示真实数据。

## 三、敏感字段权限等级

敏感字段采用三级权限：

| 权限等级 | 查看敏感字段 | 录入或修改敏感字段 | 典型岗位 |
| --- | --- | --- | --- |
| 无权限 | 不可见，页面显示 `****` | 不允许 | 仓管员、普通业务人员 |
| 仅查看 | 可查看真实数据 | 不允许 | 财务复核、管理层 |
| 可编辑 | 可查看真实数据 | 允许录入和修改 | 财务负责人、采购负责人等少数授权人员 |

“可编辑”自动包含“可查看”。未进行明确配置的人员一律按“无权限”处理，不能因为其拥有管理员、组织负责人或某个岗位名称而自动获得敏感信息权限。

## 四、页面与业务设计原则

### 1. 业务页面按权限呈现字段

人员进入业务页面后，系统根据当前登录用户的敏感字段权限动态展示内容。

- 有查看权限：显示真实金额、单价、成本和合计。
- 无查看权限：字段位置保持不变，统一显示 `****`。
- 有编辑权限：金额输入控件可以使用。
- 无编辑权限：金额输入控件禁用或不显示，后端同时拒绝相关写入。

这样能够保持操作流程、业务口径和权限判断的一致性。

### 2. 金额及派生数据统一保护

权限保护不能只覆盖名称为“金额”的字段，还应覆盖所有可以直接或间接反推出财务数据的内容，包括：

- 采购单价、采购总价、应付、实付、退款和剩余应付；
- 销售单价、销售额、收款、退款和折价金额；
- 商品成本、库存成本、库存货值；
- 盘盈、盘亏、报损和报废金额；
- 毛利、利润率、成本差额等派生指标；
- 报表、导出、打印、消息、操作记录和统计图表中的金额；
- 供应商报价、结算账户等其他可被认定为关键敏感信息的数据。

### 3. 数据权限与字段权限分别判断

数据范围负责控制“能看哪一批数据”，字段权限负责控制“在这批数据里能看哪些内容”。两者不能互相替代。

例如，A 公司财务人员只能查看 A 公司数据，同时可以查看金额；A 公司仓管员同样只能查看 A 公司数据，但金额显示为 `****`；B 公司人员如果没有 A 公司数据权限，则连 A 公司的业务单据都不能看到。

## 五、安全控制要求

### 1. 默认拒绝与最小授权

- 未进入敏感字段白名单的人员默认不可查看、不可编辑。
- 查看权限和编辑权限必须由管理员人工明确授予。
- 授权人数应控制在完成业务所需的最小范围内。
- 停用、离职或删除账号的授权立即失效。

### 2. 后端是最终权限边界

前端隐藏或显示星号只能改善用户体验，不能作为真正的安全措施。系统必须在后端再次校验：

- 无查看权限时，接口不得向浏览器返回真实敏感数据。
- 无编辑权限时，即使绕过页面直接调用接口，后端也必须拒绝写入。
- 服务端计算的成本、合计和派生金额同样要执行脱敏。
- 导出、打印、消息中心和操作记录必须使用与页面一致的权限规则。

### 3. 全程审计

敏感权限的授权、变更和撤销必须记录操作人、被授权人、权限等级、授权原因和操作时间。对于高敏感场景，还可以进一步记录敏感信息查询、导出和批量打印行为。

## 六、与 OA、组织和岗位同步的关系

OA 系统可以继续作为人员、组织、部门和岗位信息的来源，进销存系统按原有接口同步这些基础身份资料。敏感字段权限属于进销存系统内部的业务安全配置，不需要修改 OA 的人员同步、组织同步、审批、消息或回调接口。

OA 岗位可以作为管理员判断是否授权的参考，但不建议仅凭岗位名称自动授予敏感权限。人员岗位发生变化时，系统可提示管理员复核，最终仍以本系统内的明确授权结果为准。

这种设计能够把“人员是谁、属于哪里”和“能否查看或修改敏感信息”清晰分开，避免 OA 组织调整意外扩大财务数据访问范围。

## 七、典型应用示例

以“库存查询”页面为例：

| 人员 | 页面权限 | 数据范围 | 敏感字段权限 | 最终效果 |
| --- | --- | --- | --- | --- |
| A 公司仓管员 | 可进入库存查询 | A 公司仓库 | 无权限 | 可看数量和批次，成本及货值显示 `****` |
| A 公司财务 | 可进入库存查询 | A 公司仓库 | 仅查看 | 可查看数量、成本和库存货值，不可修改 |
| 总部财务负责人 | 可进入库存查询 | 已授权组织 | 可编辑或仅查看 | 按授权范围查看，并在允许的业务入口维护金额 |
| B 公司普通员工 | 无 A 公司数据权限 | B 公司 | 即使有金额权限也无效 | 看不到 A 公司库存数据 |

同样的规则可以统一应用于商品资料、采购申请、采购订单、采购入库、采购退货、付款退款、库存盘点、报损报盈、销售订单、销售收退款、工作台及经营报表。

## 八、方案结论

大型企业级进销存系统应采用“角色与操作权限 + 组织数据范围 + 敏感字段权限”的分层设计。人员使用同一套菜单和业务页面，系统根据权限动态决定字段不可见、可见或可编辑，并由后端完成最终校验和数据脱敏。

这种方式可以在不改变现有业务流程和页面结构的情况下，实现岗位分工、财务保密、最小授权和全过程审计，既符合大型企业信息系统的常见设计方式，也便于后续将同一机制扩展到金额以外的其他关键敏感信息。

## 九、从源头证明方案可行

本方案不是针对当前系统临时创造的一套特殊逻辑，而是企业访问控制领域中成熟的组合设计：

> RBAC（基于角色的访问控制） + 组织/数据范围控制 + 字段级权限 + 显式人员授权 + 最小权限原则

### 1. 国际标准依据

- 美国国家标准与技术研究院（NIST）将 RBAC 定义为通过组织角色控制资源访问的安全机制。角色代表组织中的职责，用户通过角色获得完成工作所需的权限。NIST 的 RBAC 研究随后形成了 ANSI/INCITS 359 标准体系。参见 [NIST Role Based Access Control](https://csrc.nist.gov/Projects/role-based-access-control/faqs) 和 [NIST IR 6192](https://csrc.nist.gov/pubs/ir/6192/final)。
- NIST SP 800-171 的“最小权限”要求只允许用户获得完成被分配任务所必需的访问权限，并要求定期复核、重新分配或撤销权限。参见 [NIST SP 800-171 Rev.3：Least Privilege](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/800-171r3/NIST.SP.800-171r3.html)。
- 因此，“仓管员可以处理库存数量，但不能查看成本；财务人员可以查看金额；少数负责人可以编辑金额”正是按岗位职责实施最小权限，而不是异常的产品设计。

### 2. 国内制度与标准依据

- 《中华人民共和国数据安全法》第二十一条明确建立数据分类分级保护制度，并要求根据数据的重要程度以及泄露、非法获取和非法利用造成的危害采取分级保护。参见 [中国网信网：《中华人民共和国数据安全法》](https://www.cac.gov.cn/2021-06/11/c_1624994566919140.htm)。
- 国家发展改革委对数据分类分级制度的解释明确提出：应根据数据属性、重要性和敏感程度进行分类，并配置相应的安全风险控制措施。参见 [国家发展改革委：数据分类分级保护制度](https://www.ndrc.gov.cn/fggz/fzzlgh/gjfzgh/202112/t20211224_1309358.html)。
- GB/T 22239—2019《信息安全技术 网络安全等级保护基本要求》是现行国家标准，为信息系统访问控制和安全保护提供基础要求。参见 [全国标准信息公共服务平台](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=BAFB47E8874764186BDB7865E8344DAF)。
- 将采购价格、库存成本、利润和结算信息认定为企业敏感数据，并按人员职责控制查看和编辑范围，符合数据分类分级和最小必要访问的基本方向。

### 3. 国际及主流产品设计与本方案的一致性

下表不是概念类比，而是按照权限计算顺序逐项对照：

| 权限环节 | 国际标准或成熟产品惯例 | 本方案设计 | 一致性结论 |
| --- | --- | --- | --- |
| 身份与职责 | NIST RBAC 通过角色及职责组织权限 | 人员、组织、岗位继续从 OA 同步并作为基础身份 | 身份来源与应用授权分离，方向一致 |
| 功能入口 | Dynamics 365 Finance & Operations 可控制菜单、按钮、报表、服务操作和 Web 控件 | 原有菜单和按钮权限决定能否进入库存、采购等功能 | 一致，属于功能级授权 |
| 数据范围 | Oracle 通过岗位角色与业务单元、账簿、库存组织等安全上下文共同决定数据访问；SAP 通过公司代码、工厂、采购组织等限制字段控制范围 | 组织和仓库权限决定能看到哪些公司的哪些业务数据 | 一致，属于行级或组织范围授权 |
| 字段查看 | Dynamics/Dataverse 列级安全提供 `CanRead`；SAP 支持 Read 限制；金蝶提供字段查看权 | 金额查看白名单决定同一业务记录中的金额是否返回和展示 | 一致，属于字段级读取授权 |
| 字段编辑 | Dynamics/Dataverse 分别提供 `CanCreate`、`CanUpdate`；SAP 区分 Read 和 Write；金蝶区分查看权和编辑权 | 金额编辑白名单独立控制金额录入和修改，并规定编辑包含查看 | 一致，属于字段级写入授权 |
| 默认策略 | NIST/OWASP 倡导最小权限和默认拒绝；SAP 写权限默认 No Access | 未明确进入白名单的人默认不能查看、不能编辑金额 | 一致，而且采用更保守的安全默认值 |
| 技术执行点 | OWASP 要求每次请求都在可信的服务端执行授权校验；Dynamics 服务端保护表、字段和行 | 前端负责展示，后端 API 决定是否返回真实金额并拒绝越权写入 | 一致，安全边界不依赖页面隐藏 |
| 展示方式 | Dynamics 字段安全可对未授权字段显示 `********`；同一记录再叠加列级权限 | 同一库存或采购页面中，有权者看真实金额，无权者看 `****` | 一致，属于字段级动态控制 |
| 人员例外授权 | Dynamics/Dataverse 字段安全配置可关联用户或团队 | 当前只有极少数人员能接触金额，因此采用人工白名单 | 属于主流权限模型支持的显式用户授权方式 |
| 审计治理 | 企业安全实践要求授权可追溯、可复核、可撤销 | 记录授权人、被授权人、权限等级、时间和原因 | 一致，满足长期治理需要 |

由此可以看出，本方案的每一个关键结构都能在国际标准或成熟企业产品中找到对应设计。差别只在于大型平台通常同时支持“角色授权、用户授权、团队授权”等多种载体，而本系统考虑到金额授权对象只有少数人员，优先采用最容易核对、风险最小的人员白名单。

### 4. 为什么金额权限必须作为独立维度

菜单与操作权限、组织数据范围和金额字段权限解决的是三个不同问题：

- **菜单与操作权限**决定用户可以进入哪些业务功能，以及可以执行查看、新增、修改、审批或导出中的哪些动作。
- **组织数据范围**决定用户能够处理哪些组织、仓库和业务单据的数据。
- **金额字段权限**决定用户在已经有权访问的数据中，能否读取或修改金额、成本、价格、利润和结算信息。

三个维度应当独立配置、依次校验，最终权限取交集。任何一个维度未通过，都不能通过其他维度补足。例如，用户有金额查看白名单但没有 A 公司的数据权限，仍然不能看到 A 公司数据；用户能够查看 A 公司库存但没有金额白名单，只能看到业务数量等非金额信息。

Microsoft 官方安全架构将应用元素授权与表、字段、行的数据安全分开；Dataverse 在记录访问权之上继续判断受保护字段访问权；SAP 和金蝶也在功能权限之外继续配置组织范围及字段读写权限。这证明敏感字段权限作为独立维度，与已有角色和数据范围叠加，是成熟企业系统的标准设计。

本项目的正式设计结论是：

> 原有菜单和操作权限控制能否使用业务功能，组织与仓库权限控制能够处理哪些数据，金额白名单控制金额不可见、只读或可编辑；后端统一完成最终判断，前端依据授权结果呈现。

安全实现参考：[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 十、国际成熟企业产品的同类设计

### 1. Microsoft Dynamics 365 / Dataverse

Microsoft 的设计与本方案最接近，能够直接证明“同一业务数据、不同人员、字段显示不同”在成熟企业软件中是正式能力。

- Dynamics 365 Finance & Operations 官方安全架构明确规定，授权可以控制菜单、按钮、报表、服务操作、Web 控件以及客户端字段；数据安全则继续控制数据库中的表、字段和行。Table Permissions Framework 由应用服务器执行数据保护。因此，这种控制并非只存在于 CRM 或低代码平台，而是直接用于财务与供应链产品。
- Dataverse 明确区分记录级权限和字段级权限：用户必须先有权访问某条记录，字段安全配置才进一步决定他能否访问该记录中的敏感字段。这与本方案“数据范围权限和金额字段权限分别判断”完全一致。
- 字段安全配置分别提供 `CanRead`、`CanCreate`、`CanUpdate`，即读取、创建和修改可以分别授权，与“不可见、仅查看、可编辑”三级设计直接对应。
- 字段安全配置可以关联用户或团队，也支持针对特定人员单独共享字段权限，因此采用少数人员白名单属于成熟产品支持的标准授权方式。
- 官方文档说明，默认 API 行为是不返回受保护字段的真实数据；启用掩码后可以返回经过遮蔽的值。也就是说，真正安全边界在接口层，不只是前端隐藏。
- Dynamics 365 的官方字段安全示例中，普通未授权人员看到 `********`；销售经理获得只读权限，副总裁获得读取、创建和修改权限。这与当前方案的页面表现和三级权限模型高度一致。

## 十四、与原《权限与数据权限控制 Spec》的方案比较

### 1. 比较范围和基本评价

原《权限与数据权限控制 Spec》（DRAFT，2026-08-14）不是一份单纯的金额权限方案，而是一份同时改造控制权限、组织数据权限、字段权限、会话结构和审计机制的全局权限重构方案。

该方案具有较好的技术专业度，其中“三类权限解耦”、后端字段掩码、写入校验、导出打印覆盖、隐藏字段禁止排序筛选、权限审计和详细验收标准等内容是正确且值得吸收的。因此，本章不否定原方案，而是判断其中哪些设计不适合当前明确的业务边界，并说明为什么本系统最终采用人员金额白名单。

本次选型的业务事实是：系统规模稳定，真正需要查看或编辑金额的人员只有极少数；金额属于高敏感信息；授权必须由本系统人工确认；OA 只负责同步人员和组织，不负责决定金额权限；改造需要能够分模块试点并逐步推广。

### 2. 两个方案的关键差异

| 比较维度 | 原技术方案 | 当前人员金额白名单方案 | 当前选型判断 |
| --- | --- | --- | --- |
| 直接目标 | 建立通用的控制权限、组织数据权限和任意字段隐藏平台 | 解决少数人员能否查看、录入和修改金额的问题 | 当前方案更聚焦真实需求 |
| 授权对象 | 以角色配置隐藏字段 | 以本地系统人员明确授予金额权限 | 当前授权人数极少，按人更直观 |
| 默认规则 | 角色未配置隐藏字段时，字段全部可见 | 无白名单记录时，金额默认不可见、不可编辑 | 当前方案符合默认拒绝和财务敏感数据要求 |
| 权限语义 | 主要表达某个 `Model.field` 是否隐藏 | 明确表达无权限、仅查看、可编辑 | 当前方案更贴近业务语言和读写分离原则 |
| 多角色处理 | 多角色隐藏字段取并集，任一角色隐藏即可遮蔽 | 金额权限由人员唯一白名单记录决定 | 当前方案没有角色叠加冲突，结果容易解释 |
| 超级管理员 | `admin` 自动绕过字段权限 | 管理员不自动获得金额权限，也必须进入白名单 | 当前方案更符合系统管理与财务职责分离 |
| OA 与组织关系 | 同时修改授权组织、当前组织、Redis 会话和外部集成的数据范围规则 | OA 继续同步身份和组织，金额授权仅保存在进销存本地 | 当前方案不改变 OA 数据交换边界 |
| 数据库及系统改造 | 新增多张表、删除旧字段、重构会话并扩展约 600～700 个按钮权限节点 | 只新增人员金额白名单及统一金额权限服务 | 当前方案上线风险和迁移成本显著更低 |
| 技术耦合 | 权限配置直接绑定 Prisma Model、物理表名、物理字段名和 API 字段名 | 权限使用稳定的业务语义 `canViewAmount`、`canEditAmount` | 当前方案不容易因表字段或 DTO 调整失效 |
| 实施方式 | 倾向一次性全局重构 | 先选模块试点，验证后扩展到采购、库存、销售、报表等场景 | 当前方案更便于分阶段验收和回滚 |
| 长期扩展 | 可以发展成任意字段、角色、组织和动作的通用权限平台 | 优先覆盖金额、成本、价格、利润和结算类敏感信息 | 原方案通用性更强；当前规模暂不需要承担其复杂度 |

### 3. 原方案中不适合当前系统的重点设计

#### 3.1 角色黑名单和默认可见不适合金额数据

原方案规定“角色未配置任何隐藏字段等于不掩码任何字段”。这是一种黑名单逻辑：管理员必须准确找出所有不应看金额的角色、数据模型和字段并逐一配置。只要新增角色、新增金额字段或配置遗漏，真实金额就可能直接返回。

对于采购价格、库存成本、销售利润和结算金额，当前系统需要采用相反的安全默认值：只有得到明确授权的人才能查看。人员白名单把“遗漏配置”的后果从“意外泄露”变成“暂时不可见”，更符合 NIST/OWASP 最小权限和默认拒绝原则。

#### 3.2 角色隐藏不能清楚表达金额查看与编辑

原方案的核心关系是“角色—隐藏字段”，擅长表达某字段是否遮蔽，但不能像当前方案一样直接、稳定地表达“仅查看”和“可编辑”两个业务等级。金额权限需要回答的不是抽象字段是否隐藏，而是某个具体人员能不能读取真实金额、能不能提交金额变更。

当前方案使用 `can_view_amount` 和 `can_edit_amount`，并规定编辑自动包含查看，可以直接对应页面展示、输入控件、后端读取和后端写入校验，权限含义更清楚。

#### 3.3 超级管理员自动绕过不符合职责分离

原方案允许 `isSuperAdmin` 绕过字段权限。但系统技术管理员拥有账号、菜单和配置管理能力，并不当然拥有查看企业采购成本和利润的业务资格。

当前方案规定 `admin` 和 `*` 都不自动绕过金额白名单，把“系统管理权”和“财务敏感信息访问权”分开，更符合企业职责分离。

#### 3.4 将组织、会话和外部接口一起改造扩大了风险

原方案同时修改用户授权组织、`currentOrgId`、Redis 会话结构、数据范围断言和 `/integrations/*` 外部接口规则。这些内容可以作为未来独立的数据权限项目研究，但不是实现金额白名单的必要条件。

尤其是 OA 回调和系统同步通常没有普通用户的登录会话，不能简单依赖当前用户的 `currentOrgId`。将其与金额字段权限捆绑实施，会把局部需求扩大为影响登录、组织切换、OA 和业务查询的全局工程。

当前方案只使用本地用户 ID 判断金额授权，OA 同步继续维护人员、组织和岗位，双方边界不变，因此更容易验证，也不会因为 OA 岗位调整自动扩大金额访问范围。

#### 3.5 通用字段平台的实现复杂度超过当前收益

原方案要求所有响应对象携带 Model 元信息，并按 `model_name + table_name + field_name + apiField` 完成精确匹配；没有 Model 元信息的 DTO 还要进入降级匹配。这套机制具有通用性，但要求 Controller、DTO、嵌套对象、统计接口和导出接口长期遵守额外协议，遗漏一个出口就可能导致错误掩码或数据暴露。

当前方案以“金额”作为稳定业务权限，由统一服务和明确标记的金额字段执行控制，不让业务管理员直接面对数据库 Model 和物理字段。对于当前人员规模和敏感数据范围，这种实现更简单、更容易测试。

#### 3.6 权限项膨胀和长期兼容会削弱细粒度控制

原方案计划新增约 600～700 个按钮级菜单，同时通过前缀继承保证旧目录权限继续拥有全部子操作。这种设计便于平滑迁移，但旧的 `purchase` 或 `purchase:orders` 权限仍可能自动覆盖审批、作废、导出和导入，短期兼容机制如果长期保留，就会削弱新建细粒度权限的实际效果。

当前金额需求不需要生成数百个按钮节点。保留现有菜单和角色体系，在其结果之上叠加人员金额权限，可以以更小的变更获得明确的安全效果。

### 4. 原方案应当保留和吸收的内容

当前方案不是推翻原方案，而是保留其中与行业标准一致、且对金额权限真正必要的部分：

- 控制权限、数据范围和敏感字段权限作为独立维度维护；
- 无金额查看权限时，后端 API 不返回真实金额；
- 无金额编辑权限时，后端拒绝真实金额写入，不能只禁用前端输入框；
- 页面、详情、统计、导出、打印、工作台和消息等出口使用统一权限结果；
- 防止通过隐藏金额排序、筛选、聚合或派生指标推断真实数值；
- 授权、变更和撤销记录操作日志；
- 使用自动化测试验证普通用户、仅查看用户、可编辑用户、管理员和停用用户等边界。

这些内容可以直接服务于人员金额白名单，不需要同时实施组织会话重构和通用字段配置平台。

### 5. 当前方案为什么是本项目的最优选择

“最优”不是指人员白名单在任何规模、任何系统中永远优于角色或通用字段平台，而是指它在当前已确认的业务规模和风险条件下，同时取得了最好的安全性、实施效率和维护成本：

1. **安全性最高。** 默认拒绝，漏配不会泄露金额；管理员也不自动绕过。
2. **业务表达最准确。** 直接回答具体人员能否查看、能否编辑金额，不需要解释数据库表和字段。
3. **改造范围最小。** 不修改 OA 接口、组织同步、现有角色体系和菜单结构。
4. **上线效率最高。** 可以先验证一个模块，再逐步覆盖全系统，不需要等待全局权限平台重构完成。
5. **验收最简单。** 使用同一账号配置三个权限等级，即可从页面、API、写入、导出和日志验证结果。
6. **符合行业原则。** 采用独立权限维度、默认拒绝、最小授权、读写分离、服务端强制执行和审计追踪。
7. **保留未来扩展空间。** 如果人员规模或敏感字段类型明显扩大，可以在现有独立权限层上增加角色默认值、团队授权或通用敏感字段目录，而不需要推翻当前结构。

因此，本项目的方案选择不是为了否定技术复杂度，而是让技术投入与真实业务规模匹配。原方案适合作为未来全局数据权限平台的研究基础；当前人员金额白名单则是本阶段能够最快形成安全闭环、最符合行业原则、也最容易长期维护的正式方案。

## 十五、最终论证结论

从国际标准、国内法规、成熟企业软件和公开客户实践四个层面，可以得出以下结论：

1. **方案在理论上成立。** 它符合 RBAC、最小权限、数据分类分级和职责分离原则。
2. **方案在产品上成熟。** Microsoft、SAP、Oracle、金蝶都采用角色、数据范围和读写权限分层控制；Microsoft 的列级安全与本方案尤其接近。
3. **方案在技术上可实现。** 同一页面根据字段权限显示真实值或掩码，后端 API 同步执行脱敏和写入校验，已经是成熟平台的标准实现方式。
4. **方案在企业规模上可扩展。** 这些权限模型所在的平台已经用于数万员工、多业务单元、多仓库和跨地区集团的财务供应链系统。
5. **当前采用人员白名单是合理取舍。** 当能够查看或修改金额的人员只有少数且变化不频繁时，直接按人员明确授权比自动根据岗位推导更直观、更安全，也不会因为 OA 岗位变化意外扩大敏感数据访问范围。
6. **与原技术方案相比，当前选型更适合本项目。** 它吸收了后端掩码、写入校验、出口覆盖、审计和测试等正确设计，同时放弃角色黑名单默认可见、超级管理员自动绕过以及与组织/OA/会话捆绑的过度改造。
7. **金额权限应作为独立维度叠加。** 菜单与操作权限、组织数据范围和金额字段权限分别承担不同职责，独立维护并在后端取交集，符合成熟企业产品的分层授权惯例。

因此，本方案不是“不正规的特殊开发”，而是对成熟企业权限模型进行适度简化后的落地实现。真正需要关注的不是“能不能这样设计”，而是能否坚持后端强制校验、默认拒绝、导出与消息全覆盖、授权审计和定期复核。只要这些控制落实，该方案可以作为当前进销存系统长期使用的正式权限架构。
