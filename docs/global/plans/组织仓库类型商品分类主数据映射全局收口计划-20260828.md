# 组织—仓库类型—商品分类主数据映射全局收口计划

日期：2026-08-28
任务性质：主数据映射与创建单据选品逻辑收口
实施记录：[组织仓库类型商品分类主数据映射全局收口实施记录](../../daily/2026-08-28/组织仓库类型商品分类主数据映射全局收口实施记录.md)

## 一、需求结论

本次只统一“主数据可用范围”，不处理库存数量、库存批次、库存成本和库存过账。

唯一有效的商品映射链路为：

```text
用户有权操作的单据组织
→ 该组织已创建且启用的具体仓库
→ 具体仓库的 warehouse_type
→ warehouse_type 相同的启用商品分类
→ 分类下全部启用商品
→ 商品下全部启用 SKU
```

组织对商品的可用范围由“组织拥有的仓库类型”间接确定。商品表中的历史 `org_id` 不作为创建单据时的商品候选过滤条件，也不能覆盖仓库类型与商品分类的映射结果。

### 1.1 本次适用场景

- 创建销售订单；
- 创建采购申请、采购订单；
- 创建领用申请；
- 创建生产 BOM、生产计划；
- 创建通用入库及其他允许主动选择商品的入库单；
- 编辑上述尚未锁定、尚未执行的单据；
- 来源单据生成下游单据时重新校验主数据映射。

### 1.2 本次不适用场景

- 销售出库、领用出库、生产领料出库；
- 库存调拨、库存报损、库存盘点、库存调整；
- 任何必须选择实际库存批次的操作。

这些场景继续按“组织 + 具体仓库 + 实际库存 + SKU + 批次”运行，本次不得修改。

## 二、两层业务逻辑必须严格分离

### 2.1 主数据选品层

用于订单、申请和入库创建。

计算条件：

1. 用户有权访问单据所选组织；
2. 所选仓库属于该组织、已启用且未删除；
3. 仓库配置了有效 `warehouse_type`；
4. 商品分类已启用、未删除，并且分类 `warehouse_type` 等于仓库 `warehouse_type`；
5. 商品属于上述分类、已启用且未删除；
6. SKU 属于该商品、已启用且未删除。

明确禁止：

- 不查询库存表决定商品能否出现；
- 不要求商品已经存在库存记录；
- 不要求库存数量大于零；
- 不按商品历史 `org_id` 二次缩小候选范围；
- 不允许未配置仓库类型的分类或商品进入候选。

### 2.2 库存执行层

用于出库、调拨、报损等实际库存业务。

在主数据映射正确的基础上，额外校验：

- 商品和 SKU 在所选仓库中的库存记录；
- 可用库存数量；
- 批次、有效期和库存状态；
- 出库数量、已分配数量和重复过账保护。

本次不修改这一层。

## 三、需要统一的计算与交互规则

### 3.1 组织与仓库

- 单据组织为空：仓库和商品不可选择；
- 选择组织：只返回该组织下启用、未删除的具体仓库；
- 用户有额外组织权限：可以在允许代其他组织创建业务单据的场景选择额外组织；
- 个人申请类单据：组织仍锁定为登录人员所属组织，不因本计划改变；
- 切换组织：必须清空仓库、商品、SKU及依赖字段，防止旧组织选择残留。

### 3.2 仓库类型与商品分类

- 一个仓库只能使用自己的 `warehouse_type`；
- 一个仓库类型可以对应一个或多个商品分类；
- 商品候选是所有匹配分类下启用商品的并集；
- 同一组织存在多个相同类型仓库时，各仓库的主数据商品候选集合一致；
- 分类没有配置有效仓库类型时，不得出现在业务候选中；
- 分类停用或删除后，其商品不得继续用于新单据，但历史单据仍须正常回显名称。

### 3.3 商品与 SKU

- 商品必须属于匹配分类；
- 商品停用或删除后，不得用于新建和编辑新增明细；
- SKU 必须属于所选商品且已启用；
- 商品没有有效 SKU 时可以展示商品，但不得保存业务明细，并给出明确提示；
- 同一单据内是否允许同一商品不同 SKU，由现有单据规则决定；
- 当前销售订单继续禁止重复的“商品 + SKU”组合。

### 3.4 商品名称搜索

搜索只能在已经通过映射计算出的候选集合中进行，不能绕过映射搜索全库商品。

至少支持：

- 商品名称；
- 商品编码；
- 商品简称；
- 品牌名称（数据存在时）。

搜索规则：

- 去除输入首尾空格；
- 中文名称使用包含匹配；
- 英文和编码忽略大小写；
- 清空关键字后恢复全部映射候选；
- 无结果时区分“当前仓库类型没有可用商品”和“当前关键字无匹配商品”。

### 3.5 创建、编辑和来源继承

- 新建单据：按当前组织和仓库实时计算候选；
- 编辑单据：历史商品必须回显，但新增或更换商品必须执行当前映射；
- 更换仓库：清理与新仓库类型不匹配的明细，不允许静默保留；
- 来源单据生成下游单据：继承来源商品，但保存前仍校验目标组织、仓库类型和分类；
- 来源字段业务上锁定时，前端不得提供重新选择入口。

### 3.6 后端强制校验

前端过滤只负责交互，不能作为唯一约束。所有保存接口必须重新执行：

```text
组织访问权
→ 仓库属于组织
→ 仓库类型有效
→ 商品分类类型匹配
→ 商品有效
→ SKU 有效且属于商品
```

绕过前端提交不符合关系的数据时，后端必须拒绝。

## 四、当前代码问题与改造范围

### 4.1 公共主数据服务

当前公共方法已经校验仓库属于组织，也已经按仓库类型查询商品分类，但又额外使用商品 `org_id IN (0, 当前组织)` 过滤商品，导致映射结果不完整。

需要统一：

- `goodsOptions(orgId, warehouseId)`：按具体仓库类型返回分类下全部启用商品；
- `goodsOptionsByOrg(orgId)`：返回该组织所有启用仓库类型对应分类下的全部启用商品；
- `assertGoodsLines(...)`：校验组织—仓库—类型—分类—商品—SKU，不再使用商品历史 `org_id` 判断可用性；
- `assertGoodsActive(...)`：商品没有具体仓库上下文时，校验该组织是否至少拥有商品分类对应类型的启用仓库。

### 4.2 通用组织数据范围拦截

当前通用数据范围会自动给商品表追加商品 `org_id` 条件。即使业务服务删除显式条件，仍可能被自动拦截器再次过滤。

需要将商品主档从通用“按表内 org_id 隔离”的模型中分离，商品可用范围改由仓库类型和商品分类服务显式控制。同时保留：

- 单据组织的数据权限；
- 仓库组织归属校验；
- 商品管理页面按当前组织拥有的仓库类型限制分类范围；
- 商品新增、编辑时的分类仓库类型校验。

### 4.3 前端公共过滤

当前公共过滤允许 `categoryWarehouseType=0` 的商品继续显示，不符合唯一映射规则。

需要修改为：

- 已选仓库类型时，只保留完全相等的商品分类类型；
- 未配置类型的商品不进入业务候选；
- 未选仓库时是否展示商品，由具体表单交互决定；需要先选仓库的表单必须禁用商品选择。

### 4.4 业务模块

需接入统一逻辑的创建类场景：

| 模块 | 场景 | 商品来源 | 是否读取库存 |
| --- | --- | --- | --- |
| 销售 | 销售订单 | 主数据映射 | 否 |
| 销售 | 折价销售单的主动选品 | 主数据映射或锁定来源 | 否 |
| 采购 | 采购申请、采购订单 | 主数据映射 | 否 |
| 领用 | 领用申请 | 主数据映射 | 否 |
| 生产 | BOM、生产计划主动选品 | 主数据映射 | 否 |
| 库存 | 通用入库及允许主动选品的入库 | 主数据映射 | 否 |

明确不接入本次改造的库存执行场景：销售出库、领用出库、生产出库、调拨、报损、盘点、调整。

## 五、执行计划

### 阶段 0：建立基准矩阵

1. 列出所有创建类商品选择入口、接口和保存校验入口；
2. 记录每个组织拥有的启用仓库类型；
3. 计算每个组织“按正确映射应显示商品数”和“当前实际返回商品数”；
4. 固化氧源科技成品仓等已知差异场景作为回归样本。

交付：映射矩阵、差异清单、测试样本。

### 阶段 1：收口后端公共主数据能力

1. 修正公共商品候选查询；
2. 修正按组织预加载商品候选；
3. 修正保存阶段商品和 SKU 校验；
4. 处理商品主档与通用组织数据拦截的冲突；
5. 不修改库存查询、库存批次和库存过账服务。

交付：公共服务代码、单元测试、无数据库变更证明。

### 阶段 2：接入创建类业务模块

按以下顺序接入并验证：

```text
销售订单
→ 采购申请/采购订单
→ 领用申请
→ 生产 BOM/生产计划
→ 通用入库及其他主动选品入库
```

每个场景必须同时验证前端候选和后端保存，避免“能选不能存”或“不能选但接口能存”。

### 阶段 3：修正前端搜索与联动

1. 统一商品名称、编码、简称和品牌搜索；
2. 切换组织或仓库时清理失效选择；
3. 过滤未配置仓库类型的分类和商品；
4. 保留历史单据查看回显；
5. 不重新设计现有页面，不把代码写回通用大文件。

### 阶段 4：自动化与实际页面验收

1. 公共服务单元测试；
2. 各模块接口测试；
3. Web 类型检查和关键组件测试；
4. 使用实际账号在页面完成组织、仓库、名称搜索、商品选择和保存；
5. 对比改造前后的候选数量；
6. 回归库存执行场景，证明没有改变库存候选和库存过账。

## 七、停止与审核条件

出现以下情况必须暂停实施并由产品负责人审核：

1. 发现某类创建单据业务上确实要求“必须已有库存”；
2. 需要改变商品分类与仓库类型的一对多关系；
3. 现有商品缺少有效分类或 SKU，无法通过数据质量修复解决；
4. 必须修改数据库表结构或数据字典才能继续；
5. 改造导致库存执行场景候选范围或库存过账发生变化；
6. 历史单据无法正常回显。

## 八、数据库影响结论

- 数据库表结构：不修改；
- 数据字典：不修改；
- 历史业务数据：不删除、不批量改写；
- 数据迁移 SQL：不需要；
- 本次只修改查询、联动、搜索和保存校验逻辑。

## 九、完成标准

只有同时满足以下条件才算完成：

1. 所有创建类场景统一执行唯一映射；
2. 前端候选与后端保存校验一致；
3. 商品名称和编码可以在映射范围内正确搜索；
4. 零库存商品可以用于订单、申请和入库；
5. 不属于映射范围的商品无法通过接口绕过；
6. 库存执行场景没有发生行为变化；
7. 自动化测试和实际页面验收均通过；
8. 实施记录填写完整。
