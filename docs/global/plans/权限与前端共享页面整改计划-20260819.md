> 创建：2026-08-19
> 范围：权限判定 / 菜单授权 / 菜单显示 / 前端共享页面预加载
> 顺序：**先止血（解 403）→ 后治本（结构整改）**

## 0. 问题归纳（排查结论）

| # | 问题 | 根因 | 状态 |
|---|---|---|---|
| 1 | `*/options` 接口 403 | `inferRequestPermissions` 对列表映射页面 code、对下拉映射空/页面 code 不一致 | ✅ 已修 |

## 第一阶段：止血（解决跨模块下拉 403）

目标：让「通用页面」只请求当前业务真正需要的下拉，不再跨模块触达无权限接口。**不动路由/菜单/权限模型。**

### 1.1 WorkflowPage.vue（`apps/web/src/views/WorkflowPage.vue`）

**现状**：`loadOptions()`（约 L255-270）用 `Promise.all` 一次性请求 13 个接口：

```ts
/base-data/organizations/options
/base-data/warehouses/options
/base-data/departments/options
/base-data/customers/options
/base-data/users/options
/goods?pageSize=100&status=1
/production/boms?pageSize=100&status=1      ← 仅生产用
/production/plans?pageSize=100              ← 仅生产/领用「生产领料」用
/sales/money-order-options?pageSize=100     ← 仅销售用
/requisitions/application-options           ← 仅领用/销售「来源领用」用
/requisitions/output-options                ← 仅领用/生产「来源领用出库」用
/inventory/stock-options                    ← 仅库存/生产「来源库存」用
/base-data/units/options
```

**改动**：按 `key.value`（`group/resource`）拆成「公共基础下拉 + 按需下拉」两组：

- 公共（所有业务都拉）：`organizations / warehouses / departments / customers / users / goods / units`
- 按需（仅对应业务拉）：
  - `production/plans` → 仅 `production/*` 或「领用-生产领料」类型需要时
  - `production/boms` → 仅 `production/boms`
  - `sales/money-order-options` → 仅 `sales/discount-orders` 等销售类型
  - `requisitions/application-options` → 仅 `requisitions/*` 或销售「来源领用申请」
  - `requisitions/output-options` → 仅 `requisitions/outputs` 等
  - `inventory/stock-options` → 仅 `inventory/*` 或生产「来源库存」

**验证**：仓库管理员打开「领用出库单」不再触发 `/production/plans`、`/production/boms` 请求。

### 1.2 PurchasePage.vue（`apps/web/src/views/PurchasePage.vue`）

**现状**：`loadOptions()`（约 L481-505）拉 base-data + goods + `/purchase/orders`、`/purchase/receipts`、`/purchase/applications`。

**改动**：按 `resource.value` 拆：

- 公共：`organizations / departments / warehouses / vendors / goods / goods/categories / units`
- 按需：
  - `/purchase/applications` → 仅 `applications` 相关（来源领用/生产计划）
  - `/purchase/orders` → 仅 `receipts`（来源采购订单）
  - `/purchase/receipts` → 仅 `returns`（来源入库单）

**验证**：基础申请人（只有 `purchase:applications`）打开采购申请页不再请求 `/purchase/orders`、`/purchase/receipts`。

### 1.3 InventoryPage.vue / InventoryGeneralPage.vue

**InventoryPage.vue** `loadOptions()`（约 L463-473）拉 base-data + `/inventory/warehouses/tabs` + `/inventory/losses/approved-options`：

- 公共：`organizations / departments / warehouses / employees`
- 按需：
  - `/inventory/losses/approved-options` → 仅 `checks`（盘点来源）、`loss-outputs`（来源报损）需要
  - `/inventory/warehouses/tabs` → 非 `stocks` 才需要（现有逻辑已有 `resource==='stocks'` 短路，确认是否全覆盖）

**InventoryGeneralPage.vue** 已是「按需 + 公共」混合，仅需复核无跨模块请求。

### 止血完成标准

- 每个通用页面只请求「本模块 + 基础资料/商品参考数据」。
- 三个角色（基础申请人/仓库管理员/采购专员）分别打开各自有权限的页面，不再出现 403。

## 第二阶段：治本 A —— 菜单结构拍平（解决多显示/越权）

目标：消除「目录→子目录→页面」的多层目录，让菜单完全按「页面级权限」显示和放行。

### 2.1 拍平 `master-data:organizations`

**现状**（`hspsi_sys_menu`）：

```
master-data (id=1, type=1)
├── master-data:vendors / customers / warehouses / units  (type=2)
└── master-data:organizations (id=60, type=1)  ← 二级目录
    ├── master-data:companies   (id=104, type=2)
    ├── master-data:departments (id=105, type=2)
    ├── master-data:positions   (id=106, type=2)
    └── master-data:employees   (id=107, type=2)
```

**方案**（二选一，推荐 A）：

- **A. 平铺**：把 `master-data:companies/departments/positions/employees` 4 个页面的 `parent_id` 改为 `1`（直接挂到 `master-data`），删除 `master-data:organizations`（id=60）目录；`code` 保持不变，`route` 不变。
- B. 把 `master-data:organizations` 从 type=1 改为 type=2「页面组」：需评估前端树渲染是否支持。

**数据迁移**：
1. 生成迁移 SQL：更新 4 个页面的 `parent_id=1`，删除 id=60（并清理 `hspsi_sys_role_menu` 中指向 60 的授权）。
2. 校验各角色 `hspsi_sys_role_menu` 里是否残留 id=60。

### 2.2 拍平 `reports`

**现状**：`reports`（顶层）→ `reports:directory:base/purchase/production/sales/requisition/inventory/finance`（type=1 子目录）→ `reports:N:view`（type=2 页面）。

**方案**：同 2.1，把 21 个 `reports:N:view` 页面平铺到 `reports` 下，删除 7 个 `reports:directory:*` 子目录。

### 2.3 删除前端两处 hack

1. `apps/web/src/views/Layout.vue` L46-92：删除 `master-data:organizations` 手动注入 4 个页面的逻辑。
2. `apps/web/src/router.ts` L84-92：删除 `legacyOrganizationAllowed` 及其放行逻辑。

**验证**：菜单/路由完全由 `auth.menus`（页面级权限）决定；角色只勾「公司」时，只显示「公司」，不再连带显示部门/职位/员工，也无法直接访问后三个路由。

## 第三阶段：治本 B —— 通用页面按业务拆分

目标：把 3 个「一文件多业务」的大页面，改成「共享引擎 + 每业务薄壳 + 完整配置」，从根上杜绝跨模块预加载。

### 3.1 抽共享引擎组件 `BusinessDocumentPage.vue`

承载列表/分页/搜索、表单弹窗、明细表格、附件上传、提交 OA、审批/状态机、金额脱敏等骨架；暴露配置 + 插槽/回调。

### 3.2 升级 `business-config.ts` 为完整配置

每业务声明：`endpoint` / `columns` / `formFields` / `optionLoaders`（只声明本业务需要的下拉）/ `rowActions` / `save` / `transform`。

### 3.3 每业务薄壳 Vue 文件

`PurchaseApplication.vue`、`RequisitionApplication.vue`、`ProductionPlan.vue`、`ProductionBom.vue`、`SalesOrder.vue` … 每文件约几十行，只 `import` 自己的 config 并渲染 `<BusinessDocumentPage :config="xxx" />`。

### 3.4 增量迁移顺序（一次迁一个，不并行）

1. 先抽 `BusinessDocumentPage.vue` 骨架（用现有 WorkflowPage 逻辑逐步搬）。
2. 迁移 1 个业务类型 → 跑通 → 再迁下一个。
3. 覆盖顺序建议：领用申请 → 采购申请 → 生产计划 → 生产 BOM → 销售订单 → …（按影响面从小到大）。
4. 迁移完一个业务，同步删除 `WorkflowPage.vue`/`PurchasePage.vue`/`InventoryPage.vue` 中对应的分支。

## 风险与回滚

- **菜单拍平**：涉及菜单数据 + 角色授权数据，需在 `hspsi-dev`（测试库）先验证；迁移 SQL 保持可回滚（先备份 `hspsi_sys_menu` / `hspsi_sys_role_menu`）。
- **前端拆分**：大重构，采用增量迁移，每迁一个业务立即验证，避免一次性大爆炸。
- **止血改动**：纯前端 `loadOptions` 拆分，风险低，可独立回滚。
