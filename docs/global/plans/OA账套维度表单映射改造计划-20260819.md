## 1. 背景与问题

四方交叉核对结论（代码 / 落盘 JSON / 文档 / 数据库）：

1. 表单映射注册表 `apps/api/src/integrations/xinfutong-oa/form/form-mapping.constants.ts` 的 `OA_FORM_MAPPINGS` 只按 `business_type` 扁平索引，`formKey` 全部是账套1（华溯集团，`AAC15400_…`），**没有 `account_set_id` 维度**。
2. 数据库 `hspsi_sys_account_set` 现有 3 个账套全部 `status=1` 且已配置 `app_secret`、`event_public_key`：账套1=华溯集团、账套2=华溯生物科技、账套3=新华溯科技。
3. `hspsi_basic_organization` 中 org 13/14 归属账套2、org 15/16/17 归属账套3；这些组织提交 OA 时会用账套1 的 `formKey` 和 `uniqueName`，导致映射错位或 OA 报错。
4. 落盘 22 份表单配置（账套1、账套2 各 11 张）结构对比：账套2 与账套1 的控件类型、顺序、子表结构一致，仅 `formKey`（`AAC22502_…`）、`formId` 和全部 `uniqueName` 不同，另有 4 张表单存在 label 文本差异。
5. 4 张 OA 专用表（`hspsi_oa_form_template`、`hspsi_oa_form_field_mapping`、`hspsi_oa_approval_instance`、`hspsi_oa_approval_callback_log`）在数据库中**全部为空**，且代码**从未读写**前两张（表单模板/字段映射表），实际映射走硬编码常量。

## 2. 目标

1. 表单模板（`formKey`/`formId`/`formConfig`）与字段映射（`uniqueName ↔ local_field`）按 **`account_set_id` 维度**由数据库承载。
2. 代码从硬编码常量切换为 DB 驱动（带进程内缓存），提交时按单据组织的账套取对应映射。
3. 账套未配置表单（如账套3）时在提交阶段明确阻断并返回可读错误，不得静默回退到账套1 映射。
4. 不新增数据库表；不改动 `hspsi_oa_approval_instance` / `hspsi_oa_approval_callback_log` 两张运行态表的语义。

## 3. 数据库现状核对

**结论：复用现有 2 张表即可，无需新增表或字段。** 两张表已具备账套维度：

| 表 | 已有关键字段 | 用途 |
|---|---|---|
| `hspsi_oa_form_template` | `account_set_id`、`form_key`、`form_id`、`form_name`、`form_config`、`status`、`synced_at` | 缓存每个账套每个业务表单的完整配置 |
| `hspsi_oa_form_field_mapping` | `template_id`、`account_set_id`、`business_type`、`unique_name`、`local_field`、`component_type`、`field_label`、`required`、`sort_order` | 每个账套每个业务表单的字段映射 |

两张表均已有 `account_set_id` 字段，符合《OA审批对接数据库表设计.md》的原始设计；本计划是把这两张表从「空壳」真正投入使用。

- 或通过 `XinfutongOaFormService.getNewFormConfig()`（`new-form-config-query`）在实施时对每个账套重新拉取，确保与 OA 最新发布版本一致（OA 修改重新发布会产生新 `formId` 或 `uniqueName`）。

|---|---|---|---|
| 1 | 华溯集团 | 11 | 已发布，配置已落盘 |
| 2 | 华溯生物科技 | 11 | 已发布，配置已落盘 |

### 5.3 关键设计决策：FinTable 子元素的表达（已确认方案 A）

现状：`hspsi_oa_form_field_mapping` 没有「是否子元素 / 父控件」列；代码常量里的 `child` 标志当前**无任何消费点**（各业务 `*-oa-approval.service.ts` 硬编码手写 formData，只按 key 取 `uniqueName`，不读 `child`）。

决策：**采用方案 A，不改表。**

- **方案 A（已确认，不改表）**：`field_mapping` 仅存扁平映射（含 `FinTable` 子控件行，`local_field` 用代码现有 key）；`FinTable` 父子关系当前不消费，未来若要做「配置驱动通用组装」，再从 `hspsi_oa_form_template.form_config` 解析 `componentType === 'FinTable'` 的 `children`。
- 方案 B（加 `parent_unique_name` / `is_child` 列）已否决：child 当前无收益，且涉及数据库迁移，成本与风险不成比例。

## 6. 代码改造点

1. 新增映射读取服务（如 `OaFormMappingService`）：
   - `getMapping(businessType, accountSetId)`：按 `(business_type, account_set_id)` 读 `field_mapping` + 关联 `template`，重建与 `OaFormMapping` 等价的结构（含 child 标识）。
   - 进程内缓存（TTL 或账套/模板变更时失效），避免每次提交查库。
   - 账套无映射时抛「该账套未配置 OA 审批表单」。
2. 各业务 `*-oa-approval.service.ts`：`form: OA_FORM_MAPPINGS.xxx` 改为 `form: await mappingService.getMapping('xxx', accountSetId)`。
   - `accountSetId` 已由 `OaStarterContextService.resolve()` 从单据组织解析出来，无需新增解析逻辑。
3. `OaDocumentSubmissionService.submit()` 已接收 `accountSetId` 和 `form`，接口无需变，仅替换 `form` 的来源。
4. 保留 `OA_FORM_MAPPINGS` 作为「账套1 兜底 / 单元测试桩」：DB 读取失败且账套为 1 时降级到常量并记录告警；账套非 1 时**不降级**，直接报错。

## 7. 兼容、回滚与风险

- **账套3 不接入**（已确认）：本次不创建表单、不接入；账套3 组织提交时明确报错，不静默使用账套1 映射。
- **回滚**：DB 驱动异常时可切回硬编码常量（仅限账套1）；账套2 在回滚期间提交会被明确阻断，不产生错单。
- **表单配置更新时机**（已确认）：暂不做定时自动更新，先一次性填充两张表跑通 OA 审批流推送；后续需要再单独安排「重新同步表单映射」入口。
- **formId**（已确认）：不参与发起流程（`form-start` 只传 `formKey`），也不纳入映射读取结果；`form_id` 仅作为核对版本留档。

## 10. 与 out_staff_id 问题的衔接

本计划只解决「表单模板 + 字段映射的账套维度」；`FinPeopleSelect` 人员控件所需的 `out_staff_id`（OA staffId/STFSEQ）为空的根因与修复另列（见 OA 人员同步根因排查），两者独立，可并行推进。

### out_staff_id 修复的验证断言（独立于本计划，供人员控件回归复用）

- 根因：`XinfutongOaOrganizationService.getAllMembers()` 调用企业成员接口未传 `extFields`，导致返回不含 `idRelation.staffId` 与 `post`；同步 UPSERT 将 `out_staff_id`、`post_id` 恒写空。
- 修复：`getAllMembers()` 传 `extFields: ['org', 'position']`（`position` 返回 `idRelation.staffId` + `post`，`org` 返回组织详情）。
- 验证断言（2026-08-19 已执行通过，详见当日实施记录）：
  - [x] `out_staff_id` 覆盖全部启用员工（260 人），值取自各自账套的 `idRelation.staffId`。
  - [x] `post_id` 非 0（255/260 回填；其余 5 人 OA 侧 `post: null`，属正确结果）。
  - [x] **同人多账套样本**：陈素泰（三账套 `memberId` 均为 `U0000`、账套1/2 `staffId` 均为 `0000000001`）——三条 staff 记录独立，各自 `out_staff_id`/`post_id`/主组织取自对应账套，`STFSEQ` 相同属正常，未串账套。
  - [x] `resolvePerson` 按 `(user_id, account_set_id)` 经 `hspsi_sys_user_oa_staff` 定位本地 staff，再用 `(staff_id, account_set_id)` 取 `out_staff_id`；用「本地主键 + 账套」定位，不依赖 OA `staffId` 跨账套唯一。

### 三表关联完整性基线（已核对，2026-08-19）

- `hspsi_basic_staff`：未删 260 条（账套1=257 / 2=52 / 3=8）；`hspsi_sys_user_oa_staff` 313 条身份（253/52/8），孤儿身份 0、账套错配 0。
- `hspsi_basic_staff_organizations`：启用 staff 主组织(type=1) 缺失 0、多主组织 0；主组织 `outer_ref_id` 缺失 0；`org_id` 指向无效组织/部门 0。
- 主组织绝大多数为部门（org_type=2，312/318），与 `resolvePerson` 的 `org_type===2 → hspsi_basic_dept` 分支一致。
