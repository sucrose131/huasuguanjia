# 全局业务单号与采购主键改造计划

> 状态：已实施并完成自动化测试复核  
> 编制日期：2026-08-04  
> 适用项目：华溯管家（hspsi）  
> 涉及范围：API、Redis、MySQL 约束、后端单元测试与部署验收

> 实施记录（2026-08-04）：公共生成器、采购主键调整、采购/生产/销售/库存/领用编号迁移、Redis AOF 部署配置及数据库唯一索引补充均已落地；API 类型检查、生产构建及 API 全量 107 项单元测试均通过。

## 1. 改造背景

当前后端的业务单号生成方式没有统一：

- 库存、生产、销售、领用模块分别维护 `no()` 或 `documentNo()`；
- 采购模块部分单号直接使用前缀拼接数据库 ID；
- 多个模块在创建时先写入 `TMP${Date.now()}`，取得自增 ID 后再回写正式单号；
- 日期时区、编号长度和 ID 编码方式不一致；
- `hspsi_purchase_approve.pur_id`、`hspsi_purchase_order.po_id` 的部分创建路径显式写入应用层时间 ID，另一些路径仍使用数据库自增，存在混用；
- `Date.now()` 临时单号及采购时间 ID 在高并发、多实例条件下存在唯一键碰撞风险。

本次改造统一业务单号生成方式，并将采购申请、采购订单主键统一交由 MySQL `AUTO_INCREMENT` 生成。

## 2. 已确认的设计决策

### 2.1 数据库主键

- 所有正式业务记录主键使用数据库既有的 `AUTO_INCREMENT`；
- 创建采购申请时不再由应用层传入 `pur_id`；
- 创建采购订单时不再由应用层传入 `po_id`；
- 不重置现有数据库自增序列；
- 不修改历史记录的主键或业务单号；
- 主从记录仍通过 Prisma `create()` 返回的数据库自增 ID 建立关联。

`hspsi_purchase_approve.pur_id` 和 `hspsi_purchase_order.po_id` 在 Prisma Schema 中已经声明 `autoincrement()`，因此主键策略调整原则上不需要修改字段结构。

### 2.2 业务单号格式

统一格式：

```text
{业务前缀}{上海时区日期YYYYMMDD}{全局当日自增序号6位}
```

示例：

```text
PA20260804000001
PO20260804000002
GA20260804000003
```

规则：

- 日期固定使用 `Asia/Shanghai`；
- 日期格式固定为 `YYYYMMDD`；
- 当日序号固定六位，不足六位补前导 `0`；
- 不同业务前缀共用同一个当日序列，不按前缀独立计数；
- 不包含设备号；
- 不进行随机数异或或其他打乱操作；
- 全系统每日最多分配 `999999` 个业务单号；
- Redis 序号不回退，数据库事务回滚时允许出现跳号；
- 更新已有单据时不得重新生成业务单号。

同一天跨业务生成的结果示例：

```text
PA20260804000001  采购申请
PO20260804000002  采购订单
SO20260804000003  销售订单
IC20260804000004  库存盘点
```

## 3. 全局 BusinessNumberService 设计

### 3.1 文件结构

计划新增：

```text
apps/api/src/business-number/
├── business-number.module.ts
├── business-number.service.ts
├── business-number.constants.ts
└── business-number.service.spec.ts
```

职责划分：

- `business-number.module.ts`：声明并全局导出 `BusinessNumberService`；
- `business-number.service.ts`：负责日期、Redis 序列、格式化、上限检查和异常处理；
- `business-number.constants.ts`：集中维护 Redis Key、时区和业务前缀；
- `business-number.service.spec.ts`：验证格式、跨前缀统一计数、跨日、并发与异常场景。

### 3.2 Service 接口

```ts
generate(prefix: BusinessPrefix): Promise<string>
```

调用示例：

```ts
const purchaseNo = await this.businessNumber.generate(
  BUSINESS_PREFIX.PURCHASE_APPLICATION,
);
```

### 3.3 Redis Key

Redis Key 不包含业务前缀：

```text
hspsi:{environment}:business-no:{yyyyMMdd}
```

示例：

```text
hspsi:production:business-no:20260804
```

要求：

- `{environment}` 必须区分开发、测试和生产环境；
- 所有 API 实例必须连接同一个业务 Redis；
- 不允许因为 Redis 不可用而回退到 `Date.now()` 或本地内存计数；
- 生产 Redis 必须启用持久化，防止计数器因重启或数据回档从头开始。

### 3.4 原子递增

使用 Lua 脚本在 Redis 中原子执行 `INCR` 和首次过期时间设置：

```lua
local value = redis.call('INCR', KEYS[1])

if value == 1 then
  redis.call('EXPIREAT', KEYS[1], ARGV[1])
end

return value
```

过期时间使用上海时区计算，建议保留至对应业务日期结束后的第二天，避免跨时区、延迟任务或临近午夜请求导致 Key 过早消失。

### 3.5 数据库最终保护

- 所有正式业务单号字段必须保留或补充唯一索引；
- Redis 是号码分配器，数据库唯一索引是最终一致性保护；
- 创建时如遇业务单号唯一键冲突，重新申请号码并重试；
- 建议最多重试 3 次，超过次数后返回明确的服务异常并记录错误日志；
- 不得吞掉 Redis、数据库唯一约束或序号上限异常。

## 5. 采购主键改造

### 5.1 删除应用层时间 ID

删除 `PurchaseService` 中：

```ts
private id() {
  return BigInt(Date.now()) * 1000n
    + BigInt(Math.floor(Math.random() * 1000));
}
```

同时删除该方法对数据库主键和采购付款单号的所有依赖。

### 5.2 需要修改的创建路径

1. 手工创建采购申请；
2. 手工创建采购订单；
3. 采购申请审批通过后自动生成采购订单；
4. 直接采购订单开始采购时反向生成采购申请；
5. 临时采购入库时反向生成采购申请和采购订单。

调整原则：

```ts
const purNo = await this.businessNumber.generate(
  BUSINESS_PREFIX.PURCHASE_APPLICATION,
);

const application = await tx.hspsi_purchase_approve.create({
  data: {
    pur_no: purNo,
    // 不再传 pur_id
  },
});

const purId = application.pur_id;
```

采购订单采用同样方式，通过 `order.po_id` 获取数据库生成的主键。

## 7. 数据库检查与迁移

### 7.1 必须检查

- 所有正式 `*_no` 字段是否存在唯一索引；
- 所有纳入统一生成器的字段长度是否至少为 20；
- 当前最长前缀 `PRFL` 为 4 位，按统一格式生成后的最长单号为 18 位；所有目标字段统一按至少 20 位容量检查；
- 是否存在默认空字符串并可能在并发创建时触发唯一冲突的字段；
- `pur_id`、`po_id` 的数据库列是否仍保持 `AUTO_INCREMENT`；
- 生产环境当前自增计数器位置只记录、不重置。

### 7.2 迁移原则

- 只做字段长度、唯一索引等必要的增量迁移；
- 不批量重写历史单号；
- 不重置任何主键；
- 不执行 `prisma db push`；
- 在 `hspsi-dev-ai-02` 备份后按项目迁移规范执行 SQL；
- 迁移后重新执行 `prisma generate`、类型检查、测试和构建。

## 8. 测试计划

### 8.1 BusinessNumberService 单元测试

- 序号不足六位时补前导 `0`；

## 11. 最终审阅结论

### 11.1 已确认事项

1. 销售退货报废生成的报损单前缀由 `IL` 统一为 `ILD`；
2. 销售收款和销售退款属于不同业务，拆分为 `SRC`（销售收款）和 `SRF`（销售退款），不再共用 `PV`；
3. 采购退货、付款、退款任务、退款流水改用更短英文前缀：`PRT`、`PPY`、`PRF`、`PRFL`；
4. 接受数据库事务回滚造成业务单号跳号；
5. 确认全系统所有业务前缀每日共享同一个六位序号，容量上限为 `999999`；
6. 生产环境 Redis Key 的环境名使用 `production`；
7. Redis 不可用时采用“有限重试后失败关闭”，不启用任何第二号码源或本地降级方案。

生产环境 Redis Key 示例：

```text
hspsi:production:business-no:20260804
```

### 11.2 Redis 不可用时的已确认方案

采用“有限重试后失败关闭”，不采用时间戳、本地内存或数据库临时序列降级：

1. 单号生成请求遇到 Redis 短暂错误时自动重试，建议最多 3 次并使用短间隔退避；
2. 重试后仍不可用，创建业务单接口返回 `503 Service Unavailable`，并提示“业务单号服务暂不可用，请稍后重试”；
3. 只阻止需要生成新业务单号的创建或自动衍生操作；普通查询以及不生成新号码的更新操作不受影响；
4. 自动生成下游单据的事务必须整体回滚，禁止出现上游状态已变化但下游单据没有正式编号的情况；
5. 禁止降级到 `Date.now()`、随机数或进程内计数，否则 Redis 恢复后会形成两套并行序列并产生重复风险；
6. 可用性通过 Redis AOF、健康检查、告警和生产高可用部署保障，而不是在应用中引入第二号码源。

该方案优先保证业务单号的唯一性、可审计性和全局序列一致性。Redis 持续不可用时，暂时停止所有需要生成新业务单号的创建及自动衍生操作。
