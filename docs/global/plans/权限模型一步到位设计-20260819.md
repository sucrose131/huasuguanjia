# 权限模型一步到位设计

> 创建：2026-08-19
> 状态：设计定稿，待实施
> 目标：项目未上线前，一次性把「权限语义」定对，消除「引用数据被当成页面管理」导致的一系列 403 / 多显示 / 越权问题

---

## 1. 背景与问题归纳

排查过程中发现的权限体系问题，归结为**同一个根因**：当前权限模型把「引用某单据的数据」错误地等同于「拥有那个单据的页面」。

| # | 现象 | 直接原因 | 根因 |
|---|---|---|---|
| 1 | `*/options` 接口 403 | 列表映射页面 code、下拉映射空/页面 code 不一致 | 接口分类不清晰 |
| 2 | 角色授权漏目录 code | `roleMenuIds` 只补一级父目录 | 多层目录结构 + 授权逻辑不完善 |
| 3 | 菜单「多显示/越权」 | `master-data:organizations` 二级目录 + 前端 hack | 菜单结构与页面级权限不匹配 |
| 4 | 跨模块下拉 403 | 通用页面 `loadOptions` 全量预加载 | 前端通用页面未按需加载 |
| 5 | 引用数据 403 | 生产出库选「生产计划」→ 需 `production:plans` 页面 | **引用被绑定到页面权限** |

其中 #1、#2 已修复，#3、#4 已定位并部分修复，#5 是本次设计的核心。

---

## 2. 权限模型设计：四个正交维度

权限拆成**四个正交维度**，互不绑定：

| 维度 | 控制什么 | 权限 code 形态 | 举例 |
|---|---|---|---|
| **页面**（菜单入口） | 侧边栏是否显示、能否打开该页面 | `<module>:<resource>` | `production:plans` |
| **操作**（页面内按钮） | 新增/编辑/删除/提交/审批/确认等 | `<page>:<action>` | `production:plans:create` |
| **引用/读取**（模块级，隐式） | 能否在**别的表单**里下拉选该单据 | 拥有 `<module>` 下任一页面即自动获得 | 有 `production:outputs` 即可引用生产计划 |
| **数据范围**（已存在） | 只能访问授权组织/仓库的数据 | org scope | `hspsi_sys_user_authorized_org` |

**核心规则**：

1. **「引用」不占用「页面」权限**。拥有 `production:outputs` 的角色，就能在生产出库里下拉选「生产计划」，但侧边栏**不显示**「生产计划」入口，也不能打开 `/production/plans` 页面、不能增删改计划。
2. **引用数据不敏感**：来源下拉只返回「编号 + 名称」等摘要字段，且已受数据范围（组织）隔离，不需要页面级门槛。
3. **菜单显示 / 路由守卫只认「页面」权限**，不再认「目录 code」或任何 hack。

## 3. 接口分类规范

后端接口按「读写 + 用途」分类，权限判定规则统一（**最终落地采用「读=模块级、写=页面+操作级」**）：

| 分类 | 用途 | 权限判定 |
|---|---|---|
| **读取接口**（GET 列表/详情） | 打开页面、表单里引用另一张单据 | **模块目录 code**（拥有该模块下任一页面即通过） |
| **写接口**（POST/PATCH/DELETE） | 新增/编辑/删除/提交/审批等 | **页面 + 操作 code**（`inferRequestPermissions`） |
| **下拉选项接口**（`*-options`） | 静态下拉（组织/仓库/字典等） | 模块目录 code 或其下任一页面（已实现） |

**关键改变**：原来前端把「页面列表接口」直接当「来源下拉」用（如 `/production/plans`、`/purchase/orders`、`/goods/properties`），而这些接口的 **GET 读取被映射成页面 code**，导致「有出库页但没有计划页」的角色引用失败。现在把 **GET 读取统一按模块目录 code 判定**，引用数据不再占用页面权限；「页面入口是否显示」完全由前端菜单/路由控制（只认页面 code）。

> 说明：最初设计里考虑过「为每个被引用实体新增专用 source 接口」，实际落地改为「GET 读取 = 模块级」这一更简单的规则，效果一致且改动更小。金额等敏感字段仍由金额白名单（`amount-access`）在读取时脱敏，不因模块级读取而泄露。

### 3.1 权限判定实现

复用已实现的 `PermissionGuard` + `inferRequestPermissions`：

- **GET 列表/详情** → `inferRequestPermissions` 返回 `[模块目录 code]`（本阶段已改），拥有该目录 code 即通过。
- **GET 导出** → `[模块目录 code, 页面code:export]`，导出仍要求页面级操作权限。
- **写操作** → `[页面code, 页面code:action]`，页面 + 操作权限。
- **下拉选项接口** → 返回 `[]`，回退到装饰器的模块目录 code；`PermissionGuard` 对空映射接口按「目录 code 或其下任一子权限」判定（已实现）。

## 4. 菜单结构规范

1. **菜单只允许「目录(type=1) → 页面(type=2) → 操作(type=3)」三层，禁止「目录套目录」。**
2. 拍平现有两个「二级目录」：
   - `master-data:organizations`（组织子目录）→ 4 个页面（公司/部门/职位/员工）直接挂到 `master-data` 下，删除子目录。
   - `reports:directory:*`（7 个子目录）→ 21 个 `reports:N:view` 页面直接挂到 `reports` 下，删除子目录。
3. 删除前端两处 hack：
   - `Layout.vue` 里 `master-data:organizations` 手动注入 4 个页面的逻辑。
   - `router.ts` 里 `legacyOrganizationAllowed` 越权放行逻辑。
4. 角色配置只配「页面 + 操作」；目录 code 由后端 `roleMenuIds` 逐级补齐（已实现），「引用」能力自动随模块获得。

## 6. 数据迁移步骤（菜单拍平）

> 在 `hspsi-dev` 先验证，SQL 保持可回滚（先备份 `hspsi_sys_menu`、`hspsi_sys_role_menu`）。

```sql
-- 1. 拍平 master-data:organizations：4 个页面挂到 master-data(id=1)，删除子目录(60)
UPDATE hspsi_sys_menu SET parent_id = 1
WHERE parent_id = 60 AND type = 2;   -- companies/departments/positions/employees
DELETE FROM hspsi_sys_role_menu WHERE menu_id = 60;
DELETE FROM hspsi_sys_menu WHERE id = 60;

-- 2. 拍平 reports:directory:*：21 个页面挂到 reports(id=71)，删除 7 个子目录
--    （先确认 71 是 reports 顶层目录 id，子目录 id 为 109~115）
UPDATE hspsi_sys_menu SET parent_id = 71
WHERE parent_id IN (109,110,111,112,113,114,115) AND type = 2;
DELETE FROM hspsi_sys_role_menu WHERE menu_id IN (109,110,111,112,113,114,115);
DELETE FROM hspsi_sys_menu WHERE id IN (109,110,111,112,113,114,115);
```

> 注意：具体 id 以实际 `hspsi_sys_menu` 数据为准，执行前先 `SELECT` 核对。

## 9. 风险与回滚

- **菜单拍平**：涉及菜单数据 + 角色授权，先备份表再迁移，SQL 可回滚。
- **GET 读取模块级**：扩大了模块内「读」的范围，但金额等敏感字段仍由金额白名单脱敏；页面入口仍由前端菜单/路由按页面 code 控制，不越权展示。
- **通用页面拆分**：大重构，增量迁移，每迁一个业务立即验证。
