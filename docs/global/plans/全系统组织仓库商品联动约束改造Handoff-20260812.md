## 一、任务目标

在不建设账号数据权限的前提下，为全系统所有涉及组织、仓库和商品的业务单据建立统一、强制的映射约束。

无论当前登录账号是不是超级管理员，只要用户在某张单据中选中了组织，就必须按照该单据所选组织进行业务范围限制，不得根据登录账号所属组织判断。

统一业务链路如下：

```text
单据选择组织
  → 只能选择该组织下已启用、未删除的仓库
  → 选择仓库并读取仓库 warehouse_type
  → 只能选择商品分类 warehouse_type 与仓库一致的启用商品
  → SKU 必须属于所选商品
  → 保存时由后端再次强制校验全部关系
```

本次改造的最终标准不是“界面看起来过滤了”，而是同时满足：

1. 前端不展示不符合条件的仓库和商品；
2. 前端在组织或仓库变化时清理已经失效的选择；
3. 后端拒绝任何绕过前端提交的错误组织、仓库、商品关系；
4. 来源单据生成下游单据时仍需重新校验映射关系。

## 二、已确认的业务边界

### 2.1 本次必须完成

- 单据选择组织后，仓库仅限该组织范围；
- 单据选择仓库后，商品仅限与该仓库类型匹配的分类；
- 商品对应的 SKU 必须有效并属于该商品；
- 组织变化后清空原仓库，并处理已经选择的商品、SKU、批号和库存；
- 仓库变化后重新校验已有商品明细，不能让不匹配明细继续保存；
- 所有相关保存接口增加统一后端强制校验；
- 补充核心自动化测试；
- 对历史错误数据只输出异常清单，不擅自修改。

### 2.2 本次明确不做

- 不建设账号、角色、用户组织范围等数据权限；
- 不限制超级管理员可以看到哪些组织；
- 不修改数据库表结构；
- 不新增或修改数据库字段；
- 不增加、删除或调整数据字典项；
- 不重新设计现有表单样式；
- 不处理与本任务无关的采购供应商拆单、OA审批等需求。

## 三、数据库和字典结论

现有字段足以实现本次约束，不需要数据库迁移：

- 业务单据：`org_id`、`warehouse_id`；
- 仓库：`org_id`、`warehouse_type`、`status`、`deleted_at`；
- 商品：`goods_catg_id`、`status`、`deleted_at`；
- 商品分类：`warehouse_type`、`status`、`deleted_at`；
- SKU：`good_id`、`status`、`deleted_at`；
- 部门类单据：部门的 `org_id`、`status`、`deleted_at`。

现有 `warehouse_type` 字典继续使用，不需要调整。

如果发现仓库、商品分类或历史单据配置错误，属于数据质量问题，不属于表结构或字典改造。应先生成报告，经产品负责人确认后再单独处理。

## 四、统一交互规则

### 4.1 新增和编辑单据

1. 未选择组织时：
   - 仓库选择框禁用；
   - 商品选择框禁用；
   - 提示用户先选择组织和仓库。
2. 选择组织后：
   - 只请求或展示该组织下 `status=1` 且未删除的仓库；
   - 仍未选择仓库时，商品不可选择。
3. 选择仓库后：
   - 获取仓库的 `warehouse_type`；
   - 商品列表只展示分类 `warehouse_type` 相同的启用商品；
   - SKU列表继续根据商品加载。
4. 更换组织时：
   - 清空仓库、部门等组织关联字段；
   - 清空或经确认后清空商品、SKU、批号、库存信息；
   - 不允许旧组织的数据静默残留。
5. 更换仓库时：
   - 重新校验已有商品；
   - 任何分类类型不匹配的商品都不得继续保存；
   - 依赖库存的单据同步清空批次和库存并重新加载。

### 4.2 来源单据生成的下游单据

- 组织、仓库和商品原则上从来源单据继承；
- 业务上不允许修改的字段继续锁定；
- 允许改仓库的业务，只能选择同组织且与商品分类类型一致的仓库；
- 后端不能因为数据来自上游就跳过校验。

## 五、统一 API 与后端校验建议

### 5.1 商品查询

商品选择接口应明确接收单据上下文：

- `orgId`
- `warehouseId`
- 可选 `keyword`

后端查询顺序：

1. 校验仓库存在、启用且属于 `orgId`；
2. 读取该仓库 `warehouse_type`；
3. 查询相同 `warehouse_type` 的启用商品分类；
4. 返回这些分类下的启用商品；
5. 不使用当前登录账号所属组织代替单据 `orgId`。

可复用或扩展现有实现：

- `apps/api/src/inventory/inventory-general.service.ts` 中 `productOptions()` 已具备按 `orgId + warehouseId` 过滤商品的参考实现；
- `apps/api/src/goods/goods.service.ts` 当前主要依据登录账号组织过滤，不能直接作为本次单据上下文过滤的最终逻辑。

### 5.2 公共后端校验

建议提取公共校验服务或复用库存过账校验，避免采购、生产、销售、领用分别复制不同版本。至少需要提供：

- 校验组织、仓库关系；
- 校验部门、组织关系；
- 校验商品、SKU关系；
- 校验商品分类、仓库类型关系；
- 批量校验一张单据的全部明细；
- 返回清晰、可面向用户的错误信息。

建议错误信息示例：

- `所选仓库不属于当前单据组织或仓库已停用`；
- `商品“XXX”的分类与所选仓库类型不匹配`；
- `商品“XXX”的分类未配置仓库类型`；
- `SKU不属于所选商品或已停用`。

禁止仅依赖库存确认或库存过账时才发现错误。所有可保存草稿的单据在保存草稿阶段也必须进行主数据关系校验。

- 单据仓库不属于单据组织；

- 仓库没有有效 `warehouse_type`；

审计结果应包含：模块、单号、数据库ID、组织、仓库、仓库类型、商品、分类类型、异常原因和建议处理方式。
