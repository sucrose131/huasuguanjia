## 一、优化目标

本次在不重新设计采购模块整张页面、不改变已经确认的采购主流程的前提下，统一完成以下四类优化：

1. 明确采购申请中的申请身份、OA 发起身份、成本归属和收货责任；
2. 明确采购申请提交审核前后的编辑边界；
3. 明确直接采购订单保存与开始采购之间的编辑边界；
4. 优化新增采购付款的默认金额，减少整单付款场景的重复输入。

本次需求的核心关系为：

```text
当前登录账号
├─ 申请人中文姓名
├─ 申请部门
└─ 可选择的推送 OA 组织

成本承担组织
├─ 目标仓库
└─ 收货人

采购申请草稿
└─ 提交审核后永久锁定原单

直接采购订单草稿
└─ 开始采购后锁定关键内容
```

## 二、采购申请表单优化

### 2.1 最终字段定义

| 界面字段     | 数据来源/存储                                 | 是否可编辑 | 业务含义                                   |
| ------------ | --------------------------------------------- | ---------- | ------------------------------------------ |
| 申请人       | 当前会话用户的中文姓名；单据保存 `created_by` | 否         | 当前采购申请的实际发起人                   |
| 申请部门     | 现有 `dept_id`                                | 否         | 申请人在所选 OA 组织身份下对应的部门       |
| 推送 OA 组织 | 新增 `oa_org_id`                              | 是，必填   | 本次以申请人在 OA 中的哪个组织身份发起审批 |
| 成本承担组织 | 现有 `org_id`                                 | 是，必填   | 替哪个组织提出采购需求、费用由哪个组织承担 |
| 目标仓库     | 现有 `warehouse_id`                           | 是，必填   | 成本承担组织下最终接收商品的仓库           |
| 收货人       | 新增 `receiver_id`                            | 是，必填   | 成本承担组织下负责收货及后续入库处理的人员 |
| 申请原因     | 现有 `pur_reson`                              | 是，必填   | 说明本次采购需求                           |
| 采购明细     | 现有采购申请明细表                            | 是         | 商品、SKU、单位、数量及明细备注            |
| 补充说明     | 现有 `remark`                                 | 是，非必填 | 申请原因之外的补充信息                     |

“所属组织”统一改名为“成本承担组织”；“目标部门”统一改名为“申请部门”。列表、查询条件、查看弹框和编辑弹框的字段名称必须同步，不能只修改新增弹框。

### 2.2 申请人中文姓名

- 新增采购申请时直接显示当前登录账号的中文姓名，不再显示“系统自动生成”；
- 右上角用户区域同时由手机号/登录名改为中文姓名；
- 两处共用同一个 `displayName`，避免申请人和右上角显示不一致；
- 中文姓名优先取 OA 同步员工姓名，其次取用户管理中的 `nickname`；
- 后端仍以当前会话用户 ID 写入 `created_by`，不接收前端指定申请人。

### 2.3 申请部门

- 申请部门表示申请人自己的部门，不表示成本承担组织的接收部门；
- 默认取当前账号的有效 OA 部门关系，前端只读；
- 当申请人在多个 OA 组织下对应不同部门时，选择“推送 OA 组织”后回显该组织身份对应的部门；
- 申请部门不得继续被用于限制成本承担组织的仓库和收货人；
- 后端现有“部门必须属于 `org_id`”校验需要拆分，不能把申请部门误当成成本承担组织下的部门。

### 2.4 推送 OA 组织

- 下拉选项只来自当前登录账号从 OA 同步得到的有效人员—组织关系；
- 不能直接使用本地数据权限组织，也不能因为用户具有某组织的数据查看权限就把它加入 OA 身份选项；
- 只有一个有效 OA 组织时自动选中；多个时由申请人选择；没有有效关系时禁止提交并提示先同步 OA；
- 保存草稿时持久化 `oa_org_id`，编辑和查看必须准确回显；
- 提交时后端再次验证该 OA 组织仍属于当前申请人，并验证组织所属 OA 账套已启用；
- OA 发起服务使用选定的 `oa_org_id` 解析账套、员工身份和 OA 外部组织标识，不再默认使用成本承担组织作为 OA 发起组织。

### 2.5 成本承担组织、目标仓库与收货人

- 成本承担组织的候选范围取当前账号被授权可以代为申请的组织；
- 目标仓库只显示成本承担组织下已启用、未删除且与商品分类仓库类型匹配的具体仓库；
- 收货人只显示成本承担组织下已经同步 OA 人员、已经建立启用进销存账号的员工；
- 额外数据权限不等于员工归属关系：员工只是能够查看某组织数据时，不能因此进入该组织的收货人下拉框；
- 切换成本承担组织时必须清空原目标仓库和收货人，再加载新组织的候选值；
- 保存和提交时后端再次校验仓库、收货人与成本承担组织的真实关系；
- 采购申请生成采购订单时默认继承申请单收货人，后续采购到货/入库待办继续指向该人员。

### 2.6 表单排版方案

当前两列布局在新增 OA 组织和收货人后纵向过长，申请身份、成本归属和收货信息也容易混在一起。本次确定采用“业务分区 + 桌面端三列”的布局，不改成拥挤的四列，也不重新设计整张页面。

弹框建议宽度约 `1080px`，最大宽度不超过浏览器的 `92vw`。桌面端三列、中等屏幕两列、小屏幕单列；申请原因和补充说明始终占整行。

```text
┌─────────────────────────────────────────────────────────────┐
│ 新增采购申请单                                               │
├─────────────────────────────────────────────────────────────┤
│ 申请与审批信息                                               │
│                                                             │
│ 申请人               推送 OA 组织          申请部门          │
│ 中文姓名（只读）     [请选择组织 ▼]         部门名称（只读）   │
│                                                             │
│ 成本与收货信息                                               │
│                                                             │
│ 成本承担组织         目标仓库               收货人             │
│ [选择组织 ▼]         [选择仓库 ▼]           [选择员工 ▼]       │
│                                                             │
│ 申请原因（整行）                                             │
├─────────────────────────────────────────────────────────────┤
│ 采购明细                                      [+ 添加明细]   │
│ 商品 | SKU/规格 | 单位 | 数量 | 明细备注 | 操作               │
│                                                             │
│ 补充说明（整行，非必填）                                     │
├─────────────────────────────────────────────────────────────┤
│                         [取消] [保存草稿] [提交审核]          │
└─────────────────────────────────────────────────────────────┘
```

三列字段关系按用户操作顺序排列：

```text
申请人 → 推送 OA 组织 → 申请部门
成本承担组织 → 目标仓库 → 收货人
```

组件使用约束：

- 基础字段继续使用 `el-form-item`；
- 成本承担组织使用可搜索的 `el-tree-select`；
- OA 组织、仓库和收货人使用可搜索的 `el-select`；
- 申请人、申请部门使用只读 `el-input`；
- 采购明细继续使用带边框的 `el-table`，数据较多时使用 `max-height` 固定表头；
- 商品、规格和备注启用溢出提示，删除操作列固定在右侧；
- “添加明细”放在采购明细标题右侧；
- 底部保持“取消—保存草稿—提交审核”，提交审核为主按钮。

完整操作顺序：

```text
确认申请人
→ 选择推送 OA 组织并回显申请部门
→ 选择成本承担组织
→ 选择目标仓库和收货人
→ 添加采购明细
→ 保存草稿或提交审核
```

### 2.7 冗余与权限建议

- “申请原因”保留必填；原“备注”改名为“补充说明”，避免语义重复；
- 供应商、价格、付款、运输和实际到货信息属于采购订单或入库环节，不提前放入采购申请；
- “快捷新增商品”和“补充 SKU”只对具有商品主数据维护权限的用户展示；
- 商品存在多个有效 SKU 时必须支持选择已有 SKU，不能只自动使用第一个 SKU。

## 三、采购申请编辑锁定规则

### 3.1 草稿阶段

人工新增的采购申请尚未提交审核时：

- 申请发起人可以按照新增时相同的字段范围修改；
- 可以修改 OA 组织、成本承担组织、仓库、收货人、原因、明细和补充说明；
- 可以增加、删除或替换商品明细；
- 其他人员不能替申请人修改或提交；
- 生产缺料自动生成的采购申请不适用人工草稿规则。

### 3.2 提交审核后

- 点击提交审核成功后，原申请单立即锁定；
- OA 审批中、审批通过、审批驳回、审批取消后均不得修改原单；
- 前端隐藏编辑入口并以查看模式展示；
- 后端必须拒绝任何更新请求，不能仅依赖前端按钮；
- 被驳回后如需重新发起，应复制为新的采购申请，不能恢复编辑原单。

当前后端允许已驳回申请重新编辑，与本规则不一致，实施时必须收紧。

## 四、直接采购订单保存与开始采购

### 4.1 状态边界

直接采购订单不走采购申请 OA 审核，其生效边界为“开始采购”：

```text
新增直接采购订单
→ 保存（待采购/草稿）
→ 可完整编辑
→ 开始采购
→ 订单生效并锁定关键内容
```

### 4.2 保存后、开始采购前

具有新增直接采购订单权限并处于相同组织数据范围的用户，可以按照新增时相同的业务字段范围编辑：

- 供应商、组织、部门、目标仓库、收货人；
- 到货方式、计划到货日期、运输方式、物流单号；
- 结算方式、计划付款日期、备注；
- 商品、SKU、数量、明细总价和明细备注；
- 增加、删除、替换采购明细；
- 删除尚未开始采购且没有付款、入库等下游数据的整张订单。

金额字段仍叠加金额白名单控制，没有金额编辑权限的人员不能绕过白名单修改金额。

### 4.3 开始采购后

- 隐藏编辑和删除入口；
- 后端拒绝订单更新和明细替换；
- 只能通过付款、到货、入库、退货等正式业务操作继续处理；
- 已经产生入库、付款或其他下游记录的订单不得退回草稿。

### 4.4 当前实现需要收口的内容

- 状态 `1` 已基本承担待采购/草稿作用，状态 `2` 表示采购中，可复用现有字段，无需新增状态表；
- 编辑权限目前只判断宽泛采购权限和金额白名单，需要与新增直接采购订单的操作权限及组织数据范围统一；
- 草稿保存时不应提前生成正式收货待办；
- 付款应从采购订单操作列的“付款”入口登记，草稿保存不应生成不可修改的付款记录；
- 采购申请生成的订单属于来源单据约束场景，不纳入“新增直接采购订单可完整编辑”的范围。

## 五、新增采购付款默认金额

### 5.1 交互规则

- 打开新增采购付款弹框并选择采购订单后，不再默认 `0.01` 元；
- 从未付款的订单，默认付款金额为当前有效应付总额；
- 已部分付款的订单，默认付款金额为当前剩余待付金额；
- 少数分期付款场景允许用户手动调低本次付款金额；
- 切换订单时重新读取新订单的剩余待付金额并覆盖默认值；
- 用户手动修改后，在未切换订单的情况下不得被其他界面刷新静默覆盖。

### 5.2 校验规则

- 本次付款金额必须大于 0；
- 本次付款金额不得超过订单当前剩余待付金额；
- 应付金额应采用退货、退款等调整后的有效应付口径，不能只读取原始订单总额；
- 无金额编辑白名单时不能新增或修改采购付款；
- 前端默认值只负责交互，后端保存时必须重新计算剩余待付并校验，避免并发重复付款。

该项不修改数据库表结构和数据字典，只修改付款弹框初始化、订单切换和保存校验逻辑。

## 六、数据库与接口方案

### 6.1 数据库表结构

采购申请表 `hspsi_purchase_approve` 计划增加：

| 字段          | 类型建议                     | 含义                           |
| ------------- | ---------------------------- | ------------------------------ |
| `oa_org_id`   | 与组织主键一致的整数类型     | 本次采购申请选定的 OA 发起组织 |
| `receiver_id` | 与系统用户主键一致的整数类型 | 本次采购申请指定的收货人       |

现有字段语义调整：

- `org_id`：由“所属组织”明确为“成本承担组织”；
- `dept_id`：由“目标部门”明确为“申请部门”；
- `created_by`：继续表示申请人账号，不新增申请人字段。

不新增数据表，不新增运行时数据字典分类。数据库字段字典和字段注释需要同步更新，不能把业务语义写死在前端。

### 6.2 接口调整

计划新增或调整以下接口能力：

1. 登录会话返回统一中文姓名 `displayName`；
2. 采购申请返回当前申请人的有效 OA 组织及对应部门选项；
3. 采购申请收货人选项按成本承担组织过滤；
4. 采购申请创建、编辑、详情接口映射 `oaOrgId` 和 `receiverId`；
5. 采购申请提交接口重新校验申请人、OA 组织、成本组织、仓库和收货人；
6. OA 发起服务按 `oa_org_id` 解析 OA 账套与发起身份；
7. 采购订单生成时继承采购申请收货人；
8. 采购付款订单选项返回可信的当前剩余待付金额。

## 七、实施顺序与审核点

### 阶段 0：方案审核（已完成）

- 审核本方案字段定义、联动关系、编辑边界和验收用例；
- 审核通过前不修改业务代码和数据库。

**审核点 A：产品负责人已确认本方案及实施记录格式，并要求开始实施。**

### 阶段 1：数据库和接口契约

- 增加采购申请 `oa_org_id`、`receiver_id`；
- 更新 Prisma 模型、数据库补丁和字段字典；
- 先完成接口字段映射，不接入最终业务动作。

**审核点 B：确认数据库字段、接口返回和前端字段能够一一映射。**

### 阶段 2：采购申请界面

- 完成申请人、申请部门、OA 组织、成本承担组织、仓库、收货人展示和联动；
- 同步列表、查询、查看和编辑字段名称；
- 保持现有 Element Plus 风格，采用已确认的桌面端三列响应式布局。

**审核点 C：产品负责人在浏览器审核三列分区布局、字段顺序、下拉范围和回显；此时不触发 OA。**

### 阶段 3：采购申请业务逻辑

- 接入保存、提交、OA 身份和收货人校验；
- 提交后前后端双重锁定；
- 接入订单继承和收货待办链路。

### 阶段 4：直接采购订单编辑边界

- 收口保存、编辑、开始采购和删除权限；
- 移除草稿阶段过早产生的付款和正式收货待办；
- 保持金额白名单独立生效。

### 阶段 5：采购付款默认金额

- 默认带出有效剩余待付；
- 完成订单切换、手动调整和后端防超付校验。

### 阶段 6：测试和验收

- 单元测试、接口测试、类型检查和构建；
- 使用单组织、多 OA 组织、额外数据组织和金额白名单账号进行浏览器测试；
- 将每一步修改、测试和结论写入实施记录。

| PA-10 | 篡改 OA 组织或收货人提交           | 后端拒绝                                     |
| PO-01 | 保存直接采购订单                   | 订单处于待采购，可完整编辑                   |
| PO-02 | 编辑直接采购订单明细               | 可增删商品并修改仓库、数量和金额             |
| PO-03 | 开始采购后尝试编辑                 | 前端无入口，接口拒绝                         |
| PO-04 | 草稿保存                           | 不产生正式付款记录和收货待办                 |
| PP-01 | 未付款订单新增付款                 | 默认金额等于有效应付总额                     |
| PP-02 | 部分付款订单新增付款               | 默认金额等于剩余待付                         |
| PP-03 | 分期付款                           | 可以手动调低，保存成功                       |
| PP-04 | 付款超过剩余待付                   | 前端提示，绕过前端时后端拒绝                 |

## 九、代码结构约束

- 不重新设计采购申请、采购订单和采购付款整张页面；
- 不把新增逻辑重新写回通用大文件；
- 优先复用现有采购表单、组织树、远程下拉、金额权限和业务单据组件；
- 需要新增组件时应保持职责单一，并在实施记录中说明建立原因和调用关系；
- 前端过滤与后端校验必须成对实现；
- 不修改与本方案无关的库存过账、采购入库、退货和 OA 回调逻辑。

## 十、完成标准

只有同时满足以下条件才算完成：

1. 两个新增数据库字段、接口字段和界面字段准确映射；
2. 申请身份、OA 身份、成本组织和收货责任不再混用；
3. 采购申请提交后原单不可修改；
4. 直接采购订单开始采购前可完整编辑，开始采购后锁定；
5. 采购付款默认金额符合整单付款和分期付款两种场景；
6. 金额白名单、角色操作权限和组织数据权限继续叠加生效；
7. 自动化测试和浏览器实际操作均通过；
8. 实施记录逐项填写完整，并记录最终 Git 提交号。
