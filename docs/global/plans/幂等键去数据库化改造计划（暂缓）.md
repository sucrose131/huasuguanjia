# 幂等键去数据库化改造计划（暂缓）

> 状态：待办，暂不实施
>
> 编制日期：2026-08-07
>
> 目标：在不降低库存与资金业务防重能力的前提下，评估并分阶段减少数据库中的字符串幂等键，使用固定状态机、来源单据行锁和同一数据库事务实现重复请求保护。

## 1. 当前结论

本改造不能通过直接删除 `request_key`、`generation_key` 和 `posting_key` 完成。

必须先保证：

```text
锁定业务单据
→ 检查合法状态
→ 锁定库存行
→ 写库存余额和流水
→ 更新单据状态
→ 同一事务提交
```

没有来源单据可锁定且“创建即过账”的接口，必须先改成“创建草稿—按数据库ID确认过账”两步流程，否则网络重试仍可能生成两张单据并重复操作库存。

## 2. 当前影响范围

### 2.1 `posting_key`

- 位于库存流水表 `hspsi_inventory_total_detail`；
- 当前由统一库存过账服务写入并通过唯一索引防重；
- 涉及约28个库存过账调用；
- 覆盖采购、销售、领用、生产、BOM退库、调拨、调整、报损、报盈和通用出入库等业务。

### 2.2 `generation_key`

- 领用出库自动生成及反向申请链路；
- 报损退货自动生成采购退货链路；
- 当前同时承担防重复生成和识别自动来源的作用。

### 2.3 `request_key`

- 通用出入库；
- BOM退库；
- 采购退款；
- 销售收款、退款；
- 直接领用出库等由前端提交UUID的流程。

## 3. 改造原则

1. 不以按钮禁用、前端防抖或Redis锁作为唯一保障；
2. 库存余额、库存流水和单据状态必须在同一个MySQL事务中提交；
3. 所有确认、撤销和冲正操作必须锁定业务主表记录；
4. 已完成单据不得直接改回草稿；
5. 纠错必须生成独立冲正动作或反向业务单据；
6. 自动生成单据必须先锁定来源单据，再查询并创建唯一的下游单据；
7. 字段停止使用并完成生产验证前，不执行物理删除；
8. Redis只能作为短时间重复请求拦截层，不承担最终一致性责任。

## 4. 分阶段待办

### 阶段一：库存状态机与事务审计

- [ ] 建立全部库存过账入口清单；
- [ ] 核对每个入口的主单状态、允许来源状态和完成状态；
- [ ] 核对每个入口是否在修改库存前锁定业务主单；
- [ ] 核对库存余额、批次库存、库存流水和主单状态是否处于同一事务；
- [ ] 核对重复确认时是否直接返回且不重复过账；
- [ ] 核对撤销、冲正是否使用独立状态和过账版本；
- [ ] 为缺少保护的入口补充行锁、条件状态更新和并发测试。

### 阶段二：创建即过账流程拆分

- [ ] 通用入库改为“创建草稿—确认入库”；
- [ ] 通用直接出库改为“创建草稿—确认出库”；
- [ ] 评估采购退款和销售收退款是否需要相同的两步流程；
- [ ] 创建接口只返回数据库主键ID，不直接产生库存或资金事实；
- [ ] 确认接口按主键锁定主单并执行唯一一次业务操作；
- [ ] 前端在首次创建成功后保存数据库ID，网络重试改为按ID查询或确认。

### 阶段三：自动生成单据去 `generation_key`

- [ ] 为每条自动生成链路明确来源单据类型、来源ID和业务关系；
- [ ] 锁定来源单据后查询是否已有有效下游单据；
- [ ] 在同一事务内创建下游单据和业务链路记录；
- [ ] 不再通过解析字符串前缀判断是否自动生成；
- [ ] 使用明确的 `auto_created`、来源类型和来源ID字段表达业务来源；
- [ ] 补充重复OA回调、重复任务执行和并发生成测试。

### 阶段四：停用应用层幂等键

- [ ] 统一库存过账服务不再要求 `idempotencyKey` 参数；
- [ ] 调整约28处库存过账调用；
- [ ] 普通表单不再由前端生成UUID；
- [ ] 后端停止写入新的 `request_key`、`generation_key` 和 `posting_key`；
- [ ] 保留现有字段和历史数据，进入观察期；
- [ ] 增加重复提交、并发确认、超时重试和服务异常恢复测试。

### 阶段五：生产观察与物理清理

- [ ] 统计观察期内重复单据、重复库存流水和状态不一致情况；
- [ ] 对库存余额与库存流水执行完整对账；
- [ ] 对自动生成单据与来源关系执行完整性检查；
- [ ] 经业务验收后删除无用唯一索引；
- [ ] 最后删除不再使用的字符串幂等字段；
- [ ] 更新Prisma模型、迁移脚本、接口文档和用户操作指引。

## 6. 数据库调整方向

观察期结束并确认新机制稳定后，再单独编写清理迁移，候选范围包括：

```text
hspsi_inventory_total_detail.posting_key
hspsi_inventory_general_order.request_key
hspsi_production_material_return.request_key
hspsi_purchase_refund.request_key
hspsi_sales_order_payment.request_key
hspsi_draw_approve_output.generation_key
hspsi_purchase_order_input_exit.generation_key
```

清理脚本不得加入当前 `20260804`、`20260807` 功能迁移中，必须作为独立版本发布。

## 7. 验收标准

- [ ] 同一单据连续点击确认不会重复操作库存；
- [ ] 两个并发请求只有一个可以完成状态迁移；
- [ ] 数据库事务中途失败时，库存、流水和单据状态全部回滚；
- [ ] 请求超时后重试不会生成第二张已生效单据；
- [ ] 重复OA回调不会生成重复下游单据；
- [ ] 已完成单据不能通过改回草稿再次执行；
- [ ] 冲正和再次业务操作有明确、可审计的独立记录；
- [ ] 移除幂等字段前后库存对账结果一致；
- [ ] 全量自动化测试、真实数据库验收和并发压力测试通过。

## 8. 风险等级

整体风险：高。

主要风险：

- 创建即过账接口在网络重试时重复生成单据；
- 少数旧业务入口缺少主单行锁；
- 自动生成来源识别依赖现有字符串前缀；
- 撤销或状态回退后可能允许再次过账；
- Redis锁过期或服务崩溃造成跨系统状态不一致；
- 过早删除历史字段会降低异常追溯能力。

因此，本计划必须在当前功能完成上线验收后单独排期实施。
