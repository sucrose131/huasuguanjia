## 1. 背景与目标

当前代码存在两条并行开发线：

1. `feature/20260809-requirements-delivery` 包含 `codex/0807-new-require` 的完整内容，并在其上追加了 7 个采购修复、验收和文档提交；
2. `feature/sync` 基于 `dev` 继续开发，包含薪福通 OA 重构、OA 表单和审批接口、华溯之家商品同步及文件上传接口。

本次目标是在不直接污染 `dev` 的前提下建立独立整合分支，完整保留两条开发线的有效能力，解决公共入口、数据库模型、环境配置和依赖文件冲突，完成全量验证后再决定是否合入 `dev`。

本次是代码整合，不新增业务需求，不直接修改生产数据库，不提前切换现有审批业务。

## 3. 本次整合范围

### 3.1 必须纳入

- `feature/sync` 的薪福通 OA 最新目录结构、配置、组织同步、表单、审批、回调和上传能力；
- `feature/sync` 的华溯之家商品同步能力；
- `feature/20260809-requirements-delivery` 中已完成的商品、采购、库存、附件、售后、领用、BOM 退库、列表 ID 和文档改造；
- 当前未跟踪的 `database/migrations/20260809_complete_column_comments.sql`；
- 两边新增依赖、Prisma 模型和环境变量示例。

### 3.2 明确不在本次范围

- 不将生产环境或开发环境审批模式直接切换到 OA；
- 不把 OA 回调自动接入全部业务单据库存过账；
- 不重新设计统一审批状态机；
- 不执行生产数据库迁移；
- 不修改真实 OA、华溯之家或 OSS 密钥；
- 不在未经确认的情况下推送远程或直接合入 `dev`；
- 不借合并之机顺带重构无关业务代码。

## 4. 审批业务边界

本次整合必须保持以下规则：

1. 当前业务单据继续使用现有审批机制；
2. 审批通过后直接执行现有库存处理的规则保持不变；
3. `feature/sync` 的 OA 能力作为外部集成基础设施和接口保留；
4. 不在本次合并中新增“提交单据即自动发送 OA”的监听接线；
5. 不因 OA 模块存在而改变业务单据当前状态值、按钮权限或库存过账时机；
6. 后续统一审批与 OA 双模式切换继续按照全局专项计划实施，并通过 `.env` 明确启用；
7. 未配置 OA 参数时，应用应可以正常启动，现有本地审批不受影响。

## 8. Prisma 与数据库专项核对

Prisma 冲突不能只以任一分支为准，必须逐项对照当前数据库导出和迁移脚本：

1. 保留 OA/外部系统相关模型、映射、索引和字段；
2. 保留全业务附件字段；
3. 保留售后进展、BOM 退库、领用退回库位和库存扩展字段；
4. `hspsi_inventory_general_order.attachments` 必须保留；
5. `hspsi_inventory_general_order_detail.base_cost` 以数据库实际的 `decimal(12,4)` 为准；
6. 生产缺料单同时保留附件字段和数据库实际存在的单号唯一约束；
7. BigInt 主键继续通过 API 字符串化，不因合并改变类型；
8. 检查新增迁移文件命名、顺序和重复执行风险；
9. 字段注释迁移只修改 COMMENT，不改变数据、索引和业务类型；
10. 未经再次确认，不向生产数据库执行任何迁移。

## 12. 回退方案

1. `dev` 在整合验证完成前不产生任何变化；
2. 整合失败时停止在 `feature/20260810-requirements-sync`，源分支保持不变；
3. 不使用 `git reset --hard` 或覆盖源分支；
4. 已形成的冲突解决按小粒度提交保存，必要时可逐提交回退；
5. 未执行数据库迁移时，代码回退不涉及数据库恢复；
6. 测试库若执行迁移，执行前保存结构与数据备份，并按迁移影响单独制定回退 SQL；
7. 最终合入 `dev` 后如发现问题，优先使用反向提交，不改写共享分支历史。
