# 统一审批与 OA 双模式改造计划

> 状态：方案方向已确认；采购退货、销售订单和生产缺料口径已冻结；待实施
>
> 编制日期：2026-08-05
>
> 默认上线模式：`internal`
>
> 关联计划：`docs/plan/OA审批对接专项计划（暂缓）.md`
>
> 最新业务口径：保留现有“审批通过后直接操作库存”的行为，本计划与旧计划冲突时以本计划为准

## 1. 改造背景

当前采购、库存、生产、销售和领用模块分别维护自己的提交、通过、驳回、审批字段和审批后业务逻辑，主要存在以下问题：

- 审批状态和业务状态没有统一模型；
- 草稿和待审批大量共用 `approve_status = 0`，工作台无法只靠审批状态准确识别待办；
- 审批接口只校验采购、库存、生产、销售、领用等模块级权限，没有独立审批权限；
- 没有统一审批实例和完整审批历史；
- 审批驳回后的恢复规则不一致；
- 部分审批通过会直接操作库存，部分只生成下游草稿；
- 采购退货必须进入审批，旧的直接完成路径需要移除；
- 未来接入 OA 时，如果逐个业务复制推送、回调和重试代码，会形成第二套审批逻辑。

本计划在保留现有内部审批能力的前提下，建设一套统一审批框架，并通过环境配置决定新提交的审批实例走本系统内部审批、OA 审批或影子联调模式。

## 2. 建设目标

### 2.1 核心目标

1. 所有需要审批的业务统一通过 `ApprovalService` 提交和完成审批；
2. 内部审批和 OA 审批只作为两种审批结果来源，不复制审批后业务逻辑；
3. 默认保持现有内部审批，OA 未就绪时不影响系统上线；
4. 支持全局配置和按业务类型逐步切换；
5. 审批渠道在单据提交时固化，切换配置不改变处理中实例；
6. 使用事务 Outbox 保证 OA 推送事件不丢失；
7. 使用回调 Inbox 保证重复回调不重复处理；
8. 明确区分审批状态、业务办理状态和库存过账状态；
9. 工作台统一从审批实例生成准确待办；
10. 保留完整审批版本、动作、推送、回调和异常处理记录。

### 2.2 非目标

本计划不在第一阶段实施：

- 通用入库和通用出库审批；
- 单据附件及 OA 附件同步；
- 借用调拨；
- OA 产品本身的流程设计和审批人规则配置；
- 完整工作流设计器；
- 任意多级内部审批编排；
- 完整固定资产管理。

通用入库和通用出库继续按已确认规则直接过账，不进入统一审批实例。

## 3. 总体原则

### 3.1 一套审批领域，两种正式渠道

系统只建设一套：

- 审批实例；
- 审批状态机；
- 审批历史；
- 审批权限；
- 审批结果事件；
- 审批后业务处理器。

审批结果可以来自：

- `internal`：本系统审批人点击通过或驳回；
- `oa`：OA 回调通过或拒绝。

### 3.2 审批渠道按实例固化

环境配置只决定“新提交”使用哪个渠道。审批实例创建后必须保存：

```text
provider = internal / oa
mode_snapshot = internal / oa / shadow
```

已有审批实例始终按保存的渠道继续处理，不因修改 `.env` 或服务重启而改变。

驳回后重新提交应创建新的审批版本，新版本按重新提交时的配置选择渠道。

### 3.3 不自动降级

OA 推送失败时：

- 审批实例进入推送失败状态；
- 系统按规则自动重试；
- 管理员可以人工重试；
- 不得自动改为内部审批；
- 不得同时开放内部通过和 OA 回调。

确需从 OA 迁移到内部审批时，必须使用专门的管理员迁移操作，填写原因并保留审计日志。

### 3.4 渠道切换不改变审批通过后的业务效果

当前阶段保留现有审批通过后的业务行为。统一审批只替换审批结果来源，不改变审批通过后是否生成下游单据或直接操作库存。

例如：

- 库存调拨审批通过后继续完成调出、调入双边库存过账；
- 库存调整审批通过后继续直接调整库存；
- 报损选择直接报废时继续直接扣减库存；
- 报亏出库审批通过后继续直接扣减盘亏库存；
- 报盈入库审批通过后继续直接增加盘盈库存；
- 采购退货如果最终保留审批路径，审批通过后继续扣减库存并生成退款任务。

内部审批和 OA 审批必须调用相同的业务结果处理器，产生相同结果。

OA 回调接口本身只负责验签、去重并可靠记录审批结果，然后由结果任务执行现有库存操作。这里的异步拆分是技术可靠性设计，不代表增加人工出入库环节。审批结果处理成功后，业务和库存效果应与当前内部审批同步处理一致。

## 4. 模式和环境配置

### 4.1 全局配置

```env
APPROVAL_MODE=internal
```

允许值：

| 值         | 正式审批来源 | OA 行为                             | 适用阶段           |
| ---------- | ------------ | ----------------------------------- | ------------------ |
| `internal` | 本系统       | 不推送                              | 第一阶段和应急回退 |
| `oa`       | OA           | 正式推送并接收结果                  | 正式接入           |
| `shadow`   | 本系统       | 同时推送测试流程，OA 结果不驱动业务 | 联调和观察期       |

生产环境缺少 `APPROVAL_MODE` 时默认使用 `internal`，并记录启动告警。

### 4.2 按业务覆盖

为支持逐项上线，增加：

```env
APPROVAL_PROVIDER_OVERRIDES=purchase_application:oa,requisition_application:oa
```

解析优先级：

```text
业务类型覆盖配置
→ APPROVAL_MODE
→ internal
```

覆盖值同样只允许 `internal`、`oa`、`shadow`。存在未知业务类型、重复定义或非法值时，生产环境启动失败，不允许静默忽略。

### 4.3 OA 配置

```env
APPROVAL_OA_BASE_URL=
APPROVAL_OA_APP_ID=
APPROVAL_OA_APP_SECRET=
APPROVAL_OA_CALLBACK_SECRET=
APPROVAL_OA_TIMEOUT_MS=10000
APPROVAL_OA_MAX_RETRIES=8
APPROVAL_OUTBOX_POLL_INTERVAL_MS=3000
```

规则：

- `oa` 或 `shadow` 模式启用时，必须校验 OA 必需配置；
- 密钥只从环境变量或正式密钥系统读取，不写入数据库、日志和代码仓库；
- 测试和生产环境使用不同地址、应用标识、密钥和流程模板；
- 日志只保存必要请求摘要、响应摘要、状态码和追踪编号。

## 5. 统一状态模型

### 5.1 审批状态

```text
PENDING_PUSH   待推送OA
PUSH_FAILED   OA推送失败
IN_APPROVAL   正在审批
APPROVED      审批通过
REJECTED      审批拒绝
CANCELLED     已撤销或作废
```

内部审批实例创建后直接进入 `IN_APPROVAL`。

OA 审批实例按以下方式变化：

```text
PENDING_PUSH
→ IN_APPROVAL
→ APPROVED / REJECTED

PENDING_PUSH
→ PUSH_FAILED
→ PENDING_PUSH（重试）
```

### 5.2 审批结果处理状态

审批结果和审批后业务处理必须分开记录：

```text
NOT_REQUIRED
PENDING
PROCESSING
PROCESSED
FAILED
```

例如 OA 已通过但生成采购订单失败时：

```text
approval_status = APPROVED
result_status = FAILED
```

不得把审批状态重新改回审批中，也不得要求 OA 再次回调。

### 5.3 业务和库存状态

业务表继续维护自身办理状态；库存相关单据逐步补充统一过账状态：

```text
业务状态：草稿 / 待审批 / 待办理 / 办理中 / 已完成 / 已关闭
过账状态：未过账 / 部分过账 / 已过账 / 已冲销 / 过账失败
```

第一阶段不强制一次性重构所有历史状态字段，但统一审批代码不得再以单独的 `approve_status = 0` 判断待审批。

- `business_id`；
- `business_no`；
- `submit_version`；
- `provider`；
- `mode_snapshot`；
- `approval_status`；
- `push_status`；
- `result_status`；
- `applicant_user_id`；
- `responsible_user_id`；
- `org_id`；
- `request_key`；

### 6.3 审批动作日志 `hspsi_approval_action_log`

记录：

- 撤回、取消；
- 渠道人工迁移；
- 业务结果处理成功、失败和重试。

### 6.4 Outbox 表 `hspsi_approval_outbox`

建议字段：

- `id`；
- `event_id`，唯一；
- `event_type`；
- `aggregate_type`；
- `aggregate_id`；
- `payload_json`；
- `status`；
- `retry_count`；
- `next_retry_at`；
- `locked_at`；
- `locked_by`；
- `processed_at`；
- `last_error`；
- `created_at`。

业务提交、审批实例创建和 Outbox 事件写入必须处于同一 MySQL 事务。

Redis 可以用于唤醒和加速消费，但 MySQL Outbox 是可靠事件来源，Redis 中的事件丢失不能导致审批丢失。

### 6.5 回调 Inbox 表 `hspsi_approval_callback_inbox`

建议字段：

- `id`；
- `provider`；
- `external_event_id`，唯一；
- `external_instance_id`；
- `payload_hash`；
- `payload_json` 或脱敏摘要；
- `signature_valid`；
- `process_status`；
- `processed_at`；
- `last_error`；
- `created_at`。

重复回调必须返回成功，但不能重复变更审批状态、生成下游单据或库存过账。

### 6.6 OA 人员映射表

建议新增 `hspsi_approval_external_user_mapping`，保存：

- 本系统用户ID；
- OA 用户ID；
- OA 工号；
- OA 组织ID；
- 状态；
- 最近校验时间。

不使用姓名作为唯一匹配依据。

## 7. 服务和模块设计

### 7.1 `ApprovalService`

统一提供：

```ts
submit(input);
approveInternal(input);
rejectInternal(input);
cancel(input);
retryPush(instanceId);
receiveOaResult(input);
retryResult(instanceId);
getInstance(businessType, businessId);
listPending(query);
```

所有业务模块不再直接写审批人、审批时间和审批意见作为审批事实，只通过统一服务操作。

### 7.2 审批渠道适配器

定义统一接口：

```ts
interface ApprovalProviderAdapter {
  provider: 'internal' | 'oa';
  submit(instance: ApprovalInstance): Promise<ProviderSubmitResult>;
  cancel?(instance: ApprovalInstance): Promise<void>;
  query?(instance: ApprovalInstance): Promise<ProviderStatus>;
}
```

- `InternalApprovalAdapter`：创建内部待办，等待本系统操作；
- `OaApprovalAdapter`：将审批实例转换为 OA 请求，通过 Outbox Worker 推送；
- Shadow 模式正式实例仍为内部审批，OA 推送和回调单独标记为影子数据，不允许驱动正式结果。

### 7.3 审批结果处理器

每种业务注册处理器：

```ts
interface ApprovalResultHandler {
  businessType: string;
  onApproved(context: ApprovalContext): Promise<void>;
  onRejected(context: ApprovalContext): Promise<void>;
}
```

处理器必须满足：

- 幂等；
- 可重试；
- 能识别已经生成的下游单据；
- 不因重复事件重复库存过账；
- 失败时记录明确错误，不回滚已经确认的审批事实。

### 7.4 兼容当前同步体验

内部审批初期可以在审批事务提交后立即尝试处理审批结果，以保持“点击通过后马上看到采购订单或出库草稿”的当前体验。

同时必须保留可重试结果任务：

```text
审批结果提交
→ 创建唯一结果任务
→ 当前请求尝试立即处理
→ 失败时由后台 Worker 接管重试
```

OA 回调只负责可靠落库并尽快返回，业务结果由结果 Worker 处理，避免 OA 回调因库存或下游业务处理耗时而超时。

## 8. 统一事件

首期定义：

```text
approval.submitted
approval.push.requested
approval.push.succeeded
approval.push.failed
approval.approved
approval.rejected
approval.cancelled
approval.callback.received
approval.result.requested
approval.result.succeeded
approval.result.failed
```

事件必须包含：

- 唯一 `eventId`；
- 审批实例ID；
- 业务类型、业务ID和业务单号；
- 提交版本；
- 审批渠道；
- 发生时间；
- 必要操作者；
- 追踪ID。

事件负载不得包含 OA 密钥、登录密码或无业务需要的个人敏感信息。

## 9. 权限设计

新增独立权限：

```text
approval:view
approval:internal-approve
approval:internal-reject
approval:retry-push
approval:retry-result
approval:migrate-provider
approval:audit-log
```

规则：

- 业务模块权限决定能否查看业务单据；
- 审批权限决定能否在本系统通过或驳回；
- `provider = oa` 时，即使拥有内部审批权限也不能审批；
- 默认不允许创建人审批自己的单据；
- 如个别业务需要允许自审，必须按业务类型显式配置并记录原因；
- 人工重试、渠道迁移和查看完整原始回调只授予管理员。

## 10. 前端改造

### 10.1 统一展示

业务详情统一展示：

- 审批渠道；
- 审批状态；
- OA 推送状态；
- OA 流程编号；
- 当前审批人或审批摘要；
- 提交版本；
- 审批意见；
- 审批时间；
- 审批结果处理状态。

### 10.2 按渠道显示操作

内部审批实例：

- 有审批权限且状态为审批中时显示“通过、驳回”；
- 驳回原因前后端同时必填。

OA 审批实例：

- 隐藏内部通过、驳回；
- 显示“待推送、审批中、推送失败、已通过、已拒绝”；
- 有管理权限时显示“重试推送”；
- 提供 OA 流程编号，是否提供跳转链接取决于 OA 能力。

Shadow 模式：

- 仍显示内部审批按钮；
- OA 状态明确标记“影子联调，不影响正式审批”。

### 10.3 工作台

工作台待办改为查询统一审批实例，至少同时满足：

```text
provider = internal
approval_status = IN_APPROVAL
当前用户具有审批权限和数据范围
```

OA 审批实例不作为内部审批待办；可以在单独的“OA 审批跟踪”区域展示推送和审批状态。

## 11. 当前审批业务迁移矩阵

| 业务类型                    | 当前通过结果                 | 是否立即影响库存 | 首批OA建议 | 迁移前置工作                 |
| --------------------------- | ---------------------------- | ---------------- | ---------- | ---------------------------- |
| `purchase_application`      | 自动生成采购订单             | 否               | 是         | 提取采购订单生成处理器       |
| `purchase_return`           | 扣库存并生成退款任务         | 是               | 是         | 已确认只保留审批退货路径     |
| `inventory_transfer`        | 调出、调入双边过账           | 是               | 否         | 提取双边过账处理器并保证幂等 |
| `inventory_adjustment`      | 直接库存调整                 | 是               | 否         | 提取库存调整处理器并保证幂等 |
| `inventory_check`           | 生成报亏、报损、报盈单据     | 否               | 第二批     | 统一驳回后恢复和差异单幂等   |
| `inventory_damage`          | 报废扣库或生成折价销售单     | 视去向           | 否         | 提取处置处理器并保证幂等     |
| `inventory_shortage_output` | 一次性扣减盘亏库存           | 是               | 否         | 增加驳回恢复或重新生成机制   |
| `inventory_overflow_input`  | 直接增加盘盈库存             | 是               | 否         | 提取报盈入库处理器并保证幂等 |
| `production_plan`           | 进入生产中或转缺料采购       | 否               | 是         | 提取库存重检与状态处理器     |
| `sales_order`               | 保存后直接进入后续办理       | 否               | 否         | 已确认普通销售订单无需审批   |
| `discount_sales_order`      | 待出库或直接完成来源批次扣库 | 视来源           | 否         | 区分人工审批与来源处置确认   |
| `requisition_application`   | 自动生成领用出库草稿         | 否               | 是         | 提取出库草稿生成处理器       |

生产缺料不纳入审批实例。缺料产生时直接生成待审批采购申请，原 `/production/shortages/plan/:id/approve` 遗留入口删除，不再保留人工审核步骤。

## 13. 切换和回退规则

### 13.1 正常切换

修改 `.env` 后通过正式发布重启生效，不实现运行时热切换。

切换只影响切换后新提交的审批版本：

```text
旧 internal 实例 → 继续内部审批
旧 oa 实例       → 继续等待 OA 回调
新实例           → 使用新配置
```

### 13.2 回退到内部审批

当 OA 整体不可用时：

1. 将新提交默认模式切回 `internal`；
2. 重启服务并完成健康检查；
3. 已经推送 OA 的实例继续保持 `oa`；
4. 未推送成功的 OA 实例由管理员逐笔决定继续重试、取消后重提或迁移；
5. 禁止批量直接修改数据库中的 `provider` 和审批状态。

### 13.3 人工迁移实例

管理员迁移必须：

- 只允许尚未获得正式审批结果的实例；
- 先尝试取消原 OA 流程；
- 生成新的审批版本，不覆盖旧实例；
- 填写迁移原因；
- 记录操作人、时间、原渠道和目标渠道；
- 原 OA 后续回调只能归档，不能改变新实例。

## 14. 幂等、并发和事务要求

1. 同一业务提交版本只能创建一个审批实例；
2. 同一审批实例只能创建一个有效 OA 流程；
3. 同一 OA 回调事件只能处理一次；
4. 同一审批结果只能触发一个结果任务；
5. 下游单据使用来源审批实例或业务来源唯一约束防重；
6. 库存过账继续使用现有幂等键、数据库事务和库存行锁；
7. 审批实例状态变化使用行锁或乐观版本号；
8. 通过和驳回并发到达时，只允许第一个合法终态成功；
9. 老审批版本的回调不能覆盖新审批版本；
10. Worker 使用租约锁，进程退出后任务可以被其他实例接管。

## 17. 验收标准

### 17.1 统一审批

- 所有迁移业务都通过 `ApprovalService` 创建审批实例；
- 同一提交版本只有一个有效审批实例；
- 内部审批和 OA 审批使用相同结果处理器；
- 审批历史完整且不可被覆盖；
- 草稿不会出现在待审批工作台；
- 创建人默认不能审批自己的单据；
- 驳回原因前后端必填；
- 驳回后的恢复行为符合各业务规则。

### 17.2 双模式切换

- `internal`、`oa`、`shadow` 三种模式符合定义；
- 配置切换只影响新提交实例；
- OA 模式禁止内部通过和驳回；
- Shadow 回调不改变正式审批和业务状态；
- OA 不可用时可以安全切回内部模式接收新申请；
- 旧 OA 实例不会因回退被错误改为内部审批。

### 17.3 OA 可靠性

- 业务事务成功后 OA 推送事件不会丢失；
- 推送失败可以安全重试；
- 同一业务提交不会创建多个有效 OA 流程；
- 重复回调不会重复生成下游单据或库存过账；
- 旧版本回调不能覆盖新版本；
- 签名无效、时间戳过期和重放请求被拒绝并记录；
- 人员无法匹配时进入可追踪异常，不分配给错误用户。

### 17.4 业务和库存

- OA 通过和内部通过产生一致的业务结果；
- 审批结果处理失败不丢失审批事实；
- 库存过账失败可以追踪和补偿；
- 库存相关结果处理具备事务、行锁和幂等键；
- OA 回调不会因长时间库存操作而超时；
- 通用入库和通用出库不受统一审批改造影响。

4. OA 流程实例和回调事件唯一标识；
5. 12 类业务对应的 OA 模板；
6. OA 用户与本系统用户的稳定映射字段；
7. 内部审批是否一律禁止创建人自审；
8. 采购退货已确认只保留OA审批退货；
9. 确认调拨、调整、报损、报亏和报盈继续在审批通过后直接操作库存；
10. 库存结果任务失败后的管理员重试、人工补偿和告警责任人；
11. OA 审批意见和审批过程需要同步到何种粒度；
12. OA 是否支持撤回和取消；
13. Shadow 模式使用测试模板还是真实模板的测试分支；
14. 人工渠道迁移的授权人员和审批要求；
15. OA 附件同步继续保持暂缓，还是另行批准实施。

## 19. 推荐结论

本项目应先完成统一内部审批，再接入 OA，而不是直接在现有各业务审批方法中增加 OA 请求。

推荐正式路线：

```text
现有内部审批
→ 统一 ApprovalService（仍为 internal）
→ Outbox / Inbox 和 OA Adapter
→ Shadow 联调
→ 采购申请、采购退货、领用申请、生产计划逐项 OA
→ 高风险库存业务提取幂等结果处理器并逐项接入 OA
→ 全局 OA，内部审批保留为可控回退能力
```

这样既能保留当前系统的可用性和回退能力，也能保证内部审批与 OA 审批不会发展成两套长期不一致的业务实现。
