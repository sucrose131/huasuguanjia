# AI功能开发与交付规则

> 状态：项目级强制规则
>
> 生效日期：2026-08-09
>
> 适用范围：本项目后续所有新增功能、业务改造和会影响用户操作或业务数据的缺陷修复

## 1. 规则目标

本规则用于保证业务人员能够在开发前看懂并确认界面、字段和数据流，开发人员能够依据明确的数据库映射和 API 契约实施，后续接手人员能够通过文档和记录还原每次交付。

所有功能默认遵循以下顺序：

```text
需求和边界确认
→ 核对最新数据库结构与字典
→ 前端界面及交互设计
→ 前端字段—API—数据库映射
→ API契约与事务设计
→ 业务负责人确认
→ 前后端实现
→ 自动化验证和浏览器验收
→ 更新实施构想与实施记录表
→ 经授权后进行Git提交
```

除紧急故障处置外，不得跳过“设计、映射、确认”直接开发业务逻辑。紧急处置完成后也必须补齐文档和验证记录。

## 2. 第一阶段：确认需求和边界

开发前必须用业务语言说明：

- 用户是谁；
- 用户从哪个页面进入；
- 用户要完成什么；
- 哪些情况允许操作；
- 哪些情况必须拦截；
- 保存、提交、取消、关闭和失败分别产生什么结果；
- 哪些内容属于本次范围；
- 哪些内容明确暂缓。

存在歧义时先列出待确认项，不得用代码替业务人员作出会改变业务结果的决定。

## 3. 第二阶段：核对数据库和字典

### 3.1 先核对，后设计

必须以当前目标分支和目标数据库的最新结构为准，核对：

- 可复用的主表、明细表和关系表；
- 主键、业务单号和来源关系；
- 字段类型、长度、是否允许为空和默认值；
- 唯一索引、普通索引和软删除规则；
- 现有数据字典类别和字典项；
- 基础资料表，例如单位、组织、仓库和人员；
- 历史数据兼容性。

### 3.2 数据库变更原则

- 能使用现有表和字段完成的功能，不新增表或字段；
- 不得把数据写入含义不相符的旧字段；
- 不得为了页面显示方便随意增加数据库字段；
- 不得把技术状态、权限或配置随意塞进业务字典；
- 需要新增表、字段、索引或字典时，必须先说明原因、替代方案、影响和迁移方式，经业务负责人确认后再实施；
- 未经确认不得直接修改目标数据库结构或字典数据。

数据库结构已经明确冻结的任务，设计必须在现有结构内完成；如果发现现有结构无法保证数据正确性，应停止该部分实现并提交证据，不能强行绕过。

## 4. 第三阶段：先做前端界面和交互设计

业务逻辑开发前，应先提供可供业务负责人确认的界面方案。可以使用线框图、静态原型、现有页面上的改造设计或低成本交互稿，不要求先完成正式前端代码。

界面方案至少说明：

- 页面入口和操作路径；
- 新增、修改或删除的字段；
- 字段顺序、标签、必填项、默认值和提示语；
- 按钮出现条件及点击结果；
- 正常、加载、空数据、无权限和错误状态；
- 搜索无结果、重复数据和校验失败状态；
- 保存、提交、取消、关闭页面后的数据结果；
- 移动端或窄屏是否需要特殊处理；
- 是否复用项目现有组件和视觉风格。

设计目标是让业务负责人能够在开发前判断“用户是否会用、字段是否正确、操作是否容易出错”。

## 5. 第四阶段：建立字段映射

每个新增或变化的业务字段都必须建立可追溯映射：

| 页面字段 | 业务含义 | API字段 | 数据库表 | 数据库字段 | 字典/基础资料来源 | 必填/默认值 | 写入时机 |
| --- | --- | --- | --- | --- | --- | --- | --- |

映射规则：

- 页面展示字段必须说明数据来源；
- 页面提交字段必须说明最终存储位置；
- 计算字段必须说明计算口径，不得伪装成数据库原始字段；
- ID 必须明确对应哪张表的哪个主键；
- BigInt ID 通过 API 按字符串传输；
- 字典字段必须写明字典类别代码；
- 基础单位等非字典数据必须写明基础资料表；
- 临时页面状态必须明确标记为“不写数据库”；
- 无法找到正确数据库承载位置的字段不得进入正式开发。

## 6. 第五阶段：定义 API 和数据生命周期

实现前必须明确：

- API 路径和请求方法；
- 调用权限及组织数据范围；
- 请求字段、返回字段和错误结构；
- 分页、筛选和排序规则；
- 新增、修改、删除、提交和撤销的状态限制；
- 幂等规则和重复请求处理；
- 并发控制；
- 事务边界；
- 外部系统失败时的处理方式；
- 操作日志和审计要求。

涉及主表单内快捷创建数据时，默认遵循：

```text
快捷窗口确认
→ 仅形成当前页面临时数据
→ 主业务表单成功保存或提交
→ 在同一事务中创建基础资料、回填ID并保存业务单据
```

用户取消、关闭页面或主表单保存失败时，临时数据不得写入数据库，不得产生孤儿基础资料。

## 7. 第六阶段：业务确认门槛

正式实现业务逻辑前，至少向业务负责人提交：

1. 业务流程和范围；
2. 前端界面或交互设计；
3. 字段—API—数据库映射表；
4. API和事务方案；
5. 数据库、索引和字典是否变更；
6. 待确认项和风险。

业务负责人确认后才能进入实现。小功能可以使用简化设计稿和精简映射表，但不能省略映射和确认本身。

## 8. 第七阶段：实施原则

- 前端限制用于改善体验，后端必须执行最终权限和业务校验；
- 组织数据范围必须以后端登录身份为准，不能只信任前端传入的组织 ID；
- 所有库存增减必须明确唯一执行者，防止重复过账；
- 自动生成和外部回调必须具备幂等保护；
- 主单、明细、快捷创建资料和关系数据应按业务要求使用同一事务；
- 已完成业务原则上通过反向单据或冲正处理，不直接篡改历史；
- 保留项目现有风格和组件，避免同一能力在多个页面出现不同交互；
- 不得为了通过测试而削弱真实业务校验。

## 9. 第八阶段：验证和验收

每个功能按风险选择并记录以下验证：

- 后端单元测试；
- 前端组件或逻辑测试；
- API 类型检查；
- Web 类型检查；
- 数据库迁移验证；
- API 实际调用验证；
- 浏览器实际操作；
- 权限和跨组织访问测试；
- 重复提交、并发和事务回滚测试；
- 空数据、错误提示和取消操作测试；
- 关键数据写入后的数据库回查。

不能仅以“页面能打开”或“类型检查通过”认定业务功能完成。

## 10. 第九阶段：两份文档同步维护

每次功能开发必须同步维护：

### 10.1 实施构想

记录当前有效的业务规则、范围、界面方案、字段映射、API方案、验收标准和剩余工作。

### 10.2 实施记录表

以原始一级需求作为固定目录，在每项需求下按“下一个开发人员能够理解、验证和接手”的粒度记录交付项，不要求拆到每个接口或每个按钮。

每个交付项至少记录：

- 做了什么；
- 影响哪些主要页面、接口或数据；
- 验证结果；
- 当前状态；
- 遗留问题；
- Git 提交号。

一个任务包含多个功能时，应分别归入对应一级需求，不能只写一条“本次需求全部完成”。

## 11. 完成定义

只有同时满足以下条件，功能才能标记为“已完成”：

- 业务范围已经确认；
- 界面和交互符合确认方案；
- 所有字段都有正确映射；
- API、权限、事务和幂等规则已经实现；
- 必要数据库变更已经在目标环境执行；
- 自动化检查通过；
- 关键路径完成浏览器验收；
- 失败、取消和重复操作经过验证；
- 实施构想与实施记录表已经同步更新；
- 遗留问题已经明确记录。

不满足上述条件时，应使用“部分完成”“代码完成待验收”或“暂缓”，不能写成“已完成”。

## 12. 禁止事项

- 未确认界面和字段映射就直接实现复杂业务逻辑；
- 页面新增无法映射到数据库或明确计算口径的字段；
- 仅前端过滤数据，后端不做权限控制；
- 快捷新增窗口确认后立即写入孤立基础资料；
- 未经确认新增表、字段、字典或改变字段含义；
- 用历史对话中的中间结论覆盖最新确认口径；
- 没有测试或验收证据就标记完成；
- 只更新代码，不更新实施构想和实施记录表；
- 用过细且无法阅读的流水记录代替可交付功能记录；
- 用一条笼统记录掩盖一个任务中的多个独立交付内容。
