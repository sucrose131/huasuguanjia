# 当前需求汇总与实施构想

> 文档状态：需求汇总与方案讨论稿，尚未进入开发
>
> 编制日期：2026-08-07
>
> 本文以最近一次沟通确认的业务口径为准；如与此前计划或需求描述冲突，以本文列出的“当前理解”为准。

## 1. 文档目的

本文汇总当前提出的全部待改需求，并说明建议的业务模型、数据处理方式、实施顺序、风险和仍需确认的问题。

本阶段只形成需求与方案，不修改前后端代码、不执行数据库迁移。

## 2. 已确认的统一业务口径

### 2.1 商品、分类和仓库

- 商品分类绑定的是具体“仓库类型”，不是某一个具体仓库；
- 商品资料不应预先指定供应商、所属组织和具体仓库；
- 实际采购或发生其他业务时，再由业务单据选择组织、供应商和具体仓库；
- 业务单据所选仓库的仓库类型必须符合商品分类要求；
- 部分分类只允许部分组织使用，部分通用分类允许多个组织共同使用；
- 商品新增时自动准备一条默认 SKU，用户不需要额外点击“设为默认”。

### 2.2 库位

- 库位是用户自由填写的文字，不是标准化库位基础资料；
- 库位用于查询某个位置历史上曾经摆放过什么商品；
- 库位不作为当前库存结存维度；
- 系统不承诺计算某个自由文本库位的实时剩余库存；
- 库位输入需要提供当前操作员的个人历史推荐，仍允许输入新内容。

### 2.3 菜单主列表 ID

- 只改造每个菜单进入后看到的顶层主列表；
- 统一列顺序为“序号 → ID → 原有业务列”；
- ID 展示该列表主记录的真实数据库主键；
- 不要求给弹窗明细、SKU 行、BOM 行、展开子表、报表内部子表增加 ID。

### 2.4 库存与反向业务

- 报损去向选择“退货”时，报损单负责发起业务链，采购退货单负责唯一一次库存扣减；
- 临时采购商品需要进入正式库存；
- 库存界面的部门、领用人查询默认展示全部实际领用历史，而不是只展示当前未退结存；
- OA 驳回由直接领用出库反向生成的申请时，只作废申请，不自动恢复已经完成的库存出库。

## 3. 需求一：商品主档去除交易归属字段

### 3.1 当前理解

商品主档只回答“这是什么商品”，不提前回答“由哪个组织向哪个供应商采购并放入哪个仓库”。

商品档案保留：

- 商品名称、编码、分类；
- 基础单位、商品形态、供应方式；
- 品牌、规格、参考成本、参考售价；
- 商品属性；
- SKU 信息。

商品档案移除：

- 默认供应商；
- 所属组织；
- 默认仓库。

组织、供应商、具体仓库改为采购申请、采购订单、采购入库等具体业务单据的交易字段。

### 3.2 建议处理方式

1. 前端商品新增、编辑、查看和列表移除组织、供应商、默认仓库；
2. 后端商品保存不再接收或信任这些字段；
3. 商品选择接口改为全局商品主档，不再通过 `goods.org_id` 判断商品归属；
4. 采购、生产、销售、领用和库存模块逐一清理依赖 `goods.org_id`、`goods.vendor_id`、`goods.warehouse_id` 的逻辑；
5. 采购业务在单据层选择本次组织、供应商和仓库；
6. 库存过账继续校验具体仓库类型与商品分类仓库类型一致；
7. 删除采购入库读取商品默认仓库的兜底逻辑；
8. 数据库字段先完成引用审计，再通过独立迁移删除或停止使用。

### 3.3 分类组织范围

建议分类支持两种组织范围：

```text
global       所有组织可使用
restricted   仅指定组织可使用
```

限定范围使用“分类—组织关联表”保存。商品选择分类时，根据当前业务组织过滤可选分类。

### 3.4 风险

- 当前商品表和部分业务校验使用 `org_id`；改成全局商品主档是系统级调整，不是只隐藏表单字段；
- 同一个商品被多个组织使用后，商品编码是否全局唯一需要统一；
- 不同组织对同一商品需要不同供应商、采购价格时，应保存在供应关系或交易记录中，不能重新塞回商品主档。

## 4. 需求二：新增商品自动生成默认 SKU

### 4.1 当前理解

- 打开新增商品页面时自动生成一条 SKU 草稿行；
- 第一条 SKU 自动设置为默认 SKU；
- 自动继承商品基础单位；
- 用户填写基本资料后可以直接保存，不需要点击“设为默认”；
- 真正的 SKU 数据在保存商品时与商品一起写入数据库；
- 新增的第二条及后续 SKU 默认不是默认 SKU；
- 系统始终保证有且只有一个默认 SKU。

### 4.2 建议处理方式

- 将初始 SKU 的 `isDefault` 设置为 `1`；
- 商品基础单位变化时，同步更新尚未被用户单独修改的初始 SKU 单位；
- 只有一条 SKU 时禁止取消其默认状态；
- 删除当前默认 SKU 前要求先指定另一个默认 SKU，或者由系统自动选择剩余第一条；
- 后端继续做“有且只有一个默认 SKU”的最终校验，防止导入和 API 绕过前端。

## 5. 需求三：全业务单据统一附件

### 5.1 当前理解

- 所有业务单据统一支持多附件；
- 草稿状态可以上传和删除；
- 审核通过后可以追加附件，但不能删除历史附件；
- 作废、关闭单据只能预览和下载；
- 文件格式、大小和数量受统一配置限制；
- 查看、上传、删除分别校验单据权限；
- 所有附件操作保留审计日志。

### 5.2 建议处理方式

建设通用附件中心，而不是在每张业务表上增加附件字段：

```text
document_type + document_id + attachment_id
```

主要组成：

- 通用附件表；
- 附件操作日志表；
- 统一上传、预览、下载、删除接口；
- 单据状态适配器；
- 单据权限适配器；
- 通用前端附件面板。

附件存储与数据库元数据分离，数据库不直接保存大文件内容。

### 5.3 待确认

- 实际文件存储位置；
- 单文件大小、单据附件数量和格式白名单；
- 审核中状态是否允许新增或删除；
- 附件列配置是否按业务类型单独设置。

## 6. 需求四：自由文本库位及个人历史推荐

### 6.1 当前理解

库位是用户输入的文字，例如“A区3排上层”，用于记录商品在某次入库时被放置的位置。

查询目标是：

> 输入库位文字，查询这个位置历史上曾经摆放过哪些商品、SKU 和批次。

查询结果不是该库位当前实时余量。

### 6.2 建议处理方式

建立统一库位历史表，记录：

- 组织、仓库；
- 原始库位文字和标准化搜索文字；
- 商品、SKU、批号；
- 当次入库数量；
- 来源单据类型、ID、单号和明细 ID；
- 操作人和实际入库时间；
- 正常或已冲正状态。

只在入库实际完成时写入库位历史，不在草稿保存时写入。

### 6.3 个人历史推荐

推荐数据按以下范围隔离：

```text
当前用户＋当前组织＋当前仓库
```

排序综合考虑：

1. 文字匹配程度；
2. 最近使用时间；
3. 使用频次。

用户仍可以输入从未使用过的新库位。

### 6.4 查询结果

可以展示历史入库数量和当前仓库总库存，但必须明确：当前仓库总库存不代表该自由文本库位当前剩余数量。

## 7. 需求五：库存界面增加历史库位查询

### 7.1 当前理解

原“按库位查询实时库存”的表述调整为“按历史库位查询摆放记录”。

支持条件：

- 组织、仓库；
- 一个或多个库位关键词；
- 商品、SKU、批号；
- 入库日期；
- 操作人；
- 来源单据类型。

### 7.2 建议处理方式

建议在库存菜单增加“历史库位”视图，与“当前库存”分开：

- 当前库存：继续使用现有实时库存结存；
- 历史库位：读取统一库位历史记录。

多库位条件按“或”匹配，库位文字支持模糊查询。

## 8. 需求六：入库明细自动生成批号

### 8.1 当前理解

- 新增入库明细时自动生成一次默认批号；
- 用户可以修改；
- 保存、重新打开或编辑已有明细时不重新生成；
- 只有新增加的明细行才生成新批号；
- 最终以用户保存的批号为准；
- 导入和 API 创建也应执行相同规则。

### 8.2 建议处理方式

- 批号由后端统一生成，前端取得默认值后允许修改；
- 批号生成接口需要幂等，避免网络重试不断产生新值；
- 明细一旦有批号就不覆盖；
- 后端保存时校验批号长度和适用唯一范围；
- 采购入库、通用入库、生产入库、调拨入库、退回入库等统一调用批号服务。

### 8.3 待确认

- 批号格式；
- 批号全局唯一还是按商品/SKU/仓库范围识别；
- 复制历史入库单时是否重新生成批号。

## 9. 需求七：直接领用出库反向生成申请

### 9.1 当前理解

1. 用户可以直接创建并完成领用出库；
2. 库存立即扣减；
3. 系统反向生成领用申请；
4. 反向申请初始状态为已通过；
5. 两张单据互相关联并可跳转；
6. OA 驳回时只作废反向申请，不自动退回库存；
7. 实际退回通过领用退回单处理，可以选择不同仓库和库位；
8. 处理领用出库作废时同步处理反向申请。

### 9.2 建议的作废方案

不建议将“作废”简单实现为改状态，也不建议所有情况都自动恢复库存。

建议区分：

- 业务退回：创建领用退回单，可以部分、多次、跨允许仓库和库位退回；
- 技术冲正：管理员对刚发生的错误操作执行，生成明确反向库存流水；
- OA 驳回：只作废反向申请，已完成出库保持有效；
- 未过账草稿作废：可以直接作废并同步反向申请。

已完成出库正常情况下不允许无库存动作地直接作废。

### 9.3 待确认

是否采用上述“业务退回＋管理员冲正”组合方案。

## 10. 需求八：菜单主列表统一显示数据库 ID

### 10.1 当前理解

所有菜单进入后的顶层主列表统一为：

```text
序号 → ID → 原有业务列 → 操作
```

- ID 是该主记录真实数据库主键；
- ID 只读；
- 不修改业务单号；
- 不改造弹窗明细、SKU、BOM 明细、展开子表和其他内部表格；
- 当前没有序号列的菜单主列表先补序号，再补 ID。

### 10.2 建议处理方式

1. 建立“菜单页面—主列表—数据库主表—主键字段”审计表；
2. 所有主列表 API 统一返回字符串形式的 `id`；
3. BigInt 不转换为 JavaScript Number，避免精度丢失；
4. 建立公共 ID 列组件，统一宽度、固定位置和空值展示；
5. 对动态资源页面分别验证每个菜单资源返回的是对应主表 ID；
6. 增加静态检查或页面清单，防止遗漏菜单。

本期按最新口径只要求展示 ID，不把全系统列配置中心作为该需求的前置条件。

## 11. 需求九：报损去向“退货”并生成采购退货

### 11.1 当前理解

1. 报损出库去向增加“退货”；
2. 选择后按商品、SKU 和批号追溯采购来源；
3. 找不到来源时禁止保存；
4. 报损单生成采购退货单；
5. 报损单自身不扣减库存；
6. 采购退货确认时执行唯一一次库存扣减；
7. 两张单据互相跳转；
8. 采购退货允许人工补充和有限编辑。

### 11.2 建议处理方式

- 报损单状态增加“待采购退货、退货处理中、已退货、退货已取消”等链路状态；
- 同一批号存在多条采购来源时，由用户选择来源，不能静默取第一条；
- 采购退货可编辑物流、原因、备注、仓库和库位；
- 商品、SKU、批号不能改成与来源无关的数据；
- 退货数量不能超过报损来源数量；
- 采购退货作废后同步回退报损链路状态；
- 用唯一来源关系和库存过账键防止重复扣减。

## 12. 需求十：发货信息下的客服跟进记录

### 12.1 当前理解

- 发货主记录保持不变；
- 客服可以新增多条独立跟进记录；
- 每条记录保存内容、处理状态、操作人和时间；
- 以时间线展示完整历史；
- 新增跟进不覆盖原发货数据。

### 12.2 建议处理方式

新增发货跟进子表，并采用追加式审计记录。原则上不物理删除；如允许修改，应保留修改日志。

## 13. 需求十一：华数之家售后申请及处理历史

### 13.1 当前理解

- 外部售后申请推送后生成系统售后主单；
- 外部申请原始信息作为不可变快照保存；
- 使用外部唯一编号保证重复推送幂等；
- 每次处理中间过程保存为独立子记录；
- 所有处理记录挂在售后主单下；
- 页面展示完整处理时间线。

### 13.2 建议处理方式

第十、十一项可以共用一套通用“跟进记录”能力，但分别挂载到发货记录和售后主单，权限和状态字典可以按业务类型配置。

## 14. 需求十二：实验室临时采购进入库存

### 14.1 当前理解

- 临时采购允许直接填写商品名称；
- 临时商品需要完成入库并参与后续库存、领用和退库；
- 退库可以关联原领用单；
- BOM 领用中的临时物料剩余部分允许退库。

### 14.2 建议处理方式

库存必须依赖稳定的商品和 SKU 身份，因此不建议仅在库存表保存自由文本名称。

建议后台自动创建：

- 临时商品档案；
- 默认 SKU；
- 临时商品标识；
- 专用临时物料分类；
- 内部商品编码；
- 确定的基础单位。

临时商品默认不进入普通商品选择范围，可以通过专门筛选查看。后续如转为正式商品，应走归档或合并流程，不能删除已经产生库存流水的商品。

### 14.3 待确认

- 同名临时商品是否自动复用，还是每次采购都新建；
- 临时商品使用什么默认基础单位；
- 谁拥有将临时商品转为正式商品的权限。

## 15. 需求十三：BOM 整单出库支持多次退库

### 15.1 当前理解

- BOM 整单出库增加退库入口；
- 每次打开自动带出当前可退剩余数量；
- 支持部分退库和多次退库；
- 累计完成退库数量不能超过原出库数量；
- 退库单关联原 BOM 出库单；
- 原单可以查看历次退库记录；
- 临时补料或临时物料也纳入可退范围。

### 15.2 建议处理方式

```text
当前可退数量 = 原出库数量 - 已完成退库数量 - 处理中占用数量
```

- 保存时使用数据库事务和行锁重新校验；
- 作废的退库释放占用和可退数量；
- 退库实际完成时执行入库过账；
- 每张退库单保存来源出库单和来源明细；
- 禁止通过并发请求累计超退。

## 16. 需求十四：临时出库去向增加“其他”

### 16.1 当前理解

- 新增临时出库去向字典；
- 保留“实验出库”；
- 新增“其他”；
- 只影响临时出库，不影响销售、领用、报损等其他出库类型；
- 历史数据无需迁移。

这是相对独立、风险较低的字典和表单调整。

## 17. 需求十五：库存界面增加组织、部门和领用人查询

### 17.1 当前理解

- 默认展示全部已经实际发生的领用历史；
- 支持组织、部门、领用人多条件组合过滤；
- 以实际领用出库和领用退回为数量依据；
- 申请单只用于流程追溯，不作为实际领用数量；
- 不默认限定为当前未退结存。

### 17.2 建议处理方式

库存菜单建议拆成两个独立视图：

- 当前库存：展示仓库实时库存；
- 领用记录：展示全部领用历史和退回情况。

领用记录展示：

- 组织、部门、领用人；
- 商品、SKU、批号；
- 领用数量、已退数量、未退数量；
- 出库仓库和历史库位；
- 领用时间；
- 领用申请、出库单和退回单跳转。

后续可以增加“全部、尚未退清、已全部退回”范围筛选，但默认仍为全部历史。

## 18. 建议实施阶段

### 阶段一：低风险体验调整

1. 新增商品自动生成默认 SKU；
2. 临时出库去向增加“其他”；
3. 菜单主列表统一增加 ID；
4. 入库批号生成规则确认后实现自动批号。

### 阶段二：商品主数据模型调整

1. 商品改为全局主档；
2. 移除商品组织、供应商和默认仓库；
3. 增加分类组织适用范围；
4. 清理所有业务模块对商品组织和默认仓库的依赖；
5. 回归采购、生产、销售、领用和库存仓库类型校验。

### 阶段三：通用基础能力

1. 统一附件中心；
2. 统一库位历史记录；
3. 个人库位输入推荐；
4. 历史库位查询；
5. 发货与售后共用的跟进记录能力。

### 阶段四：反向单据和库存闭环

1. 直接领用出库反向生成申请；
2. 领用退回和技术冲正；
3. 报损退货生成采购退货；
4. BOM 多次退库；
5. 临时采购商品自动建档并入库。

### 阶段五：查询与外部集成

1. 库存菜单增加领用历史视图；
2. 组织、部门、领用人组合查询；
3. 华数之家售后推送和幂等；
4. OA 驳回反向申请状态处理；
5. 后续统一审批系统接入。

## 19. 实施原则

### 19.1 库存只能影响一次

任何反向生成的业务单据都必须明确唯一的库存执行者，禁止来源单和生成单重复增减库存。

### 19.2 单据不物理删除业务历史

已经完成库存、付款、退款或外部推送的单据，原则上通过作废、冲正和反向单据处理，不物理删除业务历史。

### 19.3 前后端双重校验

商品分类、仓库类型、默认 SKU、可退数量、附件权限等规则必须由后端最终校验，前端限制只用于改善操作体验。

### 19.4 所有自动生成必须幂等

自动批号、反向申请、采购退货、BOM 退库、临时商品和外部售后主单都必须设置业务唯一键，防止重复请求产生重复数据。

### 19.5 数据迁移独立审阅

删除商品组织、供应商、仓库字段，以及增加分类组织范围、附件表、库位历史表、跟进表、来源关联字段等数据库调整，应形成独立迁移文件和回滚说明，执行前再次审阅。

## 20. 开工前仍需确认的问题

1. 分类组织范围是否需要系统强制执行，还是暂时只通过实际使用区分；
2. 商品改为全局主档后，商品编码是否要求全局唯一；
3. 已完成领用出库是否采用“业务退回＋管理员技术冲正”的组合方案；
4. 自动批号的最终格式和唯一范围；
5. 同一批号存在多个采购来源时，是否由用户选择来源；
6. 同名临时商品复用规则和默认基础单位；
7. 附件存储、大小、数量、格式和审核中权限；
8. 商品表原组织、供应商、仓库字段是直接物理删除，还是先停止使用、完成数据观察后再删除。

## 21. 总体建议

不建议将全部需求一次性同时开发。商品全局化、库位历史、附件中心和反向库存链路都会影响多个模块，应该按阶段实施，每个阶段完成数据库迁移审阅、单元测试、接口测试、前端类型检查、生产构建和核心业务回归后，再进入下一阶段。

第一阶段可以优先解决用户当前最直接的操作障碍；第二阶段先统一商品主数据口径；第三阶段建立可复用的通用能力；第四阶段再实现高风险库存反向链路。
