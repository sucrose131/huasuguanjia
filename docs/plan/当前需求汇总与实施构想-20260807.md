## 1. 文档用途和维护规则

本文用于说明当前十五项需求及后续新增集成范围的最终业务口径、实施状态和后续工作。此前讨论稿、历史对话或旧计划与本文冲突时，以本文和配套实施记录表中的最新确认结论为准。

从本次更新开始，每次需求开发必须同时维护两份文档：

1. 本文：更新当前要做什么、业务规则、范围和验收标准；
2. 实施记录表：追加记录实际做了什么、修改范围、验证结果、完成日期和遗留问题。

不能只修改代码而不更新记录表，也不能只在记录表中写“已完成”而不保留验证依据。

所有需求必须先完成界面设计、字段—API—数据库映射和业务确认，再进入正式逻辑开发；具体流程遵守项目级《AI功能开发与交付规则》。

## 3. 已确认的统一业务规则

### 3.1 商品、分类、组织和仓库

- 商品是全局主档，不直接绑定所属组织、默认供应商或具体仓库；
- 商品分类必须关联一个仓库类型；
- 分类不直接绑定组织，不建立“分类—组织”关联表；
- 普通组织账号可见的分类和商品，由该组织拥有的启用仓库类型动态推导；
- 组织新增某种类型的启用仓库后，应自动获得该仓库类型对应分类及商品的可见范围；
- 组织停用或删除某类最后一个仓库后，应失去该仓库类型对应分类及商品的业务可选范围；
- 业务单据选择的仓库必须属于当前组织，且仓库类型必须与商品分类要求一致；
- 商品基础资料的可见性过滤和业务保存时的后端校验必须同时存在，不能只依赖前端隐藏。

已确认超级管理员默认查看全部商品和分类；普通账号使用自身登录组织范围。本轮不新增跨组织切换器。

### 3.2 快捷创建商品

- 系统不存在“临时商品”业务类型；
- 单据内快捷创建的商品保存后就是正式商品；
- “商品是否已经存在”必须按全局商品主档判断，不能只查询当前组织可见范围；
- “商品是否允许当前账号使用”按登录组织的启用仓库类型判断，这两个判断不能混为一体；
- 用户优先从现有商品中选择；商品不存在时，可以在业务单据中快捷创建；
- 当前组织范围内搜索不到时，系统必须继续检查全局同名商品：全局已有则禁止重复新增；
- 全局已有且当前组织可用时，直接选择已有商品；全局已有但组织没有对应仓库类型时，提示所需分类和仓库类型，并要求先配置仓库或联系管理员；
- 全局商品已停用、已删除或所属分类不可用时，同样禁止重复新增，并提示联系商品管理员处理原档案；
- 快捷创建输入商品名称、现有叶级分类和基础单位；
- 系统自动创建正式商品和一条默认 SKU，并回填当前单据明细；
- 商品分类要求的仓库类型必须与当前组织所选仓库匹配；
- 商品、SKU和业务单据必须在同一事务中保存，任一环节失败时整体回滚；
- 商品名称重复、同商品下 SKU 规格重复时禁止重复创建。

系统自动生成“默认规格”SKU，换算数量为 1；供应方式、商品形态和价格沿用既有后端默认值，不在快捷窗口中展示。

### 3.3 库位

- 库位继续作为业务单据中的自由文本字段；
- 库位不作为实时库存结存维度；
- 本期不建立库位历史表；
- 本期不开发个人库位推荐和历史摆放查询。

### 3.4 售后记录和客服进展

- “发货客服跟进”和“售后处理进展”是同一个需求；
- 用户在本系统创建一条售后主记录，并关联销售订单及相关商品；
- 一条售后主记录下面可以增加多条独立客服处理进展；
- 每条进展记录处理内容、状态、处理人和实际处理时间，作为后续操作证据；
- 新增进展不能覆盖售后主记录或历史进展；
- 编辑和软删除进展必须保留操作审计；
- 华数之家售后同步本期暂缓，当前只要求本系统内部售后功能可用。

### 3.5 菜单主列表 ID

- 每个菜单进入后的顶层主列表统一显示“序号 → ID → 原有业务列”；
- ID 是当前主记录真实数据库主键，并按字符串返回，避免 BigInt 精度丢失；
- Dashboard、汇总报表、弹窗明细、SKU 行、BOM 明细、展开子表和无单一主键的聚合表不在本需求范围；
- 当前代码已在通用基础资料、商品、分类、属性、采购、库存、生产、销售、领用和系统主列表中增加序号与 ID，仍需在实际浏览器中按菜单清单做最终复核。

### 3.6 OA审批集成

- 业务表单继续在华溯管家中创建和保存，华溯管家是业务数据主系统；
- 业务环节是否需要OA审批必须形成明确清单，不需要审批的环节继续使用现有流程；
- 需要审批的表单在本系统提交后，将约定的必要字段发送到OA，并进入“审批中”；
- OA是审批结果的唯一判定方，本系统不再执行一套重复的人工审批；
- OA只向本系统回传审批通过或不通过，并可同时回传OA流程编号、审批意见和审批时间；
- 本系统负责验证回调来源、幂等接收结果、更新本地表单审批状态并保留记录；
- 审批通过后，只有表单中指定的执行人或有明确授权的人员可以继续办理后续业务；
- 审批不通过时，表单不得继续执行业务，并应展示OA返回的结果和意见；
- 提供给OA的内容应为稳定的接口字段协议，不直接暴露数据库整表结构；
- 需要统一解决华溯管家账号与OA账号的人员标识映射。
- 普通销售订单来源于已经在线上完成的订单，不需要本系统或OA再次审批；保存后直接进入可办理状态；
- 折价销售单属于独立处置业务，不随普通销售订单取消审批，是否进入OA仍需单独确认。
- 采购退货必须进入OA审批；提交时不扣库存，只有OA审批通过后才执行唯一一次库存扣减并生成退款任务；
- 生产缺料清单不需要审批；一旦产生缺料，系统立即自动生成待审批采购申请，所有缺料采购统一在采购申请环节审批。

当前尚未确认哪些具体单据必须进入OA、每类单据的业务摘要字段和驳回后的本地状态处理规则，因此本项状态为“待设计和实施”，不能标记为已开发或仅待测试。

### 3.7 采购单据“更多”与操作记录

- 采购申请、采购订单、采购入库、采购退货、采购付款和采购退款的“更多”不得出现空菜单；
- 不论单据处于草稿、处理中、已完成或已关闭状态，“更多”都必须显示“操作记录”；
- “操作记录”展示当前单据的创建、提交、审批、入库确认、付款、退款及生成下游单据等可由现有业务数据准确还原的动作，并显示操作人、时间、结果和说明；
- “业务链路”属于内部追溯能力，本期不在采购管理菜单中向用户展示；
- 历史数据未单独保存某一步骤时间时，界面必须明确标注“历史表未单独保存”，不得使用其他更新时间冒充；
- 已完成单据继续隐藏已经失效的编辑、提交、审批和删除动作，但保留仍合法的后续动作，例如已入库单发起退货、付款记录撤销等。

本能力复用现有采购主表、明细表、审批字段、创建/更新时间和用户表，不新增数据库表、字段或数据字典。前端通过 `GET /purchase/:resource/:id/operation-history` 读取操作记录。

## 4.1 新增集成范围：OA审批

## 6. 本轮已采用的确认结论

1. 超级管理员默认查看全部组织的商品和分类；
2. 普通账号按自身登录组织过滤，普通账号没有任何启用仓库时商品和分类范围为空；
3. 本轮不新增跨组织切换器；
4. 快捷建档固定为商品名称、叶级分类、基础单位三个必填项；
5. 默认 SKU 使用“默认规格”、`pcs_qty=1`、`is_default=1`，价格为 0，供应方式和商品形态沿用既有系统默认值；
6. 采购订单来源入库保持商品只读，直接采购入库开放新商品快捷建档；
7. 保存采购申请草稿成功时也创建正式商品和默认 SKU，关闭或取消未保存表单不创建。
8. 商品名称唯一性按全局主档判断，组织仓库类型只决定可用性，不改变全局唯一规则。
9. 原十五项需求完成测试与OA新增集成范围分开管理，OA未开发不能被记录为原十五项的测试失败。
10. OA负责作出审批决定，本系统负责发起、接收可信结果、更新状态和控制后续执行权限。
