# 领用仓库范围扩展实施记录（纳入固定资产库/低值易耗品库/仓储库）

日期：2026-09-01
对应需求：领用管理（领用申请单 / 直接领用出库）
对应全局文档：`docs/global/plans/直接领用出库跨组织仓库改造计划.md`、`docs/华溯管家-可落地技术架构文档.md`

## 一、问题现象

- 账号 `19174164719`（黎名玉，十方清源 org 7 / 行政部）创建领用申请单时，仓库下拉只有 4 个：
  医疗耗材(9)、办公用品库(7)、办公设备库(5)、办公家具库(6)。
- org 7 实际有 9 个启用仓库，固定资产库(14)、低值易耗品库(15)、仓储库(16) 被排除。

## 二、根因排查结论

- `requisition.service.ts` 的领用仓库类型白名单初始为 `[4, 5, 6, 7, 8, 9, 10, 11, 12]`（行政类+健服类），
  前后端三处共用：`applicationFormOptions` 仓库下拉、`validateApplicationReferences` 保存校验、`directOutputOptions`。
- 白名单写死于初始代码，而字典中 14 固定资产库/15 低值易耗品库/16 仓储库为后补类型，白名单未同步扩展；
  `docs/global/plans/库存及业务规则改造计划.md` 明确"固定资产可以参与现有库存业务：…领用"。
- 附带发现业务矛盾：领用申请单商品下拉（`all-goods-options`）按组织**全部**仓库类型返回商品，
  org 7 共 1140 个商品，其中 507 个属于白名单外类型（type 1→18、14→18、15→464、16→7），
  这些商品永远匹配不到仓库，导致"选商品后仓库下拉为空、单据无法保存"。
- 结论：不是权限/数据范围 bug，而是白名单范围未覆盖业务已实际使用的仓库类型。

## 三、业务确认

2026-09-01 业务负责人确认：领用仓库范围扩展为
`[4, 5, 6, 7, 8, 9, 10, 11, 12, 14, 15, 16]`（行政类+健服类+固定资产库+低值易耗品库+仓储库）；
1 销售实体成品、2 生产原料、3 销售虚拟商品、13 生产备件 继续排除（走销售/生产/其它流程）。

- 领用模块自动化测试：`requisition.service.spec.ts` 30 项、`requisition-oa-approval.service.spec.ts` 6 项、
  `requisition-oa-callback.controller.spec.ts` 13 项，共 49 项全部通过。
- API 实际调用（账号 19174164719 / org 7）：
  - `GET /requisitions/application-form-options?orgId=7` → 仓库 4 个 → **7 个**（新增 47 仓储库、48 低值易耗品、51 固定资产库）；
  - `GET /requisitions/direct-output-options` → 7 个，均带组织名；
  - `GET /requisitions/product-options?orgId=7&warehouseId=48` → 返回低值易耗品库 464 个商品，此前"商品可选但仓库不可选"的死角解除。
- API 类型检查：requisition 相关 0 错误；全量类型检查仅剩既有外部同步测试（integrations）类型错误阻断，与本次无关（0828 实施记录已注明该历史问题）。
