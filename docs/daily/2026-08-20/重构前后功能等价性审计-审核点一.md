> 日期：2026-08-20

> 本阶段范围：只做静态功能审计与风险分级，不修改业务代码、不修改数据库。

## 1. 审计目标

确认 2026-08-19 前端从 `PurchasePage.vue`、`InventoryPage.vue`、`WorkflowPage.vue` 重构为“共享引擎 + 独立配置 + 独立表单 + 薄页面”后，旧版本已经实现的用户功能是否完整迁移。

本次审计坚持两项原则：

1. 保留当前模块化拆分架构，不以恢复旧功能为理由重新形成通用大文件。
2. 旧代码只作为功能基准；已经由业务负责人重新确认的新规则优先于旧代码。

## 2. 已确认的全局问题

### P0-01 共享引擎未接入页面操作权限

旧页面通过 `canAction` / `canPageAction` 控制新增、编辑、删除、审批、确认等操作。当前 `BusinessDocumentPage.vue` 只按 `config.creatable` 和单据状态展示按钮，没有读取页面操作权限。

影响：

- 无权限用户可能看见新增、编辑、删除、审批、过账等按钮；
- 点击后依赖后端返回 403，前后端权限表现不一致；
- 31 个共享引擎页面均受影响。

### P0-02 采购申请生成采购订单能力回退

旧版本已经提供：

- 整单生成；
- 选品生成；
- 关联订单；
- 专用预览弹框；
- 选择供应商、勾选明细、填写金额；
- 区分已生成和剩余可生成明细。

当前页面只有一个“生成订单”入口，直接跳转采购订单页面。`PurchaseApplicationOrderPreviewDialog.vue` 仍存在，但没有任何页面引用。

### P0-03 采购金额计算规则回退

业务已确认规则：用户输入明细总金额，系统按照“总金额 ÷ 本次采购数量”计算单价。

当前 `PurchaseOrderForm.vue` 改为用户输入单价，再按照“数量 × 单价”计算总金额，与确认规则相反。

### P0-04 采购退款金额编辑白名单未完整接入

`PurchaseRefundForm.vue` 只判断金额查看权限，没有判断金额编辑权限；满足退款状态条件时会显示登记退款和撤销流水操作。

影响：前端金额白名单行为与采购付款、销售收退款页面不一致，必须同时核对后端最终拦截。

### P1-01 采购操作记录未迁移

`PurchaseOperationHistoryDialog.vue` 仍存在，但当前新业务页面没有引用。原采购申请、订单、入库、退货等页面的“操作记录”入口消失。

### P1-02 单据追溯未迁移

`DocumentTraceDialog.vue` 仍存在，但当前新业务页面没有引用。采购、库存、生产、领用、销售的上下游单据追溯入口没有迁入新页面。

### P1-03 附件能力大面积未迁移

旧采购、库存和综合业务表单使用 `DocumentAttachments.vue`。当前共享表单体系没有提供附件挂载能力，仅一般出入库及少量生产专用弹框仍保留附件。

### P1-04 部分审批意见被固定值或空值替代

例如采购申请驳回直接提交“驳回”，不能填写真实原因；部分库存审批使用空意见。旧版本中采购申请、采购退货等驳回操作要求用户填写原因。

### P1-05 固定 720px 通用弹框不适合全部业务表单

当前共享引擎对所有表单统一使用 720px 弹框。采购订单、库存盘点、生产出库、售后进展等包含复杂明细的表单，原设计需要更大的业务弹框或专用布局。

### P1-06 当前分支类型检查未通过

API 测试文件存在 TypeScript 类型错误，集中在华溯之家、十方清源同步测试及部分 Prisma 查询类型。运行时可以启动，但不能认定当前分支已经完成工程验证。

## 4. 优先级汇总

### P0：先恢复或验证

1. 共享引擎页面和操作权限；
2. 采购申请整单生成、选品生成、关联订单；
3. 已生成申请明细防重复；
4. 采购订单总金额输入、自动计算单价；
5. 采购退款金额编辑白名单；
6. 采购申请到采购入库完整链路；
7. 所有库存过账、撤销、作废和重复操作防护；
8. 领用、生产、销售核心库存链路；
9. OA申请身份与审批结果回写；
10. 金额查看/编辑权限与后端最终校验。

### P1：P0稳定后恢复

1. 采购付款原操作入口；
2. 驳回原因输入；
3. 采购操作记录；
4. 单据追溯；
5. 业务附件；
6. 来源单据和后续单据跳转；
7. 生产补料明细；
8. 复杂业务弹框尺寸和布局；
9. 售后进展与退换货完整回归；
10. TypeScript 类型错误清理。

### P2：最终验收前完成

1. 查询条件和字段完整性；
2. 表格列宽、固定列、状态颜色和金额对齐；
3. 分页、空状态和错误提示；
4. 无效组件、死代码和重复请求清理；
5. 数量预警和有效期预警体验回归。

## 5. 推荐实施顺序

1. 业务负责人审核本清单及优先级；
2. 设计共享引擎扩展契约：权限、详情加载、业务弹框插槽、附件、追溯、操作记录；
3. 审核共享引擎设计，防止重新形成大文件；
4. 实施共享权限与扩展骨架；
5. 恢复 P0 采购生成和金额逻辑；
6. 浏览器验收采购界面；
7. 自动化验证采购链和数据库结果；
8. 验证全部库存事务；
9. 依次恢复领用、生产、销售和售后；
10. 完成角色矩阵、全链路回归和最终差异归零报告。

## 6. 审核点一需要确认的内容

1. 是否同意将“共享操作权限、采购拆单生成、采购金额规则、库存过账安全”列为最高优先级；
2. 库存盘点是否接受“先创建盘点单，再回列表编辑实盘数量”的新交互，还是恢复旧版同弹框连续操作；
3. 采购付款是否必须恢复到采购订单行操作，或同时保留付款页面直接登记；
4. 单据追溯、操作记录和附件是否统一作为 P1 恢复；
5. 是否按“采购 → 库存 → 领用 → 生产 → 销售/售后”顺序执行。

业务负责人确认审核点一后，进入共享引擎设计阶段；未确认前不修改业务逻辑。

## 7. 审核点一确认结果

业务负责人已于 2026-08-20 确认：

1. 同意将“共享操作权限、采购拆单生成、采购金额规则、库存过账安全”列为最高优先级；
2. 库存盘点必须恢复旧版“同一弹框内创建盘点单、载入明细、连续录入实盘数量并提交”的操作；
3. 采购付款必须恢复到采购订单行操作；
4. 单据追溯、操作记录和附件统一作为 P1 恢复；
5. 实施顺序确定为“采购 → 库存 → 领用 → 生产 → 销售/售后”。

据此进入审核点二：共享引擎扩展契约与独立业务组件边界设计。审核点二通过前，不实施业务逻辑。
