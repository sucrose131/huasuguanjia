# 采购单号唯一冲突修复实施记录

> 日期：2026-09-03
> 现象：临时采购入库提交报 `PrismaClientKnownRequestError: Unique constraint failed on uk_purchase_approve_no`（申请单号 PA 重复）
> Git 提交：feature=`5a93ad5`，test=`20a87a8`

## 根因
- 采购单号由 Redis `INCR` 按"前缀+业务日"发号，仅在 Redis key 不存在时用库内当日最大号作初始种子；
- 当库被重导/合并进更高单号、或多个后端实例在 Redis 计数不同步（或不同 Redis 库）时，会从落后/相同的位置继续发号 → 生成的 `pur_no` 与库内已有号冲突，`hspsi_purchase_approve.create` 唯一键失败。
- 本地核查佐证：Redis PA 计数=10，库内当日最大 PA=…005（多次失败重试已烧号产生空洞）。

## 交付
| 文件 | 改动 |
| --- | --- |
| `business-number.service.ts` | `INCREMENT_SCRIPT` 增加 dbMax（ARGV[3]）：每次发号前比较 Redis 计数与库内当日最大号，计数落后时先抬升到库内最大值再 INCR，杜绝与库内已有号冲突 |
| `purchase.service.ts` | `saveReceipt` 新建入库单（含临时采购入库自动生成申请/订单号）：把整段事务改为可重试，`pur_no/po_no/po_input_no` 唯一键冲突(P2002)时整事务重跑并重新发号（最多 3 次）；编辑已有入库单不自动发号，保持单次执行 |
| `business-number.service.spec.ts` | 断言 INCR 参数含库内托底值；新增"库内最大号作为 Redis 下限防导入冲突"用例 |
