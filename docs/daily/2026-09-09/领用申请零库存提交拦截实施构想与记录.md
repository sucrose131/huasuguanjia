# 领用申请零库存提交拦截实施构想与记录

日期：2026-09-09
对应需求：领用管理—领用申请单选择仓库后，选择无库存物品时提示且不允许提交。

## 一、需求确认与实施边界

- 零库存商品/SKU 仍保留在候选列表中，便于用户识别和暂存业务需求，不通过库存过滤候选。
- 用户选择商品、规格或切换仓库后，如果当前仓库对应 SKU 库存小于等于 0，页面立即提示“暂无库存，不能提交”。
- “保存草稿”仍允许；“保存并提交审核”必须拦截零库存明细。
- 本次只判断库存是否大于 0，不判断申请数量是否超过现存量，不新增库存预占。
- 明细未填写意向批号时按商品 + SKU 总库存判断；填写意向批号时，后端按对应批号库存判断。
- 首次提交和 OA 失败后的重新提交都执行相同的后端库存校验，不能通过绕过页面直接调用接口提交。
- 仓库确认出库时保留原有库存校验，处理申请后库存变化和并发操作。

## 二、数据库与字段核对

本次不新增表、字段、索引或数据字典，也不需要执行数据库脚本。

| 校验维度 | 数据来源 | 条件 |
| --- | --- | --- |
| 未指定批号 | `hspsi_inventory_total.inventory_qty` | `org_id + warehouse_id + goods_id + sku_id`，且库存记录未删除 |
| 指定批号 | `hspsi_inventory_batch_total.inventory_qty` | `org_id + warehouse_id + goods_id + sku_id + batch_no` |
| 提示商品名 | `hspsi_goods_info.goods_name` | `goods_id` |
| 提示规格 | `hspsi_goods_info_sku.spec_models` | `sku_id` |

前端继续复用 `GET /requisitions/all-goods-options` 返回的 `skuStockByWarehouse` 做即时提示；后端直接查询库存汇总表作为最终提交判断，避免仅靠前端控制。

## 三、界面与接口设计

### 3.1 页面交互

- 选择零库存规格后立即弹出警告。
- 零库存明细的规格列下方显示红色提示“当前仓库暂无库存，不能提交”。
- 切换仓库后重新计算所有已选明细并提示。
- 点击提交时再次统一检查；点击保存草稿不执行该拦截。

### 3.2 后端校验点

- `saveApplication(..., submit=true)`：在主数据合法性校验后、主表和明细写入前检查库存。
- `submitApplicationToOa(...)`：OA 重试前重新读取单据、明细和实时库存，通过后才调用 OA。
- 库存小于等于 0 或找不到对应库存记录时返回业务错误，并列出最多 3 条无库存商品规格。

## 五、风险与控制

- **库存并发变化**：申请提交通过后库存仍可能被其他业务消耗。本次不预占库存，最终以出库确认时的既有库存校验为准。
- **申请数量大于库存**：本次按已确认范围不拦截，只要当前库存大于 0 即可提交，避免改变“申请”和“实际出库”的业务分层。
- **历史草稿和 OA 重试**：历史单据重新提交时同样校验实时库存，可能被新规则拦截，这是预期行为。
- **批号口径**：页面即时提示使用 SKU 汇总库存，指定批号的精确库存由后端提交校验兜底；因此可能出现页面未标红但提交时报该批号无库存。
- **性能**：每次提交使用批量查询，不逐行访问数据库；不增加数据库结构和数据迁移风险。
