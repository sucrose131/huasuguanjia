## 3. P0-R01 实际改造

### 3.1 统一状态机

新增纯计算模块 `apps/api/src/purchase/purchase-order-lifecycle.ts`，统一输出：

- 订单主状态 1至6；
- 原始到货率和数量处理完成率；
- 普通待入库、普通可生成入库、换货待入库和换货可生成数量；
- 已入库实物退货、换货退回、换货补入和当前净留存；
- 剩余应付、待退款任务、未分配超付、退款异常关闭；
- “生成普通入库”、“生成换货入库”、“退回未到货”操作开关。

状态不再由某个单一动作直接写死，而是在入库确认/撤销、退货生效、付款新增/撤销、退款新增/作废、退款任务关闭后调用同一回算。

### 3.2 典型链路结果

| 场景 | 结果 |
| --- | --- |
| 全部未到货退回，无资金待办 | `6 已结束`，前端隐藏且后端禁止普通入库 |
| 部分入库＋其余退回，资金结清 | `6 已结束`；原始到货率保留真实比例，处理完成率100% |
| 已发生退回，仍有普通待入数量 | `5 退货处理中`，继续开放普通入库/退回未到货 |
| 数量已处理，仍有剩余应付 | 无退货时为 `4 已入库`；有退货时为 `5 退货处理中` |
| 换货退回已生效、尚未补入 | `5 退货处理中`，只按已生效换货数量开放“生成换货入库” |
| 退款流水作废后重新出现待退 | 由 `6` 重新打开到 `5` |
| 已入库订单撤销付款后出现待付 | 由 `6` 重新打开到 `4`；存在退货链时回到 `5` |
| 退款任务带余额关闭 | 允许 `6`，但明示“已结束（退款任务关闭）” |

### 3.3 入库、换货和并发保护

- 订单生成入库改为事务内锁定采购订单行，在锁内检查既有待入库单，避免并发重复生成。
- 普通入库 `inputType=1`、换货入库 `inputType=2`共用原入库单界面和原有 `purchase_input_type`字典，没有新编组件。
- 换货入库不再重复增加订单的原始到货快照；确认时校验累计数量不超过已生效换货退回数量。
- 入库确认先完成库存过账和入库单状态写入，再回算采购订单，避免回算看不到刚确认单据。
- 待入库锁定只扣减对应类型的可用数量，换货入库不会错误占用普通未到货退回额度。

### 3.4 生产缺料、待办和摘要

- 生产缺料来源订单允许供应商无法交货时退回未到数量，不再以“不能低于缺料数量”把原订单永久锁死。
- 退回后按实际已入库数量重新同步缺料；未补足时缺料恢复为待处理，未执行生产计划恢复为等待采购的状态。
- 采购订单待办只在 `6 已结束` 时完成，不再把状态4/5错当成完成。
- 列表摘要已改为按全库 `status=6` 统计已完成，其余为待处理；不再使用本页数据或错误的状态3口径。

## 8. 字典和历史订单回算

已新增可重复执行脚本：

```bash
cd apps/api
npm run backfill:purchase-order-lifecycles
```

脚本会：

1. 把 `purchase_order_status=5` 的字典名称改为“退货处理中”；
2. 逐单锁定并回算所有有效采购订单的付款快照和主状态；
3. 输出扫描数、成功数、失败数和逐单失败原因；
4. 如历史订单存在重复“商品＋SKU”，明确报错要求先合并，不会静默按价格分摊。

实际执行前已核对 `.env` 数据库目标正确，但本机无 3306 监听，也未安装可启动的 MySQL/MariaDB 服务；脚本返回 Prisma `P1001 Can't reach database server at 127.0.0.1:3306`。因此：

- 代码、字典改名逻辑和历史回算程序已完成；
- 本地数据库实际字典与历史订单还没有被写入；
- MySQL 在 3306 启动后必须执行上述命令并将结果补入本节，才能核销“数据回算”。
