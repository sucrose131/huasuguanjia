# P0-R01 采购订单全量退回未到货业务闭环问题复盘记录

> 日期：2026-08-26
> 分支：`dev`
> 当前状态：产品结论已确认并已进入实施；本文保留为原始复盘证据
> 后续记录：[P0-R01 及 P2-01 至 P2-03 剩余改造总实施记录](./P0-R01及P2-01至P2-03-剩余改造总实施记录.md)

## 1. 业务结论

采购订单的全部未到货数量都被退回后，订单已经不存在可继续履约的数量：

1. 采购订单状态应进入 `6 已结束`；
2. 前端不得再显示“生成入库”按钮；
3. 后端生成入库接口必须拒绝已结束订单，不能只依赖“剩余数量为 0”的末端校验；
4. 订单列表汇总中的“已完成”应按 `status=6` 统计。

部分退回时，只要仍有可履约剩余数量，订单仍可按剩余数量继续生成入库单；全量退回与部分退回必须分别验证。

## 2. 当前缺陷证据

- `apps/api/src/purchase/purchase.service.ts` 的 `recalcOrderStatus` 只汇总 `po_input_id > 0` 的到货后退货单，没有把 `po_input_id = 0` 的“退回未到货”单据作为退货数量参与状态判断。
- 当全部未到货数量退回时，`confirmedQty=0`、`confirmedReturnQty=0`，现有首个分支会把已开始采购的订单继续计算为 `2 采购中`，没有进入 `6 已结束`。
- `apps/web/src/views/business/configs/purchase-order.ts` 当前仅按状态 `2/3` 和 `isAllArrived` 控制“生成入库”按钮；错误状态会导致全量退回后按钮仍然出现。
- `generateReceipt` 当前只明确阻止状态 `1`，随后依靠“没有剩余可入库商品”兜底；业务状态和入口没有形成一致的双重保护。
- 采购订单列表汇总当前把 `status=3` 统计为 `complete`，与需求文档规定的 `status=6 已结束` 不一致。

## 3. 后续实施范围

1. 修正订单状态重算，覆盖未到货取消数量、实际入库数量和到货后退货数量的组合；
2. 修正前端“生成入库”的显示条件；
3. 修正后端生成入库接口的状态白名单和剩余数量校验；
4. 修正采购订单列表完成/待处理汇总口径；
5. 增加部分退回、全量退回、部分入库后退货、全量退回后禁止生成入库的自动化回归用例；
6. 不新增数据库表、字段或数据字典，不改变当前前端拆分架构。

## 5. 产品状态模型草案（待业务负责人确认）

本问题不能只按订单主表的一个 `status` 判断。采购订单页面必须同时表达四个互不替代的维度：

1. **订单主状态**：当前整条业务链路处于待采购、执行中、退货处理中还是已结束；
2. **数量履约结果**：原采购数量分别有多少已入库、未到货退回、已入库退货、换货待收和待入库；
3. **资金进展**：有效应付、累计付款、累计退款、剩余应付以及是否仍有待退款；
4. **单据任务进展**：是否存在待入库单、待生效退货单、待退款任务或换货入库任务。

订单主状态继续复用现有 `purchase_order_status` 的 1 至 6，不新增主表字段。建议把值 5 的产品语义由狭义的“部分退货”统一解释为“退货处理中”；是否同步修改字典中文名称，必须由业务负责人确认后再执行。

### 5.1 状态定义

| 状态值 | 当前名称 | 本次明确后的业务含义 | 允许的主要操作 |
| --- | --- | --- | --- |
| 1 | 待采购 | 订单尚未开始执行 | 查看、编辑、删除、符合条件时付款、开始采购 |
| 2 | 采购中 | 已开始采购，尚无确认入库，仍有正常待收数量，且没有进入退货/换货处理 | 查看、付款、生成入库、退回未到货 |
| 3 | 部分入库 | 已有确认入库，仍有正常待收数量，且没有进入退货/换货处理 | 查看、付款、生成入库、退回未到货 |
| 4 | 已入库 | 数量履约已经完成，但仍有正常付款或其他非退货资金事项未完成 | 查看、付款；实物退货从入库单发起 |
| 5 | 部分退货（建议产品语义：退货处理中） | 已发生未到货退回、实物退货或换货，且仍存在待收、待换货入库、待付款、待退款或待关闭事项 | 查看，并根据实际剩余数量开放正常入库、未到货退回、换货入库、付款或退款 |
| 6 | 已结束 | 数量义务、库存处理和资金任务均已完成或已按有原因关闭，不再存在可继续执行的业务动作 | 仅查看和业务链路追溯 |

### 5.2 数量和金额计算口径

以下数据均可从现有订单、入库、退货、付款和退款表计算，本轮原则上不新增数据库字段：

| 计算量 | 计算口径 |
| --- | --- |
| 原采购数量 | 订单明细 `qty` 合计 |
| 未到货退回 | 订单明细 `cancel_qty` 合计 |
| 正常待收 | `原采购数量－未到货退回－已确认正常入库`，不能用订单状态代替 |
| 待入库锁定 | 有效且状态为待入库的正常入库明细合计 |
| 已入库实物退货 | 已生效、退货类型为“采购退货”的来源入库退货数量 |
| 换货待收 | 已生效换货退回数量－已确认换货入库－待换货入库锁定 |
| 当前净留存 | 已确认正常入库＋已确认换货入库－已生效实物退货－已生效换货退回 |
| 数量处理完成率 | 已经完成入库或未到货退回的原订单数量 ÷ 原采购数量；换货任务未完成时不能显示整单完成 |
| 原始到货率 | 已确认正常入库 ÷ 原采购数量，用于如实说明原订单实际到货比例 |
| 有效应付 | 原始应付－已生效“采购退货”金额；“采购换货”不减少应付 |
| 净已付 | 累计有效付款－累计有效退款 |
| 剩余应付 | `max(有效应付－净已付, 0)` |
| 待退款义务 | `max(净已付－有效应付, 0)`，并与退款任务未退金额核对 |

`is_all_arrival` 当前实际更接近“有效收货义务是否完成”，不能再作为“原采购数量是否全部到货”的展示文案。按钮和接口必须直接依据逐行剩余可入数量判断。

### 5.3 订单结束条件

订单只有同时满足以下条件才进入 `6 已结束`：

1. 所有订单明细的正常待收数量为 0；
2. 所有换货待收数量为 0；
3. 不存在有效待入库单；
4. 不存在草稿、待提交、待审批或待办理的退货/换货单；
5. 剩余应付为 0；
6. 不存在待退款或部分退款任务；退款任务必须为“已退款”或有明确原因的“已关闭”；
7. 不存在尚未分配到退款任务的超付金额；
8. 生产缺料来源订单若取消未到货数量，必须同步恢复缺料或形成替代采购链路，不能静默把生产缺口当作已解决。

退款任务“已关闭”属于行政终结，不等于“已退款”。此类订单可以结束，但资金进展必须显示“退款任务已关闭（未全额退款）”，不得显示“已退款”或普通“已结清”。

### 5.4 典型业务场景矩阵

| 场景 | 订单主状态 | 数量/资金进展 | 是否允许继续入库 |
| --- | --- | --- | --- |
| 尚未开始采购 | 1 待采购 | 未执行 | 否 |
| 已开始、尚未入库、仍有待收 | 2 采购中 | 待收货 | 是 |
| 已入库一部分、仍有待收且无退货 | 3 部分入库 | 部分入库 | 是 |
| 原数量全部入库，但仍有待付款 | 4 已入库 | 到货完成、待付款 | 否；只能从已入库单发起实物退货 |
| 原数量全部入库且资金结清 | 6 已结束 | 全部入库、资金结清 | 否 |
| 未到货退回一部分，仍有正常待收 | 5 退货处理中 | 部分取消、仍待入库 | 是，按逐行剩余数量 |
| 入库一部分，剩余未到货全部退回，尚待付款或退款 | 5 退货处理中 | 部分入库、部分取消、资金处理中 | 否，正常待收为 0 |
| 入库一部分，剩余未到货全部退回，资金已结清/退款完成 | 6 已结束 | 已处理 100%；分别显示入库量和未到货退回量 | 否 |
| 全部未到货退回，未付款或无需退款 | 6 已结束 | 到货 0、未到货退回 100%、无资金待办 | 否 |
| 全部未到货退回，已付款但退款未完成 | 5 退货处理中 | 待退款或部分退款 | 否 |
| 已入库后发生采购退货，退款或剩余付款未完成 | 5 退货处理中 | 实物已退、资金处理中 | 否；普通采购退货不重新开放入库 |
| 已入库后采购退货，退款/付款均处理完成 | 6 已结束 | 显示最终净留存数量及退款结果 | 否 |
| 已入库后发起采购换货，替换商品尚未入库 | 5 退货处理中 | 换货待入库 | 只允许生成“换货入库” |
| 换货商品已重新入库，但订单仍有待付款 | 4 已入库 | 换货完成、待付款 | 否 |
| 换货商品已重新入库且资金结清 | 6 已结束 | 换货完成、资金结清 | 否 |
| 退款任务被有原因关闭且无其他业务待办 | 6 已结束 | 异常结束：退款任务已关闭，保留未退金额 | 否 |

### 5.5 反向纠错必须重新打开订单

- 作废退款流水后，如果重新出现待退款金额，订单由 6 回到 5；
- 撤销付款后，如果重新出现剩余应付，普通完整入库订单由 6 回到 4，存在退货链路的订单回到 5；
- 撤销待入库单后释放锁定量，订单重新根据已确认入库和剩余数量回到 2、3 或 5；
- 退货被驳回或删除草稿时，只有已生效退货量参与订单状态，草稿和驳回单不得减少数量或金额；
- 已结束订单不允许普通编辑，只有具备权限的反向单据或纠错动作可以触发重算，并保留操作日志。

## 6. 全面复盘新增发现

以下问题需要和 P0-R01 一并处理或明确拆出，不得只修“全部未到货退回后状态错误”：

1. **订单状态重算不完整**：当前只在未到货退回、确认/撤销入库和实物退货生效时调用；付款、撤销付款、退款完成、退款流水作废、退款任务关闭均不会重算订单。
2. **未到货退回未参与退货状态判断**：状态重算只查询 `po_input_id>0` 的实物退货，漏掉 `po_input_id=0` 的订单未到货退回。
3. **状态 5 的前后端语义冲突**：需求规定可以根据剩余数量继续后续处理，但前端只允许状态 2/3 生成入库和退回未到货；待办同步又把状态 5 直接视为已完成。
4. **换货链路没有闭环**：系统已有“采购换货”和“采购换货入库”字典，但换货退回后没有重新形成换货待收数量，状态 5 也不能生成换货入库。
5. **到货进度口径冲突**：列表当前使用 `arrival_qty/pcs_qty`，需求文档写的是 `arrival_qty/有效采购数量`；两者分别代表原始到货率和有效履约率，不能只保留一个模糊百分比。
6. **`is_all_arrival` 名称与实际语义不一致**：取消未到货后，已入库达到有效采购数量就会写 1，但这不代表原订单全部到货。
7. **订单摘要统计错误**：当前把状态 3 计入“已完成”，需求规定应按状态 6 统计。
8. **退款关闭与资金结清混淆**：退款任务可以带剩余金额关闭，订单必须显示异常关闭结果；现有 `pay_status` 只有是否结清，无法单独表达“退款关闭但未全退”，需要使用退款任务计算展示，不能伪造已退款。
9. **生成入库并发风险**：生成入库前的既有待入库查询发生在事务和订单行锁之外；并发请求可能同时生成多张待入库单，与“同一订单仅一张有效待入库单”的规则不一致。
10. **结束判断不能只按总量聚合**：必须逐订单明细判断剩余数量；仅用订单总数量可能掩盖不同商品/SKU之间尚未完成的明细。
11. **重复商品/SKU的退款单价存在歧义**：订单明细没有限制同一商品/SKU只能出现一次，退货明细也没有保存来源订单明细 ID；当前退款金额按 `goods_id+sku_id` 查单价，若同一订单重复 SKU 且价格不同，退款金额可能取错。实施前需确认“禁止同订单重复 SKU”或补充可追溯方案，未经确认不新增字段。
12. **生产缺料来源不能静默结束**：当前会阻止取消后低于生产缺口，但供应商确实无法交货时仍需要业务出口；应恢复缺料并允许形成替代采购订单，而不是让原订单永久无法结束。
13. **退货流程基线不一致**：采购需求文档写“实物退货提交即完成”，当前代码和界面实际采用草稿、提交、OA/人工审批后扣库存。订单状态只能以“已生效退货”为准，但最终采用哪条产品流程需要业务负责人确认。
14. **环境文档过期**：采购需求文档仍写 `hspsi-dev-ai-02`，项目强制规则和 `apps/api/.env` 实际指定 `127.0.0.1:3306/hspsi-dev`。本次已按项目强制规则核对；本地数据库服务当前未启动，因此尚未读取实际字典数据，不做任何数据库写入。

## 7. P0-R01 建议实施边界

本项确认后建议一次完成以下内容：

1. 建立一个统一的订单状态/进展计算函数，所有入库、退货、付款、退款和反向纠错动作调用同一口径；
2. 后端所有操作使用逐行剩余数量和任务状态做最终校验，前端只同步展示同一规则；
3. 订单列表和查看弹框增加“履约结果/业务进展”计算展示，不新增可编辑字段；
4. 修复状态 5 的可操作性、待办完成条件、摘要统计和 `is_all_arrival` 误用；
5. 补齐普通采购退货与采购换货的不同数量、金额和入库规则；
6. 对生成入库增加订单行锁和幂等保护；
7. 覆盖全部典型场景、反向纠错、并发重复请求和生产缺料联动自动化测试；
8. 业务负责人确认前不修改数据库表、字段和字典中文名称。
