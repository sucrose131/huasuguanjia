## 1. 本项业务范围

用户从采购订单列表点击“生成入库”后，系统生成或取得该订单现有的待办理入库单，进入采购入库页面并自动打开“办理采购入库”弹框。用户必须在弹框中核对和填写本次入库数量、批次、效期、库位等信息，再点击“执行入库”。

本项同时消除采购入库列表中绕过该弹框直接“确认入库”的入口。

明确不包含：

- P0-02“退回未到货”弹框；
- 采购订单新增/编辑弹框的运输、物流、金额与首次付款区域；
- 其他采购、库存、生产、销售和领用页面；
- 后端业务逻辑、数据库结构和数据字典变更。

## 2. 旧分支产品基准

旧版 `apps/web/src/views/PurchasePage.vue` 的交互为：

1. `generateReceipt(row)` 调用 `POST /purchase/orders/:id/generate-receipt`；
2. 成功后执行 `router.push({ path: '/purchase/receipts', query: { receiptId: result.id } })`；
3. 采购入库页面监听 `receiptId`，加载 `GET /purchase/receipts/:id` 后以编辑模式打开入库弹框；
4. 弹框复用 `PurchaseReceiptDetails`，允许填写本次入库数量、批号、库位、生产日期、有效期、到货日期和备注；
5. 弹框底部为“取消”和“执行入库”，不提供绕过明细填写的列表直接确认入口；
6. “执行入库”要求用户同时具备当前新增/编辑权限和确认入库权限。

旧版 `apps/web/src/components/PurchaseReceiptDetails.vue` 与当前同名组件执行 `git diff fix/0818-dashboard-org-scope..HEAD` 无差异。本次继续复用该旧版组件，没有重新设计或复制组件。

## 3. 改造前缺失证据

1. 当前 `purchase-order.ts` 生成入库成功后只显示消息，没有跳转或打开入库弹框；
2. 当前 `purchase-receipt.ts` 已经具备 `receiptId → 加载详情 → openEdit` 的深链处理，但上游没有传入 `receiptId`；
3. 当前采购入库列表额外存在“确认入库”，直接调用确认接口，用户可以不进入分批入库弹框；
4. 当前入库表单底部额外存在旧版没有的“保存”按钮，弱化了旧版“填写明细后执行入库”的明确操作路径；
5. 当前“执行入库”按钮没有恢复旧版确认权限显示条件。

## 4. 实际改造

### 4.1 采购订单生成后打开入库弹框

修改 `apps/web/src/views/business/configs/purchase-order.ts`：

- 保留原生成入库接口和成功消息；
- 接收当前共享引擎的 `ctx`；
- 生成成功后调用 `ctx.navigate('/purchase/receipts', { receiptId: String(result.id) })`；
- 复用 `purchase-receipt.ts` 已有的 `openFromRoute`，加载详情并打开当前拆分后的 `PurchaseReceiptForm`。

### 4.2 禁止绕过分批入库弹框

修改 `apps/web/src/views/business/configs/purchase-receipt.ts`：

- 删除列表级 `confirm` 行操作；
- 待入库单继续显示“办理入库”；
- 用户必须进入入库表单填写或核对明细后才能执行确认。

### 4.3 恢复旧版弹框底部操作和权限条件

修改 `apps/web/src/views/business/forms/PurchaseReceiptForm.vue`：

- 保留“取消”和“执行入库”；
- 删除旧版不存在的独立“保存”按钮；
- “执行入库”恢复为同时校验新增/编辑权限和 `purchase:receipts:confirm` 权限；
- 继续复用现有 `PurchaseReceiptDetails` 和当前 Form 拆分结构；
- 保存失败或确认失败时保持弹框打开，允许修正或重试。
